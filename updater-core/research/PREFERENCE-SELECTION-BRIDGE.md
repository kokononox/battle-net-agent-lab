# Preference → candidate bridge — 0.26

## Problem fixed, without claiming vendor semantics
The previous layer parsed and preserved `.build.info` clauses but the candidate was still checked only against a separately supplied mandatory typed profile. This layer connects the two. `preference_selection_bridge.review_preference_candidate` accepts raw owned metadata copies (not caller-asserted facts), validates the Retail baseline/config content key, reruns the existing full target/plan/catalogue/decoded metadata identity gate, binds exact ProductConfig to the saved target versions table, then evaluates the observed PUBLIC clauses with optional markers preserved against both manifests.

It never rewrites language aliases silently: if release-bound ProductConfig canonical locales differ from observed input, a review/replan is required and the integration stops (an earlier strict missing-tag gate can also stop first). Original architecture tokens are not silently remapped to target tags. The strict typed-profile bitmap is a comparison, not a fallback. Both observed-clause and strict-profile selections must agree with the existing identity-verified candidate for integration to return. There is no new candidate database, file activation or writer.

Privacy-critical change: dropping optional acct/geoip terms merely because they are private would change a query if the same name existed in the manifest. Their names are checked internally against BOTH validated tag tables. Only when absent in both may they be omitted in this candidate grammar; if present in either table, stop with a fixed code and no private value echo. Four historical private qualifiers were absent and withheld. No raw private token or installation path is emitted. This is not a proof of official private-tag semantics outside this candidate grammar.

The pure tag review can audit an absent optional public region/category independently per manifest. It retains the missing term and reports strict comparison unavailable rather than guessing a mandatory default. The full candidate integration does not permit this to bypass the existing strict gate. Unknown features/types, wrong-kind optional dimensions, missing mandatory tags, duplicate public clauses and inconsistent metadata stop. Unknown vendor behavior remains unqualified; applicable extra_tags are facts in the attached ProductConfig report, not silently applied or declared disabled.
