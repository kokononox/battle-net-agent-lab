# WLab Snapshot 0.1.4

ابزار تازه برای گرفتن **یک snapshot از حافظهٔ بازی و استخراج گزارش کوچک کد**. این همان ابزار قبلی WLab-OneClick/CDB نیست.

## تغییر این نسخه: ذخیره روی درایو بازی

طبق درخواست کاربر، پوشهٔ هر اجرا، `snapshot.dmp` و `READY-TO-SEND.zip` اکنون روی **درایو فایل Wow.exe انتخاب‌شده** ساخته می‌شوند، نه درایو LocalAppData و نه محل اجرای WLab. مثلاً اگر بازی روی D باشد، خروجی این‌جاست:

```text
D:\WLabSnapshot\YYYYMMDD-HHMMSS-ID\
```

فایل‌های نصب بازی دستکاری نمی‌شوند؛ خروجی پوشه‌ای مستقل در ریشهٔ همان درایو دارد. برای مسیر فاقد drive letter محلی یا خطای نوشتن، برنامه خطا می‌دهد؛ بی‌سروصدا به C یا مسیر دیگری برنمی‌گردد. فضای خالی و لغو زیر ۱ GiB روی **درایو خروجی جدید** بررسی می‌شوند. حداقل ۸ GiB پیش از capture حفظ شده است؛ ۱۶ گیگابایت گزارش‌شده توسط کاربر تضمین کفایت برای dump کامل نیست. مقدار واقعی فضای آزاد، drive و مسیر خروجی در گزارش جدید ثبت می‌شوند.

cache کوچک ابزار Microsoft، لاگ launcher و قفل مشترک نسخه‌ها همچنان در LocalAppData می‌مانند؛ فقط خروجی حجیم و گزارش اجرا منتقل شده‌اند. پس اگر درایو سیستم حتی برای فایل‌های کوچک جا نداشته باشد، آن خطا مستقل است.

گزارش اجرای 0.1.3 نشان داد آزمون دو فرزند و آماده‌سازی موفق، هش فایل بازی مطابق و امضای Microsoft معتبر بوده‌اند. capture_started=false و خطای حداقل ۸ GiB رخ داد؛ بنابراین عادی‌بودن بازی در آن تلاش، شاهد پایداری حین snapshot نیست. گزارش کاربر «عادی بود» با همین محدودیت ثبت شده است.

## اصلاح نتیجهٔ مبهم آماده‌سازی

گزارش کاربر از نسخهٔ 0.1.2 فقط `run.json` داشت: `capture_started=false`، وضعیت `preparation_failed` و `prepare_exit_code=null`. لاگ رابط نیز توقف در همین مرحله را نشان می‌دهد. بنابراین این تلاش شاهد ایجاد dump، اختلال بازی یا شکست قطعی دانلود نیست. در کد قبلی، نتیجهٔ null با مقایسهٔ مستقیم به‌اشتباه شکست شمرده می‌شد. علت دقیق null روی Windows کاربر هنوز اثبات نشده است.

از 0.1.3 اجرای helperها از `Start-Process -PassThru` به `System.Diagnostics.Process.Start` با handle متعلق به خود برنامه تغییر کرده است. صفر، غیرصفر و وضعیت نامعلوم جدا ثبت می‌شوند؛ null دیگر صفر یا شکست عادی فرض نمی‌شود. stdout، stderr و نتیجهٔ هر مرحله در فایل‌های مستقل نگه داشته می‌شوند و گزارش کوچک آن‌ها را نیز جمع می‌کند.

پیش از دانلود و پیش از هر دسترسی capture به بازی، دو پردازش آزمایشی متعلق به WLab با کد خروج **0 و 7** اجرا می‌شوند. **کد 7 در این آزمون عمدی است و خطای بازی نیست.** دریافت صحیح کد خروج و هر دو جریان خروجی الزام می‌شود؛ شکست آزمون، capture را متوقف می‌کند. این کنترل، آزمون واقعی ProcDump یا تضمین پایداری بازی نیست.

اصلاح نمایش 0.1.2 حفظ شده است: `CREATE_NO_WINDOW` بدون درخواست SW_HIDE برای رابط، بررسی پنجره با PID و عنوان دقیق، و ثبت `window-state.json`. از رسیدن کاربر به دکمهٔ Capture در اجرای قبلی، نمایش رابط در آن تلاش قابل استنباط است؛ اما اجرای واقعی رابط 0.1.4 در محیط ساخت Linux آزموده نشده است.

پیام پایان نیز اصلاح شده: اگر capture شروع نشده باشد، دیگر ادعای وجود `snapshot.dmp` نمی‌کند.

## سابقهٔ قفل شروع



در 0.1.0 کاربر پیش از دسترسی به رابط، پیام «already open» دید. از این گزارش به‌تنهایی معلوم نیست یک رابط قبلی واقعاً فعال بوده یا قفل به‌صورت نامناسب مانع شروع شده است؛ مالک قفل روی سیستم کاربر تأیید نشده است.

در این نسخه، **قفل Mutex هنگام بازشدن رابط حذف شد**. چند پنجره می‌توانند باز شوند، اما ثبت snapshot در یک زمان برای این کاربر، با handle انحصاری `capture.lock` محدود می‌شود. وجود فایل قدیمی به‌تنهایی مانع نیست؛ بازبودن handle است که تلاش دوم را متوقف می‌کند. این قفل به بستن هیچ فرایند دیگری متکی نیست. بعد از خروج فرایند، handle توسط سیستم آزاد می‌شود.

بررسیِ وجود ProcDump دیگر نیز همچنان پیش از capture برقرار است. نسخهٔ 0.1.0 از قفل فایل تازه خبر ندارد؛ برای این آزمایش فقط نسخهٔ 0.1.4 را به کار ببر و در نسخهٔ قدیمی Capture نزن. اگر capture پس از لغو هنوز در حال اجرا باشد، وضعیت نامطمئن ثبت و قفل تا بسته‌شدن رابط نگه داشته می‌شود؛ وجود ProcDump فعال نیز مانع تلاش جدید است.

لاگ شروع هر بار مستقل است و روی لاگ بازِ اجرای قبلی نوشته نمی‌شود. اگر بازشدن رابط تأیید نشود یا PowerShell با خطا خارج شود، پوشهٔ لاگ باز می‌شود. هیچ بستن اجباری PowerShell، بازی یا نسخهٔ قبلی در این اصلاح وجود ندارد.

## اجرای بعدی — فقط یک تلاش با نسخهٔ جدید
1. ZIP را **Extract** کن و `WLab-Snapshot-0.1.4.exe` را اجرا کن. درخواست دسترسی Administrator ویندوز را، اگر نمایش داده شد، تأیید کن.
2. بازیِ آزمایشی را باز نگه دار. اگر در فهرست نبود، **Refresh** را بزن. نسخهٔ پشتیبانی‌شده فقط همان `12.1.5.70448` با SHA256 ثبت‌شده است؛ فایل متفاوت باعث توقف بدون capture می‌شود.
3. مرحلهٔ فعلی را انتخاب کن: **Character selection** برای صفحهٔ انتخاب شخصیت یا **In world** برای داخل محیط بازی. این انتخاب، گزارش خودت است؛ برنامه مرحله را تشخیص نمی‌دهد. برای این گام ورود به محیط بازی لازم نیست.
4. با **View EULA** شرایط ابزار Microsoft را بخوان؛ در صورت پذیرش، کادر پذیرش را علامت بزن و **Capture once** را فشار بده.
5. صبر کن تا پوشهٔ نتیجه باز شود. **فقط `READY-TO-SEND.zip` را بفرست** و بگو بازی عادی و قابل استفاده ماند، فریز شد یا بسته شد. اگر خطا ثبت شد هم همان گزارش را بفرست و capture را فعلاً تکرار نکن. اگر `snapshot.dmp` واقعاً ایجاد شد، فایل بزرگ را روی دستگاه نگه دار؛ گزارش کوچک dump کامل را شامل نمی‌شود. اگر capture شروع نشد، وجود dump انتظار نمی‌رود.

نصب Python، دیباگر، واردکردن PID یا دستور لازم نیست. برنامه خودش بازی را اجرا نمی‌کند. دکمهٔ capture در هر بار بازکردن ابزار فقط یک بار تلاش را آغاز می‌کند؛ تلاش مجدد خودکار ندارد.

## نیازمندی‌ها
- Windows 11 x64؛ یا Windows Server 2016+ با محیط دسکتاپ و Windows PowerShell 5.1 و WinForms.
- اینترنت در اولین اجرا برای دریافت مستقیم ProcDump از Microsoft؛ در اجراهای بعد، نسخهٔ دارای هش صحیح از cache محلی استفاده می‌شود.
- حداقل ۸ GiB فضای خالی در درایو بازی انتخاب‌شده که خروجی روی آن ذخیره می‌شود. **این فقط حداقل بررسی‌شده است، نه سقف اندازه یا تضمین کفایت فضا.** full dump ممکن است چندین GiB و بزرگ‌تر باشد؛ زیر ۱ GiB فضای خالی درخواست لغو صادر می‌شود.
- نصب بازی باید همان hash پشتیبانی‌شده را داشته باشد. نسخهٔ تازهٔ بازی با آدرس‌های قدیمی بررسی نمی‌شود.

`WLab-Snapshot-0.1.4.exe` ساختهٔ این پروژه و **بدون امضای ناشر تجاری** است. امضای Microsoft فقط برای ProcDump دریافت‌شده بررسی می‌شود؛ ابزار WLab را نباید فایل امضاشدهٔ Microsoft تصور کرد. تنظیمات امنیتی/ExecutionPolicy/فایروال تغییر نمی‌کنند. اگر سیاست سیستم اجرا را ممنوع کند، دورزدن آن در ابزار وجود ندارد.

## دقیقاً چه می‌کند؟
- فرایندهای Wow را فهرست می‌کند و انتخاب کاربر، PID و زمان شروع را ثبت و پیش از ثبت تصویر دوباره تطبیق می‌دهد.
- بستهٔ ProcDump را فقط از `https://download.sysinternals.com/files/Procdump.zip` دریافت می‌کند. اندازه/هش ZIP و هش فایل اجرایی pin شده‌اند؛ redirect فقط به همان میزبان HTTPS مجاز است.
- پیش از اجرا، **Authenticode معتبر و ناشر Microsoft Corporation** را در ویندوز الزام می‌کند. اعتبار واقعی امضا در محیط Linux ساخت بررسی نشده؛ این gate هنگام اجرا روی ویندوز اعمال می‌شود.
- بعد از پذیرش صریح EULA توسط کاربر، یک بار ProcDump را با آرگومان‌های زیر اجرا می‌کند:

```text
-accepteula -ma -r 1 -n 1 -at 120 PID snapshot.dmp
```

طبق مستندات Microsoft، `-r` در Windows 8.1+ از PSS/clone و `-ma` از full dump استفاده می‌کند. **این انتخاب تضمین نمی‌کند بازی بدون توقف/خطا بماند یا کدِ لازم حتماً قابل تحلیل شود.** این wrapper، CDB، Frida، exception monitoring، تزریق، patch، خاتمهٔ بازی، نصب debugger پسامرگ، ارسال به WER یا تغییر شبکه درخواست نمی‌کند. ProcDump برای snapshot به خود فرایند دسترسی می‌گیرد؛ این روش «صرفاً خواندن فایل روی دیسک» نیست.

- اگر ProcDump دیگری باز باشد، شروع نمی‌کند. درخواست لغوِ capture با روش مستند `-cancel PID` است؛ Microsoft می‌گوید این درخواست همهٔ ProcDumpهای ناظر همان PID را لغو می‌کند. برنامه کنترل انحصاری بر ابزارهایی که کاربر بعداً جداگانه باز کند ندارد.
- timeout ابزار رسمی ۱۲۰ ثانیه و timeout wrapper برای درخواست لغو ۱۸۰ ثانیه است. اگر پس از ۳۰ ثانیه خروج capture تأیید نشود، وضعیت **نامطمئن/هنوز در حال اجرا** ثبت می‌شود؛ بازی یا capture به‌زور کشته نمی‌شوند. این timeoutها سقف سخت I/O، اندازهٔ dump یا مدت توقف نیستند.
- لغوِ مرحلهٔ دانلود فقط helper متعلق به خود WLab را متوقف می‌کند؛ نه بازی.
- پس از capture، minidump به‌صورت آفلاین خوانده می‌شود. هویت فایل دیسک با SHA256 کامل و هویت ماژول حافظه با نام، timestamp، اندازهٔ image و سرآیند PE تطبیق می‌یابد؛ این تطبیق، هش کامل تمام کد بارگذاری‌شده نیست.
- دادهٔ سه تابع نامزد قبلی و حداکثر سه صفحهٔ ۴ KiB اطراف آن‌ها استخراج می‌شود. نبود حافظه، به‌عنوان **missing** ثبت می‌شود؛ صفرگذاری یا فرض برابری نمی‌شود.
- ASLR با پایهٔ ماژول داخل dump لحاظ می‌شود. مقایسهٔ بایت‌ها **raw** است؛ relocationها normalize نمی‌شوند، پس اختلاف بایت لزوماً بازشدن/رمزگشایی کد نیست.
- پس از استخراج، تا ۶۰ ثانیه بقای همان فرایند و مقدار `Responding` نمونه‌برداری می‌شود. این‌ها پایداری یا قابل‌استفاده‌بودن بازی را ثابت نمی‌کنند؛ تأیید کاربر لازم است و خطای دیرتر نیز ممکن است رخ دهد.

## چه چیزی ثابت نمی‌کند؟
این ابزار packet capture، TLS decryption، ردیاب serialization یا اثبات ارسال BIOS نیست. حتی اگر کد حافظه با دیسک فرق کند، باید آن را تحلیل کرد. ارسال یا عدم ارسال CPU/BIOS روی TCP/3724 هنوز **نامشخص** است.

موفقیت build، موفقیت ایجاد dump، حضور بایت‌های هدف و پایداری بازی چهار موضوع جدا هستند. `snapshot_extracted_observation_complete` تنها پایان مراحل ضبط/استخراج/مشاهده را می‌گوید، نه اثبات سلامت بازی یا ارسال شبکه.

## فایل‌های خروجی
پوشهٔ هر اجرا جداست:

```text
GAME-DRIVE:\WLabSnapshot\YYYYMMDD-HHMMSS-ID\
    snapshot.dmp
    report\run.json
    report\analysis.json
    report\*.bin
    report\procdump.stdout.txt
    report\procdump.stderr.txt
    READY-TO-SEND.zip
```

در خطا ممکن است بعضی فایل‌ها موجود نباشند. گزارش آمادهٔ ارسال JSONها، قطعه‌های کوچک کد و لاگ‌های مستقل آماده‌سازی، آزمون فرزند، ProcDump، استخراج و لغوِ موجود را برمی‌دارد؛ dump کامل داخل آن نیست. هیچ ارسال خودکار، telemetry، زمان‌بندی یا آپلود GitHub در برنامه وجود ندارد. dump خودکار پاک نمی‌شود.

اگر پیش از بازشدن رابط خطا رخ دهد، پوشهٔ لاگِ همان اجرا باز می‌شود؛ فایل `launcher.log` آن را بفرست. مسیر معمول `%LOCALAPPDATA%\WLabSnapshot\launcher\startup-*\launcher.log` است. در صورت UAC دو مرحلهٔ شروع با پوشه‌های جدا وجود دارند؛ فایل `elevation-handoff.txt` مشخص می‌کند کدام مرحله فقط درخواست elevation کرده است. اگر دریافت/هش/امضای ابزار شکست خورد، گزارش خطا را بفرست؛ جایگزین ناشناخته اجرا نکن.

## وضعیت آزمون
- ۲۵ آزمون Go، vet برای Linux و Windows، ساخت Windows x64 GUI و یکسان‌بودن دو build انجام شده‌اند؛ جزئیات در `QA.json`.
- پنج fixture مصنوعی استخراج، آزمون قفل میان پردازش‌های مستقل و آزمون واقعی اجرای ۱۰ پردازش کوچک با خروج صفر/غیرصفر در **Linux PowerShell/.NET** موفق بوده‌اند.
- بررسی نحو PowerShell انجام شده؛ این‌ها جای اجرای Windows PowerShell 5.1، WinForms و ProcDump روی دستگاه کاربر را نمی‌گیرند. نسخهٔ جدید پیش از capture، کنترل محدود کد خروج را روی همان دستگاه اجرا می‌کند. helper نگاشت مسیر درایو بازی نیز با چهار مسیر و چهار رد مسیر نامعتبر و mock فضای آزاد آزمایش شده؛ این آزمون نوشتن روی volume واقعی Windows نیست.
- **capture واقعی این روش هنوز تأیید نشده و سؤال ارسال CPU/BIOS روی TCP/3724 همچنان بی‌پاسخ است.**
- بسته هیچ فایل بازی، dump واقعی یا باینری Microsoft برای بازتوزیع ندارد. ProcDump مستقیماً روی دستگاه مصرف‌کننده دریافت می‌شود.

## منبع و بازسازی
منبع Go و PowerShell در `source/` است. launcher متن UTF-8 رابطِ embedشده را از stdin به Windows PowerShell می‌دهد؛ سیاست اجرای سیستم را تغییر نمی‌دهد. CLIهای داخلی `--child-probe`، `--prepare`، `--extract` و `--bundle` برای همان مراحل wrapper هستند؛ نیازی به استفادهٔ دستی کاربر نیست.

متن helper قفل و helper اجرای فرزند نیز همراه رابط embed می‌شوند. آزمون اجرای فرزند برای توسعه‌دهنده:

```sh
pwsh -NoProfile -File source/tests/child-runner-regression.ps1 -Helper source/child-process.ps1 -Exe PATH/TO/NATIVE/WLAB -Work NEW_WORK_DIR
```

 برای بازتولید آزمون مستقل قفل، PowerShell و Python لازم است (فقط برای توسعه‌دهنده، نه استفاده‌کنندهٔ ابزار):

```sh
python source/tests/lock-regression.py PATH/TO/pwsh source/capture-lock.ps1
```

با Go منطبق با provenance، در Linux یا محیط دارای cross-compile:

```sh
cd source
sh build.sh
```

برای بازتولید fixtureهای مصنوعی مبتنی بر ورودی همان build:

```sh
cd source
go build -o wlab-extract .
python tests/integration.py ./wlab-extract INPUT/Wow.exe NEW_WORK_DIR
```

fixtureها فقط byte windowهای روی دیسک را در قالب minidump مصنوعی قرار می‌دهند؛ نتایج آن‌ها شواهد runtime نیستند. فایل‌های حاصلِ آزمایش و ورودی بازی نباید وارد commit شوند.
