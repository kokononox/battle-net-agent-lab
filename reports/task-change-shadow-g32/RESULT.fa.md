# G32 — جهت Enabled و دو قاعدهٔ پیشنهادی در همان VM

## نتیجهٔ اصلی
در یک کنترل ۲۷۰ثانیه‌ای بدون اجرای Setup، مقدار Enabled برای PrintJobCleanupTask از **true به false** تغییر کرد. هم API Task Scheduler در snapshotها و هم تفاوت XML در همان VM این جهت را پشتیبانی می‌کنند. فقط فیلد `Task/Settings[1]/Enabled[1]` تغییر کرد؛ Actions، Principals، مجوزها، binding و فایل مرتبط ثابت ماندند.

در لاگ همان Task، رخدادهای شروع (100)، غیرفعال‌شدن (142)، پایان action (201) و پایان task (102) ثبت شدند. اما رخدادها ClientProcessId نداشتند؛ هم‌زمانی با پایان اجرا، خودغیرفعال‌سازی توسط DLL یا هویت دقیق فراخوان را ثابت نمی‌کند. PID سرویس ارائه‌دهندهٔ لاگ به‌جای عامل تغییر استفاده نشد. عامل دقیق همچنان اثبات نشده است.

این مشاهده مربوط به همین کنترل بدون Setup است؛ نباید آن را انتساب قطعی همهٔ تغییرهای G26/G29 یا اثبات بی‌خطر بودن ACL دانست. Enabled در این نوبت افزایش قابلیت نبود، اما برای آن هیچ معافیت خودکاری صادر نشد.

## ارزیابی پیشنهادی دو زمان‌بندی
هر دو تغییر واقعی زیر در حالت shadow شروط سخت‌گیرانه را گذراندند:

| Task | تنها تفاوت مجاز در XML | نتیجهٔ shadow |
| --- | --- | --- |
| RefreshCache | TimeTrigger / StartBoundary | candidate_matches_strict_shape=true |
| Registration | TimeTrigger / StartBoundary | candidate_matches_strict_shape=true |

شرط‌ها شامل هویت دقیق Task، XML با یک TimeTrigger/StartBoundary معتبر، برابر بودن همهٔ XML پس از جایگزینی فقط همان مقدار، pin دقیق Actions/Principals/مجوزها/فایل، ثبات binding، و امضای Microsoft تازه‌بررسی‌شده در baseline همان VM پیش از گیت بود. pinها از مشاهدات اعتبارسنجی‌شدهٔ G28/G30 گرفته شده‌اند و عمومی یا wildcard نیستند.

ارزیاب، تغییری در Enabled، action، principal، ACL، فایل، binding، XML اضافی یا دادهٔ ناقص را قبول نمی‌کند. ۱۷ آزمون مربوط گذشت. **این نتیجه صرفاً نامزد بررسی است:** ready_for_enforcement=false، enforcement_changed=false و automatic_exemptions_added=false. Classify.py و تصمیم واقعی recovery به این ارزیاب متصل نشده‌اند.

## ثبت کامل و مرزهای اجرا
ثبت ابتدا و انتهای هر چهار Task کامل بود و query/capture error صفر بود. امضای فایل‌های چهار Task در همان VM، پیش از اعمال گیت بررسی و هش آن‌ها در دو طرف بررسی امضا ثابت بود؛ زیر گیت فراخوان جدید API امضا انجام نشد. تنظیم revocation این API جداگانه audit نشده است.

گیت در ابتدا و انتهای مشاهده معتبر بود و canary زیر آن مسدود بود. Setup نه اجرا شد و نه درخواست اجرا شد. بررسی تازهٔ فایل‌های Task پیش از گیت، به معنی اجازهٔ مقصد جدید برای نصاب نیست. شبکهٔ هدف، Job/owner guard و شمارش سخت‌گیرانهٔ allowها شل نشدند.

لاگ TaskScheduler/Operational ابتدا غیرفعال بود. فقط همین channel برای probe تشخیصی موقتاً فعال شد؛ Windows security audit policy تغییر نکرد، لاگ پاک نشد و در پایان فعال/غیرفعال‌بودن channel به مقدار قبلی بازگردانده شد. ۱۷ رخداد مربوط به چهار Task از یک خواندن محدودِ ۸۹رخدادی استخراج شد؛ سقف خواندن یا سقف خروجی پر نشد. این به معنی پوشش پیوسته یا اثبات تداوم لاگ نیست. Taskهای هدف توسط آزمایش اجرا/تغییر/غیرفعال نشدند؛ اجرای طبیعی آن‌ها توسط ویندوز در لاگ دیده شد.

خطای شمارش allow در G31 این بار تکرار نشد؛ علت آن کشف‌شده یا رفع‌شده معرفی نمی‌شود. تشخیص پالایش‌شدهٔ drift برای تکرار بعدی اضافه شده است و شرط رد همان شرط قبلی است.

## بازیابی هنوز مسدود است
چهار تغییر خام، یک reschedule شناخته‌شدهٔ قبلی و سه مانع طبقه‌بندی‌نشده باقی ماندند. Proxy بسته و تخلیه شد، ولی فایروال و IIS به دلیل `unclassified_external_component_blocks_restore` بازیابی نشدند؛ canary پس از بازیابی موجود نیست. نتیجهٔ کنترل `ambient_control_observed_restore_refused` است، نه نصب موفق، بازیابی امن کامل یا EXE آماده.

گزارش ۲۸۵۰۹بایتی، ۱۱ بخش، SHA-256:

هویت/اندازه/هش گزارش و رسید کوتاه مستقل تأیید و به هم متصل شدند. تفاوت ثبت عمومی، انتقال Enabled، رخداد 142 و دو نتیجهٔ shadow مستقلاً با مسیر دیگری کنترل شدند. هنگام ثبت وضعیت، workflow هنوز in_progress بود؛ موفقیت CI ادعا نشده است. raw log، XML، SDDL، مسیر خصوصی، PID و URL امضاشده منتشر نشده‌اند.

فیلد قدیمی سراسری image_signatures_newly_verified در گزارش خام به‌اشتباه false مانده بود، در حالی‌که چهار ردیف baseline به‌صراحت checked_before_gate، valid_microsoft و hash_stable را true ثبت کرده‌اند. گزارش خام دستکاری نشده است؛ تحلیل از همین فیلدهای هر ردیف استفاده می‌کند. برآیند کد برای گزارش‌های آینده با count و scope صریح اصلاح و با ۲۰ آزمون خلاصه‌ساز کنترل شد؛ این اصلاح بعد از اجرای Windows است و به اجرای ثبت‌شده نسبت داده نمی‌شود.

زمان poll نسبی به watch است؛ snapshotها اتمیک یا مانع کرنلی نیستند. profiler جدولی نتوانست JSON تشخیصی تودرتو را به جدول یکسان تبدیل کند؛ validator محدود، manifest، assertion و کنترل مستقل به کار رفت.

## تصمیم
دو تغییر زمان‌بندی اکنون نامزدهای مشخصِ یک قاعدهٔ محدود هستند، نه مجوزهای صادرشده. تغییر PrintJobCleanupTask در این نوبت دقیقاً غیرفعال‌سازی بود، اما DACL گستردهٔ قبلی و هویت فراخوان هنوز نیاز به تصمیم مستقل دارند. سه مانع runtime حفظ شده‌اند؛ هیچ معافیت کلی برای Taskهای ویندوز ایجاد نشده است.
