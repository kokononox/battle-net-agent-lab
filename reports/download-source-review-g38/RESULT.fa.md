# G38 — بررسی منابع واقعی دانلود

## نتیجهٔ اصلی
منشأ عمومی و فایل نسخه‌دار نصاب اولیه مشخص شد؛ اما فهرست کامل و قابل‌اجازهٔ منابعِ دانلود درون نصب، از شواهد موجود به دست نمی‌آید. هیچ resource واقعی به کاتالوگ کارگزار اضافه نشد و سیاست دو میزبان قبلی تغییر نکرد.

## نصاب اولیه: منبع مشخص، مجوز اجرایی هنوز صادر نشده
صفحهٔ رسمی `https://www.blizzard.com/en-us/apps/battle.net/desktop` هنگام بررسی به `https://download.battle.net/en-us/desktop` رفت. لینک Windows این صفحه، `https://download.battle.net/en-us/?platform=windows` بود. در HTML آن، لینک دانلود زیر مشاهده شد:

```
https://downloader.battle.net//download/getInstallerForGame?os=win&gameProgram=BATTLENET_APP&version=Live
```

بدون اجرای JavaScript و فقط با HEAD، پاسخ302 سرویس به فایل زیر ارجاع داد و پاسخ فایل200 بود:

```
https://downloader.battle.net/download/installer/win/1.0.68/Battle.net-Setup.exe
```

هدر Content-Length برابر4700880 بود. فایل در این بررسی دریافت یا اجرا نشد؛ SHA-256 جدید و امضای Authenticode آن مجدداً بررسی نشده‌اند. ETag را hash امنیتی یا امضای فایل تلقی نمی‌کنیم. برابری اندازه با فایل تاریخی به معنی برابری محتوا نیست.

مسیر قدیمی `getInstaller?os=win&installer=Battle.net-Setup.exe` در Prepare آزمایش قبلی استفاده شده بود؛ مسیر فعلیِ معرفی‌شده در صفحهٔ رسمی با آن یکسان نیست. فایل تاریخی در VM قبلی اندازه، SHA-256 و امضای پذیرفته‌شده داشت، اما آن شواهد را به فایل دریافت‌نشدهٔ فعلی تعمیم نمی‌دهیم.

`downloader.battle.net` خارج از دو میزبانِ gate قبلی است. این کشف به معنی افزودن میزبان جدید نیست؛ نصاب اولیه تا اینجا در مرحلهٔ قبل از ایزوله‌سازی تهیه می‌شده است. دانلود دستی شما و بررسی فایل محلی می‌تواند این مرحله را جدا نگه دارد. اصالت منشأ نصاب هم رفتار حریم خصوصیِ اجرای بعدی آن را ثابت نمی‌کند.

## دانلودهای داخل نصب: شکاف‌های مشخص
شواهد نصب G26 با گزارش ثبت‌شده در commit494752c2d647f5c83ac87b502b1e1c535cc7d468 تطبیق داده شد. تحلیل بر request_metadata پالایش‌شده است، نه trace کامل شبکه.

| دسته | آنچه واقعاً داریم | چرا هنوز مجاز نمی‌شود |
| --- | --- | --- |
| level3.blizzard.com | درخواست‌های HTTP روی پورت80؛ در نمونهٔ ثبت‌شده GET با body خالی و query غایب | path فقط SHA-256 دارد؛ هدرهای خروجی ثبت نشده‌اند؛ hash محتوای فایل‌ها و فهرست کامل نداریم |
| us.version.battle.net | TLS روی443 با SNI مقصد | method/path/header/body رمزگشایی نشده؛ ضرورت و محتوای ارسال نامعلوم‌اند |
| /agent/versions روی1119 | مسیر probe منفی در Driver برای اثبات رد پردازش خارج Job | trace درخواست خود نصاب نیست و نباید به‌عنوان مسیر کشف‌شده وارد فهرست فایل‌ها شود |

گزارش، metadata را به256ردیف محدود کرده و شمار رخدادهای مرتبط از این حد بیشتر است. در نمونه128ردیف درخواست HTTP با123هش متمایز path دیده می‌شود؛ این اعداد فهرست کامل فایل‌ها نیستند. هش مسیر قابل تبدیل مطمئن به URL نیست. تکرار ردیف پالایش‌شده حذف نشد چون ممکن است رخدادهای جداگانه باشند. nullهای schemaهای HTTP/TLS ساختاری‌اند و صفر فرض نشدند.

وجود body خالی و query غایب در نمونه، نبود شناسه در path یا header را ثابت نمی‌کند. response_bytes در کد شامل status/header و کل پاسخ HTTP است، نه اندازهٔ خالص فایل؛ نمی‌توان آن را برای expected_bytes کاتالوگ کپی کرد.

## ناسازگاری‌هایی که آزمون آفلاین قبلی پوشش نمی‌داد
- نمونهٔ G37 فقط plan با HTTPS/443 می‌سازد؛ مسیر payloadِ مشاهده‌شده در G26 روی HTTP/80 بود. پشتیبانی همان منابع از HTTPS هنوز تأیید نشده است؛ تبدیل خودکار scheme مجاز نیست.
- پاسخ206 در نمونهٔ نصب وجود دارد؛ G37 فقط پاسخ200 کامل را می‌پذیرد و Range/resume ندارد. این مشاهده به‌تنهایی شکل درخواست Range را ثابت نمی‌کند چون هدر درخواست ثبت نشده است.
- bootstrap فقط فایل آغازگر است و جایگزین فهرست payloadها، manifestها و وابستگی‌های داخل نصب نیست.

پس50آزمون موفق G37، سازگاری با دانلود واقعی Battle.net را ثابت نمی‌کنند. بدنهٔ fixture و سیاست ثابت آزمایشگاهی با شبکهٔ واقعی تفاوت دارند.

## تصمیم
- تأییدِ منشأ صفحه و مسیر نسخه‌دار bootstrap: شواهد موجود است.
- تأییدِ hash/امضای تازهٔ فایل و فهرست کامل payloadهای نصب: انجام نشده است.
- مجوز جدید شبکه، endpoint یا فایل برای کارگزار: صفر.
- نصب، CA جدید، TLS bypass، تغییر فایروال یا Windows task: انجام نشده است.

## قدم بعدیِ محدود و قابل دفاع
1. فایل نصابِ تهیه‌شده از منبع رسمی در مرحلهٔ قبل از gate، محلی hash و روی Windows با Authenticode بررسی شود؛ تغییر hash بدون بررسی دوباره مجاز نشود.
2. پیش از اجرای نصب تازه، طرح جمع‌آوری شواهد اصلاح شود: برای HTTP قابل مشاهده، نام/path/header باید در محل خصوصی، محدود و بدون انتشار مقادیر شناسایی‌کننده قابل بررسی باشند؛ hash-only برای ساخت manifest کافی نیست. مسیرها، اصالت payload و اندازهٔ خالص آن‌ها باید مستقل بررسی شوند. دیدن اطلاعات پس از ارسال، تضمین پیشگیری از ارسال نیست.
3. درخواست ناشناختهٔ HTTPS به‌خاطر معتبر بودن دامنه مجاز تلقی نشود. اگر بدون آن دانلود پیش نرفت، این وابستگی گزارش شود و بین منبع عمومیِ manifest، روش cache یا تغییر معماری با تصمیم آگاهانه انتخاب شود؛ نه عبور کور TLS.
4. کشف جدید، فاز پژوهشیِ جدا از کارگزار تأییدشده است. هیچ trace یا GET مشاهده‌شده خودکار به کاتالوگ approved تبدیل نشود. تست نصب در این مرحله اجرا نشده است.
