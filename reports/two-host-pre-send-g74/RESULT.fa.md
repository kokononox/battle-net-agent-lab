# G74 — نمونهٔ عملی کنترل پیش از ارسال، بدون اجرای Battle.net

## خروجی این مرحله
کد اولیهٔ تصمیم‌گیری و بازسازی درخواست اضافه شد؛ برخلاف hookهای مشاهده‌گر قبلی، این نمونه در harness محلی **قبل از هر اتصال upstream** تصمیم می‌گیرد. پیش‌فرض رد است. تابع `feed` فقط قطعات را با سقف حافظه نگه می‌دارد؛ تنها `finish` می‌تواند یک درخواست کامل را بپذیرد. هیچ ورودی خامی مستقیماً forward نمی‌شود.

در ۱۷ کنترل فیزیکی محلی، ۳ مورد مجاز دقیقاً درخواست canonical را به گیرنده رساندند؛ ۱۴ مورد ردشده، صفر اتصال و صفر بایت به آن گیرنده داشتند. گیرنده واقعاً روی socket loopback بود، نه صرفاً mock یک تابع. همهٔ این موارد و آزمون‌های محلی گذشتند. این **کنترل خروجی همان harness** است، نه اثبات جلوگیری از خروج همهٔ ترافیک سیستم یا نصب‌کننده.

## سیاست پیاده‌شده
- فقط GET کامل HTTP/1.1، با Host دقیق یکی از دو میزبان انتخاب‌شده، پذیرفته می‌شود. body، query، fragment، مسیر نامنطبق، TLS opaque و پیام ناقص/چندتایی رد می‌شوند.
- مسیر CDN باید دقیقاً در catalog مستقل پین‌شده یا مرجع پین‌شدهٔ config عمومی G72 باشد. Range فقط با مرز دقیق ساختاری قدیمی یا مقایسهٔ کامل شیء عمومی DL/EN مرحلهٔ G73 پذیرفته می‌شود؛ داخل محدوده بودن کافی نیست.
- metadata فقط **۱۱ مسیر دقیق v2** موجود در دریافت‌های مستقل را می‌پذیرد. short alias، seqn و Range metadata فعلاً پشتیبانی نمی‌شوند. نام محصول عمومی به‌تنهایی allow rule ایجاد نمی‌کند.
- سقف یک درخواست 16KiB و حداکثر ۳۲ header است. duplicate header، obs-fold، bare newline، tab، بایت غیر ASCII، Transfer-Encoding، credential، header ناشناخته و Content-Length غیر از صفر رد می‌شود؛ صفر بودن Content-Length هم body واقعی را مجاز نمی‌کند.
- User-Agent ورودی فقط literal ثابت bootstrap با منشأ مستقل G67 را می‌پذیرد؛ سایر UAها فعلاً رد می‌شوند. حتی همان UA هم به upstream کپی نمی‌شود. این محدودیت برای سازگاری بی‌دلیل باز نشده و احتمال ردشدن درخواست‌های سالم واقعی وجود دارد.
- درخواست خروجی از نو ساخته می‌شود: GET، Host منتخب، `Accept: */*` و `Connection: close` ثابت‌اند. فقط مسیر عمومی دقیق و Range معتبر canonical می‌تواند متغیر باشد؛ whitespace، casing، UA، framing و header ورودی کپی نمی‌شود. صفرهای ابتدایی Range نیز canonical می‌شوند.
- reason codeها ثابت‌اند؛ مقدار خصوصی یا متن exception در audit نیست. wire داخلی در گزارش ذخیره نمی‌شود. referenceها کپی دفاعی دارند و تغییر pin با بازپذیری خودکار پاسخ داده نمی‌شود.

این سیاست تصمیم‌گیری است، نه تشخیص قطعی تمام fingerprintها. مجموعهٔ درخواست‌های عمومی هنوز می‌تواند از راه انتخاب، تعداد، ترتیب و timing اطلاعات حمل کند.

## شواهد محلی
۳۰ تست جدید، مجموع discovery را به ۱۷۱ تست رساند؛ یک تست محلی مخصوص ویندوز skip شد. مجموعهٔ کامل و کنترل گیرندهٔ محلی روی ترکیب واقعی Git blobهای پین‌شده اجرا شدند، نه نسخهٔ متفاوت working tree.

تست‌ها از جمله هر محل شکستن درخواست به دو قطعه، قطعه‌های تک‌بایتی، افزودن payload خصوصی بعد از header، query، credential، UA خصوصی، Range نزدیک‌مرز نادرست، duplicate Host، ambiguity framing، pin ناسازگار، خطای داخلی و استفادهٔ مجدد از gate را پوشش می‌دهند. متن sentinel مصنوعی و raw request در خروجی شواهد نوشته نشده است.

سه کنترل مثبت: CDN ساده، CDN با Range کامل و قطعه‌بندی تک‌بایتی، و یک route metadata عمومی. چهارده کنترل منفی شامل identifier در query/UA/cookie/authorization/body/header، Range یک‌بایت کوتاه، مقصد ناشناخته، tail پایپ‌لاین، body دیررس، header ناقص، TLS opaque، Host تکراری و Transfer-Encoding بود. برای همهٔ موارد منفی، مسیر relay پیش از ایجاد socket بازگشت؛ count اتصال صفر بود و sink هیچ receipt نداشت.

17 ردیف، case key یکتا و بدون duplicate دارند. nullهای receipt مثبت در موارد منفی و nullهای denied در موارد مثبت، مطابق نوع کنترل‌اند و missing evidence محسوب نمی‌شوند. این داده‌ها ساختگی‌اند و به تعداد درخواست واقعی Battle.net تعبیر نمی‌شوند.

## چه چیزی هنوز انجام نشده است
**این نمونه به نصب‌کننده وصل نیست و پراکسی شفاف یا حفاظت آمادهٔ استفاده نیست.** قرارداد یک پیام کامل plaintext، مسئولیت adapter مورد اعتماد است؛ EOF/finish در harness راه‌حل عمومیِ تشخیص پایان درخواست client نیست. relay آزمایشی همیشه به literal `127.0.0.1` متصل می‌شود و Host ورودی را برای اتصال مصرف نمی‌کند. ارسال HTTPS به میزبان واقعی، مدیریت پاسخ، endpoint/port/TLS binding یا certificate validation واقعی در این نمونه پیاده نشده است.

پیش از integration باید assembly درخواست در API واقعی، completion و timeout، partial write و async I/O، پیوند تصمیم به دقیقاً همان bytes ارسال‌شده و جلوگیری از bypass فرایندها/APIهای دیگر آزموده شوند. قلاب‌های قدیمی observation-only همچنان فقط مشاهده‌گرند و با اضافه‌شدن این فایل به فیلتر تبدیل نشده‌اند. شکاف‌های پوشش قبلی یا عدم نگاشت کامل ciphertext/plaintext حل‌شده فرض نمی‌شوند.

## حفظ هدف و محدوده
هدف همچنان دانلود مجاز Battle.net بدون ارسال fingerprint است. این مرحله برای نخستین اتصال کنترل‌شدهٔ تصمیم به ارسال پایهٔ اجرایی می‌سازد؛ عمومی بودن path یا GET بودن را معادل بی‌خطر بودن کل ترافیک نمی‌گیرد.

هیچ اجرای target یا درخواست تازه به Battle.net، هیچ دانلود کامل، login، Install click، مقصد runtime تازه یا تغییر allowlist انجام نشد. main و Unified Firewall Desktop 0.9.10 دست‌نخورده‌اند؛ استثنای قبلی مدیریت CI تغییری نکرده است. ترافیک زیرساخت checkout/upload خود CI، ترافیک نصب‌کننده نیست.

گام بعدیِ محدود، اتصال همین تصمیم به **یک مسیر واقعی ارسالِ مشخص** و اثبات عدم ارسال زودهنگام یا دورزدن آن در کنترل‌های مثبت/منفی است؛ نه فعال‌کردن دانلود کامل یا معرفی این prototype به‌عنوان ابزار نهایی.

## بازتولید
source مرحله در `analysis-tools/two-host-pre-send-g74` و workflow در `.github/workflows/battlenet-pre-send-g74.yml` است. `compose.py` پایه‌های G69 تا G73 را از Git blob با pin ترکیب می‌کند. سپس unittestها و `pre_send_fixture.py` اجرا می‌شوند. جزئیات contract در README آمده است.
