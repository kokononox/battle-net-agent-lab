# G67 — منشأ عمومی seqn و User-Agent مبهم تأیید شد

## پاسخ محدود به سؤال حریم خصوصی
در اجرای کامل این مرحله، دو مقدار مبهم مشخص منشأ مستقل عمومی/ثابت داشتند:
1. query با کلید seqn در مسیر summary دقیقاً با شمارهٔ توالی کلی سند summary که قبل از اجرای installer از درخواست عمومی ثابت دریافت شده بود تطابق داشت. این مشاهده با پیگیری تغییرات نسخه/کش سازگار است، نه با شناسهٔ اختصاصی دستگاه در همین مقدار.
2. User-Agent مبهم دقیقاً و به‌صورت case-sensitive و whole-value با phoenix-agent/1.0، رشتهٔ ثابت همان نصاب رسمی، برابر بود. هیچ suffix یا شناسهٔ متغیر اضافه در همین مقدار وجود نداشت.
این نتیجه دربارهٔ همین مقادیر مشاهده‌شده است؛ نبود همهٔ اشکال fingerprint، کل ترافیک یا کل دانلود را اثبات نمی‌کند. هیچ allow rule جدیدی از آن ساخته نشده است.

## اصلاح برداشت G65/G66
parser قدیمی فقط صفر یا یک # را در خط seqn می‌پذیرفت، اما پاسخ واقعی از ## seqn = استفاده می‌کند. نمونه‌های عمومی summary، agent versions و bna versions، همگی این خطای false-negative را بازتولید کردند: parser قدیمی marker را نمی‌گرفت و parser اصلاح‌شده آن را می‌گیرد. بنابراین «عدم تطابق با فهرست استخراج‌شدهٔ قبلی» دلیل کافی برای کنارگذاشتن فرضیهٔ شمارهٔ توالی نبود.

G67 شمارهٔ کلی سند summary را جدا از شمارهٔ ردیف محصول ذخیره می‌کند. در اجرای اصلی، matches_prepared_public_summary_document_sequence_exact=true و همچنین طبقهٔ مستقل query در request_value_audit برابر fixed_public_sequence_exact شد. مقدار خام query منتشر نشده است.

تطابق با seqn جدول کامل 200 روی همان TLS context=false باقی ماند. این موضوع مخفی نشده است: شاهد مثبت این مرحله، سند عمومی مستقلِ دریافت‌شده قبل از installer است؛ نه ادعای تطابق با پاسخ همان اتصال، نه pairing یک‌به‌یک درخواست و پاسخ. منابع جامعهٔ توسعه‌دهندگان نیز هشدار می‌دهند seqn ردیف summary و endpoint الزاماً با هم برابر نیستند.

## منشأ مستقل User-Agent
نصاب رسمی بدون اجرا در محیط تحلیل دریافت شد:
https://downloader.battle.net/download/installer/win/1.0.68/Battle.net-Setup.exe
طول: 4700880 بایت
SHA256: f4643a2086c0cecb1ab68cc601bf38c1a0a6f7ef5914ad03375cc9449385bec6
این همان hash پین‌شدهٔ نصاب آزمایش است. رشتهٔ ASCII ثابت phoenix-agent/1.0 در offset ده‌دهی 3580116 یافت شد. ابتدا فقط سازگاری ساختاری با هدر مشاهده‌شده مطرح بود؛ اجرای G67 equality کامل آن را تأیید کرد. متن خام هدر واقعی صادر نشده؛ ثابت مستقل موجود در باینری عمومی، مرجع مقایسه است.

الگوی User-Agent دیگر همچنان فقط agent، / و نسخه‌ای منطبق با مرجع عمومی داشت. false باقی‌ماندن regex محدود قدیمی به معنی وجود متن اضافه در این الگو نیست؛ نتیجهٔ ساختار پالایش‌شده ملاک این گزاره است.

## اجرای نخست و تنها تکرار
اجرای نخست https://github.com/kokononox/battle-net-agent-lab/actions/runs/40284772754 با source 5dd22cdc744d47672a1e3daec5246eb325727dd0، equality User-Agent ثابت را ثبت کرد؛ اما پیش از ثبت query با late_process_image_failed متوقف شد. cleanup=true بود. از آن اجرا نتیجه‌ای برای query گرفته نشد؛ runtime اولیه در initial-runtime.json حفظ شده است.

فقط یک تکرار روی runner تازه انجام شد. تنها README برای فعال‌شدن push تازه تغییر کرد؛ کد مشاهده‌گر، شرط‌های شناسایی پردازش، فایروال، اعتبارسنجی و زمان‌بندی ضعیف نشدند. تکرار با error=null، cleanup=true و مشاهدهٔ 120.2 ثانیه پایان یافت.

## کنترل‌ها و آنچه باقی است
58 تست واحد محلی و مرحلهٔ parse/test ویندوز گذشتند؛ ده کنترل بومی x86/x64 موفق بودند. کش گواهی آنلاین و آفلاین معتبر، firewall_verified=true و cleanup=true بود. بررسی ابطال خاموش نشد. main و 0.9.10 دست‌نخورده‌اند و مقصد runtime تازه‌ای باز نشد.

46 ردیف، رخداد بازسازی‌شدهٔ API هستند؛ 29 تکرار در خلاصهٔ پالایش‌شده حذف نشده‌اند و اینها شمار درخواست یکتای رسیده به سرور نیستند. 5116 بایت در non_HTTP1_or_midstream باقی مانده است. سقف audit پر نشد، اما coverage_complete=false و fingerprinting_absence_proven=false باقی‌اند.

مسیرهای CDN با بخش‌های هنوز طبقه‌بندی‌نشده باید با manifest/config و فایل‌های عمومی دانلود تطبیق داده شوند. سپس پوشش همهٔ مسیرهای فعال ارسال و کل بازهٔ دانلود باید سنجیده شود. این دو مسئله، نه تکرار آزمون نصب یا TLS، مانع بعدی حکم کلی «فقط دانلود» هستند.
