# G73 — تأیید دقیق Range کل شیء عمومی

## نتیجه
در مشاهدهٔ تازه، Range مربوط به همان کلاس باقی‌مانده دقیقاً **کل شیء عمومی کدشده** بود: شروع صفر، پایان برابر اندازهٔ عمومی منهای یک، و طول برابر اندازهٔ کامل. اندازه برای همان محصول در دو قالب metadata عمومی **Download Manifest (DL)** و **Encoding EKey (EN)** یکسان بود. کل مسیر نیز دقیقاً در مرجع مستقل پین‌شده قرار داشت. مقایسه در RAM انجام شد و Range یا مسیر خام صادر نشد.

از ۱۳ observation API دارای Range، ۱۲ مورد با قواعد ساختاری قبلی و یک مورد با مقایسهٔ دقیق کل شیء عمومی تأیید شدند؛ در این دامنهٔ مشاهده Range نامنطبق باقی نماند. این تعداد، شمار درخواست یکتای شبکه نیست و هیچ‌یک از این نتایج مجوز تازه یا تأیید نبود fingerprint نیست.

## تغییر کوچک و fail-closed
- فقط وقتی مرجع ساختاری قبلی وجود ندارد، تطابق کل شیء بررسی می‌شود. مرزهای BLTE و رکوردهای archive قبلی اولویت دارند و دست‌نخورده‌اند.
- DL و EN باید برای یک محصول مشترک وجود داشته باشند؛ اندازه‌ها باید integer واقعی مثبت، حداکثر 2^63−1 و بدون تناقض باشند. bool، float، string، اندازهٔ ناقص یا اختلاف اندازه رد می‌شود.
- فقط یک header با شکل بستهٔ `bytes=عدد-عدد` پذیرفته می‌شود. prefix ناقص، شروع غیرصفر، overrun، چند header، suffix/open range یا بازهٔ معکوس مثبت نمی‌شود. داخل محدوده بودن به‌تنهایی کافی نیست.
- برای تشخیص Range، مسیر کامل اصلی ارسال می‌شود، نه مسیر پس از حذف query؛ بنابراین افزودن query نمی‌تواند با استفاده از مسیر پاک‌شده تطابق ساختاری مثبت بگیرد. spelling و fanout متفاوت هم تطبیق ندارند.
- مرجع عمومی G69 و مرجع schema/bts مرحلهٔ G72 عوض نشدند. هیچ URL مشاهده‌شدهٔ target برای دریافت پژوهشی بازتاب داده نشد؛ برای حل Range هیچ دریافت خارجی تازه یا دانلود فایل اجرایی انجام نشد.

## اعتبارسنجی
۱۴۱ تست در ویندوز گذشت. اجرای محلی همان ۱۴۱ تست، یک skip مختص ویندوز داشت. آزمون‌های تازه مرز صحیح و نزدیک‌مرز نادرست، انواع اندازهٔ نامعتبر، اختلاف محصول، فقدان یکی از دو قالب، query و اولویت قواعد ساختاری را پوشش می‌دهند.

علاوه بر fixture مصنوعی، metadata واقعی پین‌شده دوباره decode شد: EKey/BLTE، اندازه‌های encoded/decoded و CKey/MD5 برای DL و EN بررسی شدند؛ parser خود EN نیز کنترل‌های موجود ساختارش را اجرا می‌کند. اندازه‌های ۹۹۳ مسیر مشترک DL/EN با bytes همان منابع بازسازی و با catalog مقایسه شدند. این‌ها دو قالب metadata مستقل از ورودی نصب‌کننده‌اند، نه دو نهاد قابل اعتماد مستقل یا امضای ناشر.

هر ۱۲ کنترل بومی موجود x86/x64 قبل از target گذشتند. برای این تغییر، fixture بومی تازهٔ Range اضافه نشد؛ کد معنایی همان کد آزموده‌شدهٔ Python است. کنترل‌های transport/TLS/اعتماد گواهی حذف یا ضعیف نشدند.

## اجرای محدود
[اجرای 40303775767](https://github.com/kokononox/battle-net-agent-lab/actions/runs/40303775767)، source `9ecfa937b6641cac904e3ec80caed3a5e6a10950`، فقط یک مشاهدهٔ واقعی 120.5 ثانیه‌ای داشت. error تهی، firewall verify و cleanup موفق بود؛ cache گواهی آنلاین و آفلاین موفق بود. همان یک Continue زبان مجاز بود؛ Install click، login یا دانلود کامل انجام نشد.

## ارتباط با هدف اصلی و محدودیت‌ها
هدف همان دانلود مجاز Battle.net بدون ارسال fingerprint است. این مرحله فقط ابهام Range را برداشت؛ محصول نهایی آماده اعلام نمی‌شود. مقصدهای runtime همچنان `us.version.battle.net` و `level3.blizzard.com` هستند و استثنای قبلی مدیریت CI تغییر نکرده است. هیچ allow rule تازه اضافه نشد؛ main و Unified Firewall Desktop 0.9.10 تغییر نکردند.

پوشش هنوز کامل نیست: ۴۸ ReadFile دارای overlapped I/O در ردیاب منشأ gap دارند؛ همهٔ APIها، فرایندها و مسیر دانلود کامل پوشش داده نشده‌اند. ۹۴۷۰ بایت outgoing API از نظر framing حساب شد، اما TLS record به معنای تأیید plaintext یا نگاشت یک‌به‌یک SSPI نیست. timing، selection و شناسه‌های کدشدهٔ ناشناخته نیز با عمومی بودن مسیر/اندازه منتفی نمی‌شوند.

نتیجه مربوط به **مشاهدهٔ جدید G73** است. چون Range خام تاریخی نگهداری نشده، برابری عددی Range این اجرا با نمونه‌های قدیمی G69–G72 قابل اثبات نیست؛ تاریخچه با حدس بازنویسی نشده است.

## شواهد و ادامهٔ محدود
