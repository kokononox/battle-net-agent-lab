# G70 — کلید نامنطبق پیش از ارسال در ورودی سرور نسخه دیده شد

## نتیجهٔ مرتبط با هدف اصلی
عین leaf key مسیر CDN که در مرجع مستقل G69 نبود، پیش از observation ارسال آن درخواست، در plaintext ورودیِ منتسب به `us.version.battle.net` پس از DecryptMessage موفق پیدا شد. تطبیق ASCII lower-hex بود. این یک شاهد تازه از وقوع قبلیِ کلید در ورودی شبکه است؛ **وابستگی علّی، عمومی بودن پاسخ یا نبود fingerprint از آن ثابت نمی‌شود**. مجوز تازه‌ای برای مسیر ناشناخته ساخته نشد.

یک observation از مسیر نامنطبق ثبت شد. سه source event ورودی نسخه با همان کلید تطبیق داشتند؛ چون overlap و segmentation وجود دارد، این عدد سه پاسخ مستقل یا سه منبع مستقل نیست. یک occurrence دیگر پس از درخواست در recv پورت 80 ثبت شد که شاهد منشأ پیش از درخواست محسوب نمی‌شود. در bufferهای ReadFile همگامِ ثبت‌شده occurrence پیدا نشد؛ منفی بودن این جست‌وجوی محدود، منشأ محلی را رد نمی‌کند.

پشتهٔ ارسال، offsetهای نسبی داخل Agent را نشان می‌دهد، از جمله `Agent+0x35d89a` و `Agent+0x3414da`. این‌ها محل مشاهدهٔ ارسال‌اند، نه لزوماً محل تولید یا استخراج کلید؛ یک frame نامشخص هم وجود داشت. هیچ symbol/function name حدس زده نشده است.

## چه چیزی تغییر نکرد
- 34 observation API مربوط به CDN؛ 33 مسیر کامل با مرجع عمومی مستقل تطبیق دقیق داشتند و یک مسیر همچنان نامنطبق است. تعدادها unique server requests نیستند.
- 12 از 13 Range همچنان مرز دقیق عمومی دارند؛ یک Range حل‌نشده و مسیرِ بدون Range نامنطبق، دو درخواست متفاوت‌اند.
- مرجع عمومی همان snapshot پین‌شدهٔ G69 است؛ دریافت تازه برای گسترش catalog انجام نشد. کلید نامنطبق نه در آن catalog عمومی و نه در tokenهای مرجع ثابت پیش از اجرای همین مرحله تأیید نشده است.
- Runtime همان `us.version.battle.net` و `level3.blizzard.com` با استثنای قبلی مدیریت CI است؛ مقصد تازه، ورود حساب، کلیک Install یا اجرای دانلود کامل وجود نداشت. main و Unified Firewall Desktop 0.9.10 تغییر نکردند.

## صحت اجرا و محدودیت پوشش
- اجرای موفق: [40293205084](https://github.com/kokononox/battle-net-agent-lab/actions/runs/40293205084)، source commit `11e25be92e33c76a23a6469cbbacbee33fb8d117`؛ مشاهده 120.6 ثانیه، error تهی، firewall verified و cleanup موفق.
- 90 تست در Windows گذشتند؛ در Linux همان مجموعه با یک skip مختص Windows اجرا شد. هر 12 کنترل بومی x86/x64 گذشتند، شامل دو کنترل تازهٔ اتصال کلید synthetic به ReadFile، recv و WSARecv. دادهٔ fixture با دادهٔ واقعی ترکیب نشد.
- بررسی cache گواهی آنلاین و آفلاین موفق بود؛ revocation یا اعتبارسنجی TLS ضعیف نشد.
- بایت‌های ورودی مشاهده‌شده: ReadFile همگام 3,173,586؛ plaintext سرور نسخه 45,369؛ recv انتخاب‌شده روی پورت 80 برابر 7,736,227. این‌ها byte observations هستند، نه اندازهٔ محتوای یکتای دانلود.
- retention برابر 32MiB بود؛ هیچ chunk به‌علت FIFO eviction حذف نشد و سقف source bytes پر نشد. شمار 48 ReadFile دارای overlapped I/O به‌عنوان gap ثبت شد. mmap، I/O pending، خروجی decompression و همهٔ فرایندها/APIها پوشش کامل ندارند.
- 9,470 بایت outgoing API انتخاب‌شده به 4,378 بایت HTTP candidate و 5,092 بایت record کامل TLS حساب‌پذیر بود؛ reconciliation برقرار، opaque/buffer صفر و cap فعال نشد. framing TLS معادل تأیید محتوای plaintext یا پوشش کل سیستم نیست.
- بایت خام ورودی، کلید، نام فایل، مسیر، query یا Range مشاهده‌شده در artifact/log ذخیره نشد. equality در RAM انجام شد؛ فقط دستهٔ منبع، ترتیب observation و offset نسبی ماژول صادر شد. بنابراین انتساب دقیق فیلد پاسخ را نمی‌توان پس از پایان runner از این خروجی بازیابی کرد.

## توقف آماده‌سازی پیش از اجرای واقعی
اجرای اولیه [40292278079](https://github.com/kokononox/battle-net-agent-lab/actions/runs/40292278079) در compose و قبل از اجرای نصب‌کننده/کنترل بومی/firewall متوقف شد. تمام blob SHAهای فایل پایهٔ محلی با commit ثبت‌شدهٔ G69 مطابقت داشتند؛ pin روی bytes فایل working tree ویندوز شکست. تبدیل پایان‌خط علت محتمل بود؛ نوع دقیق تفاوت بایت در log اولیه ثبت نشده است. اصلاح فقط خواندن bytes از `git show HEAD:path` به‌جای working tree بود؛ همان SHA256های ثابت حفظ شدند و سپس compose و تمام تست‌ها موفق شدند. هیچ کنترل امنیتی برای عبور از خطا حذف نشد. تنها اجرای target همین اجرای موفق بالا بود؛ اجرای تازهٔ دیگری خودکار آغاز نشده است.

## قدم بعدیِ محدود
انتساب همان کلید در RAM به **پاسخ HTTP مشخص و سند/ستون مشخصِ سرور نسخه**، سپس مقایسهٔ همان سند با دریافت عمومی مستقل و تطبیق کل مسیر CDN. این کار باید دریافت از سرور را از عمومی بودن سند و نیز وقوع قبلی را از وابستگی علّی جدا نگه دارد. صرف تکرار جست‌وجوی catalog قبلی، GET بودن، بدنهٔ خالی، شکل هش یا allowlist دو دامنه برای تأیید حریم خصوصی کافی نیست.

پس از حل این ابهام‌ها نیز پوشش پیوستهٔ دانلود کامل هنوز لازم است؛ G70 تضمین عدم ارسال fingerprint برای دانلود کامل نیست.

- `analyze.py`: کنترل هویت run/source، شمارش مستقل occurrence، تطبیق accounting و تولید manifest.
- SHA256 artifact دانلودشده، با digest صفحهٔ GitHub مقایسه شد: `c0004c5c26504e4c983d1492847ac82d4991f5fcd3eceb986ca70362b17d8a21`.
- profiler فایل runtime را به‌علت آرایه‌های ناهم‌اندازه مستقیماً نپذیرفت؛ آرایهٔ request_value_audit.rows جدا و profile شد: 46 observation و 17 ردیف تکراریِ پالایش‌شده، همگی حفظ شدند. ثابت بودن method/body و ستون‌های تشخیصی، دلیل نبود fingerprint نیست. public_download_path برای 12 ردیف سرور نسخه عمداً null است. nullهای failure_stage/error_type در کنترل، نشان‌دهندهٔ موفقیت‌اند؛ run_id شناسه است، نه کمیت تحلیلی.
