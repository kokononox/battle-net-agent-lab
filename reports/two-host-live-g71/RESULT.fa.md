# G71 — جفت‌سازی پاسخ‌ها انجام شد؛ فیلد کلید و عمومی‌بودن آن هنوز تأیید نشد

## نتیجهٔ اصلی، بدون ارتقای بی‌دلیل unknown به مجاز
کلید نامنطبقِ CDN اکنون به بدنهٔ پاسخ‌های HTTP کاملِ دریافتی از سرور نسخه منتسب است، نه فقط به یک تکه plaintext. در مشاهدهٔ نهایی، 15 درخواست GET و 15 پاسخ کامل روی TLS context متناظر با FIFO جفت شدند؛ هیچ context ردشده، بایت parser باقی‌مانده یا درخواست بی‌پاسخ در این دامنه نبود. همان کلید پیش از observation ارسال target در بدنهٔ سه پاسخ 200 دیده شد؛ نه در header. این اعداد، شمار observationهای این اجرا هستند؛ سه منبع مستقل یا اثبات وابستگی علّی نیستند.

**فیلد دقیق شناسایی نشد.** route پاسخ خارج از vocabulary ثابت باقی ماند و به‌صورت `<other_route>` گزارش شد؛ نام یا URL واقعی از آن قابل بازیابی نیست. خط‌های حامل کلید، کاراکتر `|` دارند، اما parser نتوانست آن‌ها را به ستون یک schema معتبر وصل کند. پس «جدول نسخهٔ استاندارد»، «BuildConfig»، «هش پیش‌نیاز» یا هر فیلد مشخص دیگری ادعا نمی‌شود.

**تطبیق عمومی مستقل هم مثبت نشد.** نه اسناد مستقلِ زندهٔ قبل از اجرا و نه دو ProductConfig عمومی پین‌شده، occurrence مستقلی از این کلید تأیید نکردند. هیچ برابری کامل با بدنه/زیرسند ProductConfig عمومی پیدا نشد. عمومی نبودنِ قطعی از این منفی نتیجه نمی‌شود؛ فقط تأیید عمومی نداریم. whole CDN path، منشأ عمومی و وابستگی علّی همگی false/تأییدنشده باقی ماندند. مجوز تازه‌ای ساخته نشد.

2. بررسی آفلاین agent-product عمومی نشان داد که بعضی داده‌های installer در رشتهٔ JSON جاسازی شده‌اند. این صرفاً یک قالبِ پوشش‌داده‌نشده بود، نه کشف منشأ کلید. پشتیبانی محدود از embedded JSON، MIME، جدول دارای preamble، BLTE chunkless N و برابری کامل با دو ProductConfig مستقل اضافه شد و فقط یک مشاهدهٔ تکمیلی انجام شد.
3. [40297279657](https://github.com/kokononox/battle-net-agent-lab/actions/runs/40297279657)، source `8f493c8cbd86e20d3d08c38cd4c5de81984c9b51`: موفق، 120.9 ثانیه، 15 پاسخ جفت‌شده، سه occurrence بدنهٔ پیشین؛ field و public origin همچنان نامشخص. نتیجهٔ جدید، فرض JSON/ProductConfig را تأیید نکرد. اجرای دیگری خودکار آغاز نشده است.

## وضعیت درخواست‌های CDN در مشاهدهٔ نهایی
- 41 observation API مربوط به CDN؛ 39 مسیر کامل با catalog عمومی مستقل مطابقت دقیق داشتند و دو observation نامنطبق باقی ماندند.
- آن دو observation یک leaf key مشترک داشتند؛ از این گزارش تعداد URL یا درخواست شبکهٔ یکتا نتیجه‌گیری نمی‌شود.
- 15 از 16 Range مرز عمومی دقیق داشتند؛ یک Range نامشخص باقی ماند. این با مسئلهٔ کلید مسیر نامنطبق یکی نیست.
- همهٔ GET/body-empty/domain-allowlist و نبود match با شناسه‌های محلی، به‌تنهایی اثبات نبود fingerprint نیستند.

## کنترل صحت و دامنهٔ اجرا
- 119 تست در Windows گذشتند؛ همان مجموعه در Linux یک skip مختص Windows داشت. هر 12 کنترل بومی x86/x64 موفق بود؛ دو کنترل TLS واقعی، انتساب کلید synthetic به ETag و ستون BuildConfig پاسخ درست را از طریق همان SSPI hook/FIFO pairer تأیید کردند. این‌ها fixture هستند، نه شاهد شناسایی فیلد واقعی.
- firewall verify، certificate-cache آنلاین و آفلاین و cleanup موفق بودند؛ error نهایی تهی است. محدودیت TLS/revocation، تشخیص process، UI و شبکه عوض نشد.
- Runtime همان `us.version.battle.net` و `level3.blizzard.com` و استثنای قبلی مدیریت CI را دارد. مقصد تازه، login یا Install click وجود نداشت. main و Unified Firewall Desktop 0.9.10 تغییر نکردند.
- 50 ReadFile دارای overlapped I/O در ردیاب منشأ قبلی به‌عنوان gap باقی ماندند؛ سقف source bytes پر نشد و eviction ثبت نشد. تکمیل parser روی 15 پاسخ، پوشش همهٔ APIها/فرایندها، دانلود کامل یا همهٔ محتوای شبکه نیست.
- outgoing API منتخب 12,372 بایت بود: 5,326 بایت HTTP candidate و 7,046 بایت record کامل TLS. accounting برقرار بود؛ cap یا بایت طبقه‌بندی‌نشدهٔ باقی‌مانده نبود. framing TLS محتوای آن را عمومی/بی‌خطر نمی‌کند و نگاشت یک‌به‌یک ciphertext به SSPI ثابت نشده است.

## دریافت مستقل و حریم دادهٔ پژوهش
همان هفت مسیر عمومی ثابتِ metadata قبل از اجرای target دریافت شدند؛ پنج پاسخ 200 و دو 404. headers این دریافت‌های عمومی نیز برای equality فقط در فایل PRIVATE runner نگه داشته شدند. دو ProductConfig قبلی از fixture با SHA256 ثابت خوانده و با MD5 ستون ProductConfig در versions مستقل دوباره کنترل شدند. این pin/checksumها، امضای ناشر نیستند. هیچ آدرس یا کلید مشاهده‌شدهٔ target برای ساخت یک GET مستقل بازتاب داده نشد.

یک GET پژوهشی جداگانه به `/v2/products/agent_redist/cdns` با نام محصول برگرفته از config عمومی مستقل انجام شد: 1036 بایت، status 200. Path آن `agent/Agent-Redists-Live` بود، نه prefix مرجع هدف. هیچ مسیر حدسی از آن به catalog یا allowlist اضافه نشد و هیچ فایل اجرایی/پیش‌نیاز دریافت نشد. receipt در `public-reference-receipt.json` است؛ این lookup شاهد منشأ کلید محسوب نمی‌شود.

هیچ مقدار خام کلید، مسیر target، query، header-value یا بدنهٔ واقعی از runner صادر نشد. جفت‌سازی و equality در RAM انجام شد. به همین دلیل، نام route یا header schemaِ حذف‌شده را نمی‌توان اکنون از artifact استخراج کرد؛ نباید آن را با حدس جایگزین کرد.

## شکاف باقی‌مانده و گام بعدیِ مشخص
پیش از هر اجرای دیگری، ابزار باید برای پاسخ‌های دارای `|`، **فقط شکل header و نام ستون‌های شناخته‌شدهٔ پروتکل** را به‌صورت ساختاری و بدون مقادیر ردیف شناسایی کند و ساختار route را بدون کلیدهای پویا تشخیص دهد. این شواهد باید قالب واقعی را مشخص کند، نه اینکه قالب‌های JSON/MIME بیشتری کورکورانه امتحان شوند. سپس field equality و دریافت مستقلِ همان سند با مسیر ثابت یا شناسهٔ برگرفته از مرجع عمومی لازم است. تا آن زمان مسیر unknown باقی می‌ماند.

هدف اصلی همچنان دانلود مجاز بدون ارسال fingerprint است. این مرحله یک شرط تشخیصی را پیش برد، اما **فیلد هدف را حل نکرد و آماده‌بودن نسخهٔ نهاییِ محافظ حریم خصوصی یا پوشش دانلود کامل را اثبات نکرد**.

## شواهد و بازتولید
- `runtime.json` و `control.json`: مشاهدهٔ تکمیلی؛ `initial-runtime.json` و `initial-control.json`: مشاهدهٔ اول، جدا و بدون ادغام شمارش‌ها.
- `manifest.json`: یافته‌ها و حدود ادعا؛ `analyze.py`: کنترل run/source، شمارش مستقل از hierarchy خام و reconciliation. برای اجرای دوباره، `--raw-dir` شامل JSONهای اصلی و ZIP دانلودشده و `--out-dir` مقصد خروجی را تعیین می‌کند.
- SHA256 artifact اولیه: `018e62c32b955af16d20afc3a3bee0e125c198206c5d1623f93f1a4d4cd1c287`؛ تکمیلی: `bc46cba366c9ce0072447ae8a81140f14f3e2d165bf472632fb94aff4f39064f`. هر دو با digest صفحهٔ اجرای GitHub مقایسه شدند.
- profiler فایل runtime را به‌دلیل آرایه‌های ناهم‌اندازه مستقیم نپذیرفت. آرایهٔ request_value_audit.rows جدا profile شد: 56 observation، شامل 27 تکرارِ پالایش‌شده که حذف نشدند. public_download_path فقط برای ردیف‌های CDN است؛ null در ردیف‌های سرور نسخه طراحی‌شده است. constantهای GET/body و falseهای privacy، نتیجهٔ observation هستند نه تضمین حریم خصوصی. nullهای error در کنترل نشانهٔ نبود خطا هستند؛ run_id شناسه است، نه معیار عددی.
