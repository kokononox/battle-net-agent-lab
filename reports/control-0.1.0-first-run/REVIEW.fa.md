# نتیجهٔ واقعی WLab Control 0.1.0

هر دو case لاگ Dump complete دارند. control-clone.dmp به اندازهٔ 67,735,027 بایت و control-direct.dmp به اندازهٔ 67,820,879 بایت در گزارش ثبت شده‌اند. هر دو signature=MDMP، stream_count=18 و basic_header_valid=true دارند. محتویات کامل dumpها در ZIP نیست و مستقلاً parse کامل نشده‌اند؛ موفقیت مرحلهٔ تولید فایل در هدف کنترل با شواهد لاگ/وجود/اندازه/header پشتیبانی می‌شود، نه ادعای اعتبار کامل همهٔ streamها.

در هر دو case، کد خروج واقعی ProcDump برابر 1 است، اما label عمومی runner آن را failed نامیده است. این label طبقه‌بندی عدد خروج است، نه نتیجهٔ معنایی capture. نباید هیچ مقدار غیرصفر را به‌تنهایی شکست dump فرض کرد یا از این یک مشاهده قاعدهٔ کلی «۱ همیشه موفق است» ساخت. در این نسخه و همین اجرا، شواهد artifact و لاگ با تولید dump سازگارند. probe عمدی 7 و کد -1 worker در cleanup نیز خطای بازی نیستند؛ worker بعد از هر دو case زنده بوده و سپس توسط والد خودش بسته شده است.

write probe یک MiB هم موفق است. پس در همین اجرای کنترل، نوشتن روی G و capture در هر دو مسیر clone و direct برای هدف ساده کار کرده‌اند. این نتیجه خرابی عمومی قطعی دیسک/PSS را به‌عنوان توضیح ثابت‌شدهٔ شکست بازی پشتیبانی نمی‌کند، ولی سلامت همهٔ حجم‌ها و همهٔ هدف‌ها را تضمین نمی‌کند. علت خطای snapshot بازی هنوز معلوم نیست؛ anti-cheat یا مرگ clone ثابت نشده‌اند. کاربر قبلاً تأیید کرده بازی عادی مانده و snapshot.dmp نداشته است.

دیگر تکرار همین آزمون کنترل یا همان full dump بازی صرفاً برای تأیید این نتایج لازم نیست. مسیر پیشنهادی بعدی، خواندن یک‌باره و محدود صفحات کد نامزد با API خواندن حافظهٔ Windows است: هویت build/PID/زمان شروع و پایهٔ ماژول پیش از خواندن تطبیق داده شود؛ بدون debugger/PSS/injection/patch/نوشتن حافظه یا تغییر protection. فقط سه صفحهٔ کد از پیش تعیین‌شده، نه scan حافظه یا dump کامل. دسترسی ردشده یا guard/no-access باید ثبت و متوقف شود؛ هیچ bypass یا افزایش دسترسی ویژه/درایور پیشنهاد نشده است. این مسیر هنوز پیاده‌سازی یا روی بازی اجرا نشده؛ پیشنهاد قدم بعد است، نه نتیجهٔ موجود.

ارسال یا عدم ارسال CPU/BIOS روی TCP/3724 همچنان نامعلوم است. main و GUI BIOS Path 0.2 تغییر نکرده‌اند.
