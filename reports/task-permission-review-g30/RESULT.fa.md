# G30 — بازبینی قواعد دسترسی، نه اعطای معافیت

## یافتهٔ مشخص
در هر دو snapshot، DACL مربوط به PrintJobCleanupTask یک ACE از نوع AccessAllowed، بدون پرچم اضافه، برای Authenticated Users با mask `0x001f01ff` داشت. این mask شامل `WRITE_DAC (0x00040000)` و `WRITE_OWNER (0x00080000)` است. معنای این حقوق طبق مستندات Microsoft، تغییر DACL و مالک descriptor است.

مرجع: https://learn.microsoft.com/en-us/windows/win32/secauthz/standard-access-rights

این یافته، مانع صریح اتکا به «امضای معتبر فایل + ثابت‌بودن هش ACL» برای معافیت خودکار است. این گزارش اثبات دسترسی مؤثر یک token مشخص، بهره‌برداری، ارتقای دسترسی، یا مقصر بودن نصاب نیست؛ principal اجرا و کنترل‌های دیگر نیز در ارزیابی نهایی مهم‌اند. هیچ ACL یا Task برای «رفع» این مشاهده تغییر داده نشد.

## حالت Enabled
PrintJobCleanupTask در هر دو نمونه `Enabled=false` و `Disabled` بود. بنابراین این آزمایش جهت تغییر Enabled در G29 را ثبت نکرد و نباید از آن true→false یا false→true برای G29 نتیجه گرفت. برای سه Task دیگر، Enabled در XML به‌صورت مقدار صریح قابل خواندن نبود و null نگه داشته شد؛ null به معنای false نیست.

## نتیجهٔ بازبینی محافظه‌کارانه
ابزار مستقل `analysis-tools/task-security-review/ReviewTaskSecurity.py` روی همین داده اجرا شد:
- PrintJobCleanupTask: مانع اعتماد خودکار به علت ACE کنترلی Authenticated Users.
- RefreshCache و Registration: در شکل ACE پشتیبانی‌شده، ACE کنترلیِ خارج از SYSTEM/Administrators پیدا نشد؛ این نتیجه اجازهٔ معافیت نیست.
- SvcRestartTask: ACE کنترلی برای هویت دسته‌بندی‌نشده وجود دارد؛ هویت باید جداگانه resolve شود. هویت ناشناخته، کاربران عمومی فرض نشده و ریسک مؤثر آن ادعا نشده است. قاعدهٔ موجود Svc در runtime با این بررسی advisory تغییر نکرد.

بازبینی، deny/inherited/conditional/object-specific پیچیده یا دادهٔ ناقص را unknown نگه می‌دارد؛ هیچ نتیجه‌ای مجوز اجرای Task یا تغییر تصمیم بازیابی نیست. ۱۵ آزمون مثبت/منفی برای حقوق کنترلی، دادهٔ غایب، mask نامعتبر، ACE ناشناخته و اصل «عدم صدور معافیت» موفق شد.

## دامنه و اعتبار
بررسی فقط‌خواندنی تحت SYSTEM روی VM جداگانه، دو نمونه با sleep درخواستی ۹۰ثانیه‌ای؛ فایل‌های مرتبط هر چهار Task در هر دو نمونه امضای Valid از Microsoft داشتند و هش آن‌ها با G29 برابر بود. امضا خارج از ایزوله‌سازی بررسی شد؛ سیاست revocation این API جداگانه audit نشده است.

نصاب اجرا نشد، فایروال و Taskهای هدف تغییر نکردند. فقط Task موقت خود آزمایش برای اجرای observer ساخته و در پایان unregister شد. ادعای «هیچ تغییر مطلق در سیستم» مطرح نیست.

منبع `5b4e6b32fbcc31b92e8baaadea516f54325b40da`، run `40192875844`، job `121167440691`؛ workflow با success تمام شد.

گزارش ۲۰۴۵۵بایتی، ۴۶ بخش، SHA-256:
`b59d84be8d6b3da88cb9628e3379062aa880711988f7c3d55d4e1066d768b35e`

schema/commit/run/اندازه/هش اعتبارسنجی شد؛ هشت مشاهدهٔ task و دو ACE موضوع یافته مستقلاً دوباره شمارش شدند. profiler دو snapshot را تشخیص داد؛ run_id شناسهٔ متنی است، ثابت‌های هویت معیار عددی نیستند و هشت مشاهده معادل هشت ماشین مستقل نیست. raw log، XML، SDDL، SID خصوصی و URL امضاشده منتشر نشده‌اند.

## جمع‌بندی اجرایی
capture زیر گیت در G29 اکنون کامل است؛ مانع اعتماد PrintJobCleanupTask دیگر صرفاً «کمبود لاگ» نیست. سه مانع بازیابی قبلی همچنان حفظ شدند. گسترش خودکار معافیت‌ها از روی امضای Microsoft رد می‌شود؛ EXE نهایی یا بازیابی امن سرتاسری هنوز اثبات نشده است.
