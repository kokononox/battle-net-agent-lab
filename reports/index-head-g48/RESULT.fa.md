# G48 — اختلاف اندازه هر ۱۶ فهرست با HEAD تأیید شد

## نتیجه واقعی
- هر 16 درخواست ثابت HEAD پاسخ HTTP 200 داد؛ هر 16 پاسخ دارای یک Content-Length عددی و بدون encoding، transfer یا Content-Range ناسازگار بود.
- طول فعلی هر 16 فهرست با انتظار قبلی فرق دارد؛ تعداد موارد برابر 0 است.
- هیچ بدنه‌ای توسط برنامه خوانده نشد؛ GET، Range، retry، redirect یا درخواست دیگری انجام نشد. این به معنای صفر بایت TCP/TLS یا هدر نیست.
- هر ۱۵ آزمون آفلاین پیش از شبکه موفق بود. hash کد و plan در preflight ثبت و پس از دریافت دوباره تطبیق داده شد.

## تطبیق با منبع اصلی
snapshot اصلی CDN config دوباره با MD5 محتوا و SHA256 قبلی تأیید شد. تمام ۱۶ انتظار قبلی با جفت‌های کلید/اندازه همان config منطبق‌اند. بنابراین در این بررسی خطای انتقال آن جفت‌ها به plan پیدا نشد؛ این ادعا تضمین صحت معنای خودِ فیلد منبع نیست.

جمع اندازه‌های قبلی و جمع اندازه‌های اعلام‌شده فعلی هر دو 272,368 بایت است؛ برابر بودن جمع، اختلاف تک‌تک کلیدها را برطرف نمی‌کند و نباید معیار پذیرش باشد.

## تفسیر محدود شواهد
این مشاهدات نشان می‌دهند mismatch فعلی واقعی است، نه اینکه علت آن معلوم شده باشد. هدرهای طول واقعی GETهای G46 ثبت نشده‌اند؛ HEAD جدید آن مقادیر تاریخی را بازیابی نمی‌کند. تغییر CDN، ناسازگاری config یا هر علت دیگری هنوز فرضیه است. از هدر تنها نمی‌توان نتیجه گرفت بدنه، کلید محتوا یا اعتبار ناشر درست است. هیچ index جدیدی دریافت یا پذیرفته نشد و جای نمونه سوم هنوز معلوم نیست.

## قدم بعدی پیشنهادی؛ اجرا نشده
به‌جای پذیرش خودکار طول جدید یا دریافت کامل ۱۶ index، طرحی برای دریافت فقط footer بیست‌وهشت‌بایتی هر index ثبت شد: حداکثر ۱۶ Range ثابت، جمعاً ۴۴۸ بایت بدنه مورد انتظار و ۴۶۴ بایت سقف خواندن بدنه با detector اضافه. این طرح سقف کل wire/TLS نیست.

شرایط طرح: پاسخ دقیق 206، Content-Length برابر 28، Content-Range دقیق با total مطابق HEAD؛ پاسخ 200 کل index پیش از بدنه رد شود. سپس MD5 تمام footer باید با کلید نام index از config قبلی برابر شود؛ checksum footer و فیلدهای قالب بررسی و اندازه ساختاری index از تعداد رکورد/بلوک محاسبه و با HEAD مقایسه شود. این گام فقط footer را می‌سنجد؛ checksum TOC/بلوک‌ها و محل نمونه سوم همچنان نیازمند محتوای کامل index هستند.

این فقط `next-footer-plan.unexecuted.json` است؛ footer، index یا payload جدیدی در G48 درخواست نشده. مجوز دریافت کامل index یا مجوز runtime تولید صادر نشده است.

## وضعیت محصول و نگه‌داری شواهد
هیچ installer، Agent یا payload اجرا نشد؛ firewall، hosts، task، CA و TLS policy تغییری نکردند. شاخه اصلی و محصول 0.9.10 منجمد باقی ماندند. hash کاتالوگ deny-all قبلی دوباره تطبیق داده شد؛ تعداد مجوزهای runtime صفر است. نبود fingerprinting یا نبود جمع‌آوری اطلاعات با HEAD اثبات نمی‌شود.

فقط هدرهای allowlist‌شده در رسید ثبت شده‌اند؛ Cookie/Set-Cookie، هدرهای trace و هویت به گزارش افزوده نشده‌اند. پوشه خصوصی POSIX با mode 0700 و نشانگر یک‌بارمصرف 0600 برای همین اجرای پژوهشی استفاده شد؛ این کنترل، ضد-replay سراسری یا یکپارچه‌سازی با private-store ویندوز نیست.

## بازتولید آفلاین
از ریشه checkout شاخه پژوهشی:

```sh
python -m unittest discover -s analysis-tools/index-head-g48 -p 'test_offline.py' -v
python analysis-tools/index-head-g48/analyze.py
```

تحلیل از fixture عمومی G43 در نبود snapshot خام استفاده می‌کند؛ fallback شبکه ندارد. دستور `head_indices.py` را برای بازتولید آفلاین اجرا نکنید؛ آن کد دریافت واقعی است و نشانگر همان پوشه جلوی اجرای دوباره را می‌گیرد. فایل پیشنهاد ورودی همچنان executed=false دارد چون کپی تغییرنیافته پیشنهاد G46 است؛ اجرای واقعی G48 در رسید جداگانه ثبت شده است.
