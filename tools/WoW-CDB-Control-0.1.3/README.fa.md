# کنترل مستقل CDB — نسخهٔ 0.1.3

**این بسته هیچ بازی‌ای را انتخاب یا اجرا نمی‌کند.** نصب CDB، تغییر شبکه، خواندن محتوای آپلود یا تحلیل تله‌متری هم انجام نمی‌دهد. فقط مشکل کنترل نسخهٔ قبلی را جدا می‌کند.

## چرا این نسخه؟

کنترل 0.1.2 به breakpoint رسید و فرمان gN را درخواست کرد، ولی دوباره در DbgBreakPoint متوقف شد. از آن لاگ به‌تنهایی نمی‌شد فهمید handler واقعاً اجرا شده یا RIP کجا بوده است. handler قبلی نیز مسیر ادامهٔ اجرا را ثبت یا در صورت باقی‌ماندن RIP روی همان int3 اصلاح نمی‌کرد.

کنترل جدید فقط برای **استثنای breakpoint خودِ برنامهٔ کنترل**، با نشانی دقیق تابع و بایت CC، اطلاعات مرحله را در رکورد ثابت ۶۴ بایتی می‌نویسد. اگر RIP روی همان CC باشد، فقط CONTEXT همین برنامهٔ آزمایشی را یک بایت جلو می‌برد؛ اگر از قبل بعد از CC باشد، چیزی را تغییر نمی‌دهد. نشانی/کد نامنتظره و تکرار استثنا را قبول نمی‌کند. در آغاز نیز stub دو بایتی CC C3 مربوط به DbgBreakPoint باید موجود باشد، وگرنه کنترل متوقف می‌شود.

**این رفتار روی بازی، loader بازی یا حافظه/کانتکست پردازش دیگری اعمال نمی‌شود.** هیچ شرط اجرای بازی هم حذف نشده است: این بسته اصلاً مرحلهٔ اجرای بازی ندارد.

## اجرا — کوتاه

1. ZIP را در پوشهٔ جدید قابل‌نوشتن استخراج کن و Start.cmd را اجرا کن. PowerShell، تغییر ExecutionPolicy و نصب جدید لازم نیست.
2. همان CDB رسمی x64 قبلی را بده؛ معمولاً خودکار پیدا می‌شود. **Start control tests** را بزن. لازم نیست بازی را باز کنی.
3. ابتدا کنترل بدون دیباگر اجرا می‌شود. فقط اگر خودش استثنا را هندل کند، به مسیر بعد از DbgBreakPoint برسد و خروج صفر داشته باشد، همان کنترل زیر CDB اجرا می‌شود.
4. بعد از پایان، فقط **control-only-result-….json** کنار ابزار را بفرست.

اگر CDB در prompt متوقف ماند، در پنجرهٔ ابزار **Save diagnostic now** را بزن و JSON نام‌برده‌شده را بفرست؛ این بار لازم نیست لاگ خام بفرستی. سپس در CDB دستور **qd** و Enter بزن تا جدا شود. اگر لازم شد از اجرای در جریان به prompt برسی، در پنجرهٔ CDB Ctrl+C بزن. از q، ضربدر CDB یا ادامهٔ اجباری خطای ناشناخته با g/gh/gN استفاده نکن. بستن پنجرهٔ ابزار، کنترل/CDB را متوقف یا جدا نمی‌کند.

## چه چیزی ثابت می‌شود؟

در خروجی، نتیجهٔ اجرای عادی و اجرای زیر CDB جدا هستند. کنترل نهایی فقط وقتی تأیید می‌شود که:

- اجرای بدون دیباگر با خروج صفر و رکورد تکمیل‌شده موفق بوده باشد؛
- CDB نشانه‌های دقیق اجرای اسکریپت، API و تحویل breakpoint را ثبت کرده باشد؛
- رکورد کنترل نشان دهد handler فقط یک استثنای موردانتظار را دریافت کرده، RIP معتبر بوده و به بعد از فراخوانی برگشته است؛
- کنترل هنگام برگشت هنوز دیباگر متصل داشته باشد، نه اینکه صرفاً پس از جداشدن CDB ادامه یافته باشد؛
- رکورد خطای داخلی نداشته و CDB هم خروج صفر داده باشد.

موفقیت این کنترل **به معنی سازگاری بازی با دیباگر، شناسایی TLS یا نبود/وجود ارسال CPU/BIOS نیست**.

## داده و محدودیت

رکورد ۶۴ بایتی شامل شمارنده‌ها و وضعیت‌های ثابت است، نه نشانی مطلق حافظه، محتوای بافر یا نام حساب. نشانی واقعی استثنا فقط درون خود کنترل برای تطبیق استفاده می‌شود و به رکورد/JSON نوشته نمی‌شود. JSON مشخص می‌کند handler فراخوانی شده یا نه، RIP روی int3 بوده یا بعد از آن، آیا CONTEXT خود کنترل یک بایت تغییر کرده و آیا اجرای بعد از فراخوانی انجام شده است.

برای Snapshot دستی، رکورد ممکن است هنوز در حال به‌روزرسانی باشد؛ آن را با نتیجهٔ نهایی اشتباه نگیر. ابزار هیچ پردازشی را خودکار نمی‌کشد و حفاظت ویندوز را غیرفعال نمی‌کند. استفاده از دیباگر و breakpoint نرم‌افزاری طبعاً اجرای کنترل را موقتاً متوقف/تغییر می‌دهد.

لاگ CDB می‌تواند مسیرها و پیام‌های debug خصوصی داشته باشد. **debugger-local.log و پوشهٔ جلسه را نفرست.** فقط JSON خروجی لازم است. هیچ فایل یا لاگ خودکار آپلود نمی‌شود. سقف خواندن لاگ ۱ MiB است، ولی حجم خام لاگ و مدت اجرا سقف اجباری ندارند. در صورت توقف از Snapshot و qd استفاده کن، نه انتظار نامحدود.

پوشهٔ جلسه زیر `%LOCALAPPDATA%\CdbControlOnly\<شناسه>` با ACL اختصاصی کاربر و SYSTEM ساخته می‌شود. بعد از پایان/جداسازی CDB و خروج کنترل، پوشهٔ همان جلسه را می‌توانی دستی پاک کنی.

بسته منبع است. Start.cmd با کامپایلر داخلی .NET Framework x64 دو EXE محلی از منابع همین پوشه می‌سازد. **CDB نصب‌شدهٔ فعلی کافی است**؛ آن را از محل نصب رسمی خودش انتخاب کن. امضای CDB توسط این کمک‌ابزار مستقلاً بررسی نمی‌شود. اگر سیاست سیستم مانع ساخت/اجرا شد، آن سیاست را خاموش نکن؛ فقط متن خطای کامپایل را بفرست.

## آزمون توسعه، بدون اغراق

- ۲۷ آزمون منطق و تجزیهٔ خروجی موفق‌اند.
- ۸ آزمون شبیه‌سازی‌شده روی خود handler موفق‌اند: RIP روی CC، RIP بعد از CC، کد استثنای غلط، نشانی غلط، RIP نامنتظره، استثنای تکراری، حالت غیرمسلح و بایت غیر CC.
- رابط و کنترل با C#5 و مراجع .NET Framework 4.8 برای x64 کامپایل شده‌اند.
- **اجرای واقعی Windows/CDB/VEH در محیط توسعه انجام نشده است.** آزمون‌های شبیه‌سازی جای آن را نمی‌گیرند. رکورد مرحله‌بندی‌شدهٔ این نسخه برای روشن‌کردن همین فاصله روی سیستم آزمایشی توست.

SyntheticTests.cs منبع آزمون توسعه است؛ Start.cmd آن را اجرا نمی‌کند. هیچ باینری بازی یا نصب‌کننده همراه بسته نیست.
