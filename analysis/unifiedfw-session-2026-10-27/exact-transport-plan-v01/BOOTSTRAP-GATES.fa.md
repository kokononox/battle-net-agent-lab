# دروازه‌های bootstrap — طرح، نه تضمین اتصال

## ثابت‌های هدف

- در حالت disconnected/connecting دادهٔ برنامه نباید به physical interface مجوز بگیرد؛ تنها حمل ازپیش‌بازبینی‌شدهٔ SSTP باید مستقل از نام/شمارهٔ کارت فیزیکی قابل نگهداری باشد.
- همان hostname پروفایل برای هویت سرور حفظ شود؛ تبدیل خودکار به IP و غیرفعال‌کردن اعتبارسنجی TLS راه‌حل نیست.
- پیدا شدن یک IP در cache و تطبیق یک flow با host تک‌سرویس برای اجازهٔ فایروال کافی نیست. رسید اخیر فقط همین همبستگی را ثابت می‌کند.
- خطای ۷۳۴ موقت علت‌یابی نشده؛ اتصال فعلی LAN و Connected/False برابر reconnect زیر ایزولاسیون نیست.

## مواردی که هنوز مانع اجرای واقعی هستند

1. **مرجع بازبینی مقصد:** نمایش محلی دقیق GUID/scope/owner/hostname/IP/service/port و ثبت رضایتِ متصل به همان محتوا هنوز adapter امن ندارد. hash تنها جلوی اعتماد به ورودی ساختگی را نمی‌گیرد؛ هیچ فایل approved=true کافی نیست. تغییر server/profile/IP به بازبینی تازه نیاز دارد، نه broad fallback.
2. **اعمال دقیق حمل:** باید مسیر فایل svchost، محدودیت واقعی service، remote IP و TCP443 در storeهای مربوط تازه خوانده/بررسی شوند. محدودیت PID مشاهده‌شده جای service filter را نمی‌گیرد. System32 path/hash مشاهده‌شده هم اعتماد امضا یا سلامت حافظه نیست.
3. **DNS وقتی VPN خاموش است:** cache امروز ممکن است منقضی شود یا پس از reboot نباشد. بدون طرح resolution محدود و قابل بازگشت، سردشدن cache اتصال را blocked نگه می‌دارد. هیچ اجازهٔ عمومی DNS، تغییر hosts، یا resolver مصنوعی در این مرحله اجرا نشده است؛ هر راهکار نیاز به scope/رضایت و تست مستقل دارد.
4. **TLS و وابستگی گواهی:** اعتبارسنجی اسم/زنجیره/EKU/ابطال باید سالم بماند. وابستگی‌های واقعی cache سرد، خط‌مشی و سرویس باید اندازه‌گیری شوند؛ این پروژه هنوز آنها را نمی‌داند. نه Authenticode شبکه‌زا را در مشاهده‌گر اجرا کرده‌ایم، نه اثبات کرده‌ایم TLS خود SSTP بی‌نیاز از مقصدهای دیگر است. مقصد اضافی از روی حدس مجاز نشود.
5. **underlay:** DHCP/IPv4/IPv6 و مسیر سرور باید بدون خروج دادهٔ برنامه کار کنند. Any-interface روی حمل دقیق مشکل احتمالی DHCP/route را به‌تنهایی حل نمی‌کند. LAN/Wi-Fi مستقل از alias هدف طراحی است، نه qualification تعویض کارت.
6. **transaction/recovery:** قبل از default-block/quarantine باید baseline و مسیر recovery قابل استناد باشند، حمل دقیق با read-back بررسی شود، داده در disconnect ثابتاً غیرفعال باشد و binding تازه قبل از re-enable بررسی شود. drift ناشناخته توقف است، نه reset یا Allow عمومی. خواندن bulk معتبر می‌تواند هزینه را کم کند، ولی به معنای اجرای هم‌زمانِ مراحل دارای وابستگی نیست.
7. **اثبات عملی:** پس از تکمیل موارد بالا، آزمون Windows هدفمند با packet capture برای اتصال اولیه، قطع/وصل، cache سرد، reboot و تعویض underlay لازم است. قبل از آنها no-leak یا توانایی اتصال VPN زیر ایزولاسیون ادعا نشود.

## اتصال به کد موجود

`input_valid` در draft به `saved_profile_matches`، `server_pin_current`، `transport_rule_verified`، `dns_bootstrap_ready` یا `tls_bootstrap_ready` در reconnect decision kernel تبدیل نمی‌شود. هرکدام reader/مرجع مستقل می‌خواهد. خروجی موفق مشاهده‌گر نیز خودش هیچ executor را صدا نمی‌زند. guardian و HF1.2.2 در این milestone تغییر نکرده‌اند.

نزدیک‌ترین توسعهٔ بعدی adapter بازبینی محلیِ مقصد است که raw binding را فقط در حافظه نگه دارد و برچسب approval را از فایل ورودی نپذیرد؛ بااین‌حال تا دروازه‌های bootstrap حل نشده‌اند، حتی رضایت مقصد هم اجازهٔ Apply نیست.
