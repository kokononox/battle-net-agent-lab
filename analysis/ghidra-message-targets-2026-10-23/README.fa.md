# نتیجهٔ آزمایش واقعی Ghidra روی سه هدف پیام

## نتیجهٔ قطعی این مرحله
Ghidra 12.2 در محیط تحلیل اجرا شد. هر سه تابع نامزد، فایل C همراه با `halt_baddata()` و هشدار قطع جریان به علت دستور نامعتبر تولید کردند. نمونهٔ کنترل، بدون این نشانگر، خروجی قابل‌خواندن داد. **بازیابی پذیرفته‌شدهٔ اهداف: صفر از سه**؛ این عدد درصد پیشرفت کل پروژه نیست.

هنوز مسیر CPU/BIOS → ساخت/سریال‌سازی پیام → ارسال TCP/3724 اثبات نشده است. نقش merge/creator/parse از نامزدهای متادیتا آمده، نه از اثبات رفتار این توابع.

| هدف | RVA | تعداد دستور در listing | بایت‌های پیشوند متوالی | وضعیت |
|---|---|---:|---:|---|
| merge candidate | 0x1B14120 | 2 | 6 | C ناقص با bad-data |
| creator candidate | 0x1B11190 | 0 | 0 | حتی دستور ابتدای تابع تعریف نشد |
| parse fallback candidate | 0x33068C0 | 7 | 23 | C نامعتبر برای استنباط رفتار |
| کنترل entry stub | 0x1DA9B0 | 8 | 25 | بدون halt_baddata؛ امضای تابع اثبات نشده |

هر چهار درخواست از دید API کامل شدند؛ هر چهار فایل C دارند. بنابراین API موفق یا وجود فایل C به معنای بازیابی منطق نیست. در creator حتی بازگشت موفق disassemble نیز با صفر دستور همراه بود. خطاها در C و لاگ هستند، نه ستون error خروجی TSV.

## چرا این آزمایش تکرار قبلی نبود؟
در فهرست نمونه‌های ثبت‌شدهٔ pilot و اسکریپت targeted از مرحله‌های قبلی، ورودی دقیق این سه هدف انتخاب نشده بود. targeted پیشین پنج محدودهٔ loader و دو محدودهٔ EXE را بررسی کرده بود. pilot نیز دوازده نمونهٔ دیگر داشت و تحلیل خودکار آن با محدودیت زمان متوقف شده بود. این ممیزی محدود به اسکریپت‌ها و فهرست خروجی‌های مشخص است؛ ادعا نمی‌کند تحلیل خودکار هرگز این آدرس‌ها را لمس نکرده است.

بازبینی مرجع از commit `9e4bde6537f4e3c29cf920730897f8cbcead0850` انجام شد. محتوای سه مرجع همراه این بسته با Git blob SHA1 و SHA256 کنترل شده است. بهبودهای قبلی loader پس از اعمال مدل‌های CFG تأییدشده بودند؛ آن نتایج با دیکامپایل خام این سه هدف یکسان نیستند.

## روش و محدودیت
- ورودی: Wow.exe، اندازهٔ 80,834,256 بایت؛ SHA256: `1c51e68c00e7183c2c187606d2c443c27252a629406454de4afec336e8c5753a`.
- AMD64 / PE32+، بدون CLR directory؛ image base برابر `0x140000000`.
- پروژهٔ تازه، `-noanalysis`، بدون patch بایت و بدون flow override؛ نام‌ها و محدودهٔ تابع‌ها دستی داده شدند. سه محدوده از pdata و محدودهٔ کنترل از stub شناخته‌شده آمدند.
- سقف درخواست دیکامپایل هر تابع ۳۰ ثانیه، کل فرمان ۲۴۰ ثانیه، CPU=2 و heap=1800M.
- خود فایل بازی اجرا، attach یا اصلاح نشد؛ ابزارهای Ghidra/JDK اجرا شدند.
- بایت‌های نمایش‌داده‌شده با فایل اصلی، حدود pdata، اشاره‌گرهای متادیتا و hash قبل/بعد تطبیق داده شدند. SHA کل ورودی پس از تحلیل نیز ثابت بود.
- شش آزمون منفیِ verifier، از بایت جعلی تا حذف نمونهٔ کنترل، همگی رد شدند. این کنترل‌ها اعتبار معنایی کل خروجی C را اثبات نمی‌کنند.
- عملگرهای عجیب در C تابع fallback را رفتار واقعی، I/O واقعی، رمزنگاری یا ضدتقلب تلقی نمی‌کنیم. این‌ها خروجی دیکامپایل متوقف‌شده هستند.
- توقف در پیشوندهای ۶، صفر و ۲۳ بایتی با مانع قبلاً ثبت‌شده هم‌راستاست؛ این مرحله یک بررسی واقعی با Ghidra اضافه کرد، نه رفع مانع.

## منشأ ابزار
Ghidra از release رسمی `Ghidra_12.2_build` و asset `ghidra_12.2_PUBLIC_20261016.zip` دریافت شد. اندازه و SHA256 با digest API رسمی و سابقهٔ ثبت‌شده تطبیق داشت:
`2c2cd776db3c1f6a097ba418922378ac3649cadd5e844a6f5f088ae628a7be67`.

Corretto 25.0.4.10.1 از URL رسمی AWS دریافت شد؛ اندازه و SHA256 با سابقهٔ ثبت‌شده مطابق بود:
`a45f1d385da8221fe1225dde5b6afa8e932a6acb93571b55eff4a39a2ebe7378`.
checksum مستقل ناشر برای JDK در این مرحله دریافت نشد؛ آن را تأیید ناشر نمی‌نامیم.

## تصمیم بعدی
نصب همین ابزار روی رایانهٔ کاربر یا تکرار کور دیکامپایل این سه ورودی فعلاً توجیه ندارد. مسیر مناسب بعدی، به‌دست‌آوردن شاهد تازه از **بایت‌های معتبر و قابل انتساب به همین بیلد در این سه محدوده** است؛ مثلاً artifact مجاز زمان اجرا که واقعاً این صفحات را داشته باشد. فایل‌های ثبت‌شدهٔ فعلی چنین شاهدی را فراهم نکرده‌اند. این نتیجه ناممکن‌بودن بازیابی در آینده یا نوع خاصی از محافظت را اثبات نمی‌کند.

## بازتولید
ابزار و باینری بازی عمداً در بسته/مخزن نیستند. با ورودی hash‌شدهٔ بالا و ابزارهای مشخص‌شده:

```bash
export INPUT_DIR=/path/to/input
python3 source/prepare.py
export GHIDRA_HOME=/path/to/ghidra_12.2_PUBLIC
export JAVA_HOME=/path/to/corretto-jdk25
export WORK_DIR="$PWD/work/run-01"
bash source/run.sh
python3 source/finalize.py
```

برای بررسی خروجی‌های بسته بدون اجرای دوبارهٔ Ghidra، با همان ورودی فقط `source/finalize.py` را اجرا کنید. WORK_DIR اجرای تازه باید مسیر پیش‌فرض بالا باشد تا finalize خروجی تازه را بخواند. `reports/output` حاوی C خام و listing است؛ `reports/validation.json` کنترل‌ها را ثبت می‌کند. `reports/headless.normalized.log` فقط مسیرهای محیط را جایگزین کرده است. کتابخانه‌های ورودی اضافی import نشدند؛ هیچ پروژهٔ باینری Ghidra در بسته نیست.
