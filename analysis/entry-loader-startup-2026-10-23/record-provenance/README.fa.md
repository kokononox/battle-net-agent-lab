# منشأ U و N — تطبیق مشروط با نام پایهٔ ماژول بارگذاری‌شده

## نتیجه و تصمیم

این گام منشأ بافر را مشخص‌تر کرد: **در قرارداد معمول Windows x64 و layout مرجع بررسی‌شده، record به عضو فهرست ماژول‌های لودشده و جفت فیلد خوانده‌شده به `BaseDllName.Length/Buffer` منطبق است**. در سناریوی مقدار دیسکِ global کنترل‌کنندهٔ شیفت، N برابر نصفِ رو به پایینِ طول بایتی است و بازهٔ U..U+2N با بافر همان نام سازگار می‌شود.

این تطبیق ایستا و مشروط است، نه مشاهدهٔ نام ماژول در اجرای کاربر، تأیید OS build او یا decode محتوای بافر. خواندن BIOS و ارسال CPU/BIOS روی 3724 هنوز اثبات یا رد نشده‌اند.

**تصمیم:** این شاخه فعلاً به‌عنوان مسیر نام/بافر ماژول در راه‌اندازی، از اولویت هدف سخت‌افزاری خارج می‌شود. تابع داخلی `0x6995D0` در این گام باز نشده است. کشف نقش این ورودی، مجوز دنبال‌کردن کور تابع‌های عمومی نیست؛ ادامه باید به شواهد اختصاصی جمع‌آوری مشخصات/پرشدن پیام برگردد. نتایج این شاخه حفظ می‌شوند، نه اینکه حذف یا بی‌اعتبار اعلام شوند.

## ورودی و دامنه

- همان `wow_loader.dll`، 41,250,000 بایت.
- SHA-256: `c0a3c393db5cee834387e4f151fb97b109370330a0ed02310f597cad999b6b0c`.
- commit پایهٔ این گام: `dec998500dce550a8f1d497df441d4be9bb95ab3`.
- همهٔ آدرس‌های ماژول RVA هستند؛ آدرس واقعی فرایند خوانده نشده است.
- هیچ فایل بازی اجرا، به‌عنوان کتابخانه بارگذاری یا patch نشد. فقط بایت‌ها، مدل حسابی و fixtureهای ساختگی بررسی شدند. attach، injection، تست شبکه و تغییر فایروال انجام نشد.

نتیجه مشروط به ورود به بلوک `0x14C2225`، گرفتن شاخهٔ فهرستِ غیرتهی، ثابت‌بودن کد و خواندن‌های عادی معتبر است. تغییر هم‌زمان فهرست loader مدل نشده است. دسترس‌پذیری این بلوک از ابتدای فرایند، همان حدود و فرض‌های گام‌های پیشین را دارد؛ در این گام اجرای واقعی یا پوشش همهٔ وضعیت‌های global ادعا نمی‌شود.

## ۱. زنجیرهٔ record و اهمیت انتخاب فهرست

دستورهای واقعی:

```text
0x14C2225  RAX = GS:[0x60]
0x14C222E  RAX = [RAX+0x18]
0x14C2232  RCX = RAX+0x10          ; head
0x14C223E  RAX = [RAX+0x10]       ; record/link
0x14C2242  compare RAX,RCX
0x14C2245  equal -> 0x14C3838     ; این شاخه در مسیر غیرتهی دنبال نمی‌شود
```

با فرض معمولِ GS/TEB در Windows x64، زنجیره با `TEB.ProcessEnvironmentBlock → PEB.Ldr → InLoadOrderModuleList.Flink` منطبق است. تعریف رسمی TEB و PEB موقعیت‌های آغازین را توضیح می‌دهد؛ تعریف رسمی loader-data جزئی و دارای هشدار تغییرپذیری است. نام و offset فیلدهای داخلی از مرجع مبتنی بر symbolهای عمومی گرفته شده‌اند، نه از حدس روی بخش‌های Reserved تعریف عمومی.

| دسترسی | تطبیق در layout مرجع x64 |
| --- | --- |
| `GS:[0x60]` | اشاره‌گر PEB در TEB |
| `PEB+0x18` | Ldr/LoaderData |
| `Ldr+0x10` | سرلیست InLoadOrderModuleList |
| ابتدای entry، `+0x00` | InLoadOrderLinks |
| `record+0x58` | BaseDllName.Length |
| `record+0x60` | BaseDllName.Buffer، یعنی 0x58+8 |

**نباید 0x10 از record کم کرد.** اینجا head در `Ldr+0x10` متعلق به فهرست load-order است و link آن در ابتدای entry قرار دارد. فهرست memory-order در layout مرجع head دیگری در `Ldr+0x20` و link با offset 0x10 دارد؛ اشتباه‌گرفتن این دو، تفسیر فیلدها را خراب می‌کند. همچنین `FullDllName` در offset 0x48 قرار دارد، نه 0x58.

layoutهای محدود موردنیاز با `ctypes` و نوع‌های صریح ۱۶/۳۲/۶۴‌بیتی دوباره چیده شدند. این صرفاً مقایسهٔ تعریف مرجع است؛ ctypes هیچ DLL بازی یا سیستم ویندوز را بارگذاری نکرده است.

منابع: [TEB رسمی](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-teb)، [PEB رسمی](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-peb)، [loader-data عمومی](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-peb_ldr_data)، [layout سرلیست‌ها](https://www.geoffchappell.com/studies/windows/km/ntoskrnl/inc/api/ntpsapi_x/peb_ldr_data.htm)، [layout entry](https://www.geoffchappell.com/studies/windows/km/ntoskrnl/inc/api/ntldr/ldr_data_table_entry).

## ۲. منشأ دقیق U، L و N

record ابتدا در stack ذخیره و پیش از خواندن Buffer دوباره بازیابی می‌شود؛ بنابراین تغییر RAX در محاسبات طول، منشأ اشاره‌گر U را عوض نمی‌کند:

```text
L = zero_extend(word(record + 0x58))
U = qword(record + 0x60)
N = L >> effective_shift(G)
G = word(module + 0x20F9B98)
```

در فایل بررسی‌شده G برابر `0xF92D` است. از بایت‌های واقعیِ محاسبات CL و دستور `SHR RAX,CL` ثابت شد که با همین G، شمارش مؤثر شیفت یک است:

```text
N = floor(L / 2)
U + 2*N = U + (L & 0xFFFE)   (mod 2^64)
```

اگر L زوج باشد، انتهای بازه دقیقاً U+L می‌شود. اگر L فرد باشد، یک بایت آخر در این محاسبه پوشش نمی‌یابد. زوج‌بودن را بدون شرط به همهٔ مقادیر مدل تعمیم نداده‌ایم.

طبق [تعریف رسمی UNICODE_STRING](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_unicode_string)، Length طول بایتی و Buffer اشاره‌گر به ذخیرهٔ wide-character است؛ در صورت null-terminated بودن، Length شامل صفر انتهایی نیست. این با تقسیم طول بایتی برای شمارش واحدهای ۱۶‌بیتی سازگار است. **N را تعداد code point یا کاراکتر Unicode نمی‌نامیم** و هیچ رشته‌ای در این گام decode نشده است.

### قید مهمِ global را حذف نکنید

global زمان اجرا ثابت فرض نشده است. برای هر ۶۵٬۵۳۶ مقدار ممکن G، شمارش شیفت جداگانه بررسی شد؛ همهٔ شمارش‌های ۰ تا ۶۳ ممکن‌اند و هر کدام برای ۱٬۰۲۴ مقدار G حاصل می‌شوند. پس نصف‌شدن طول، نتیجهٔ عمومی همهٔ globalها نیست.

یک شاهد حل‌گر: با G=6 و L=2، شمارش شیفت ۵۲ و N=0 است، در حالی که floor(L/2)=1. این مقدار global **نمونهٔ حل مدل است، نه مقدار مشاهده‌شده در فرایند**. وجود این شاهد جلوی تبدیل سناریوی دیسک به ادعای بی‌شرط را می‌گیرد.

## ۳. حفظ منشأ در زنجیرهٔ فراخوانی

بایت‌های آماده‌سازی آرگومان‌ها و replay پیشین `0x5C6440` دوباره تطبیق یافتند:

```text
0x14C2450: RCX=N, R8=U
  -> wrapper 0x15B40A0
0x15B410E: RDX=U, stack argument 7=N
  -> 0x5C6440
0x5C6ED9: stack argument 6=U, stack argument 8=N
  -> 0x683780
0x68379B..0x6837EF: source range U..U+2*N
```

«source» نام تفکیکی همان اشاره‌گر record در گام قبل است؛ جهت و محتوای تبدیل داخلی `0x6995D0` هنوز بررسی نشده‌اند. replay `0x5C6440` همچنان به globalهای ثبت‌شدهٔ خودش و محافظ stack وابسته است. این زنجیره، trace اجرای کاربر نیست.

برای محافظ‌های میان محاسبهٔ N و محل call، هر دو حالت PF بررسی شدند: هر دو مسیر بدون تغییر RAX به آماده‌سازی آرگومان‌ها می‌رسند. در wrapper نیز هر دو حالت CF پس از کم‌کردن stack، به بلوک انتقال یکسان می‌رسند. دستورهای مربوط به فلگ‌ها و شروع‌های واقعی هر شاخه به بایت‌ها قفل شده‌اند؛ دیس‌اسمبلی خطیِ بایت‌های گمراه‌کننده استفاده نشده است.

## ۴. آزمون و استقلال بررسی‌ها

- producer معنای دستورهای محاسبهٔ طول را با Capstone/BitVec بازسازی و پنج پرسش نقض را با Z3 بررسی می‌کند: شمارش شیفت، نصف‌شدن طول، گسترهٔ طول زوج، گسترهٔ همهٔ طول‌ها و انتهای بازه؛ هر پنج `unsat` شدند.
- verifier جدید، محاسبهٔ شیفت را با Python integer و ثابت‌های خوانده‌شده از opcodeهای قفل‌شده بازسازی می‌کند؛ برای این فرمول از Z3 و Capstone استفاده نمی‌کند.
- تمام ۶۵٬۵۳۶ مقدار G برای شمارش شیفت و تمام ۶۵٬۵۳۶ مقدار L **در G دیسک** بررسی شده‌اند. این بررسیِ جداگانهٔ دو دامنه است، نه ادعای پیمایش همهٔ 2^32 جفت G,L.
- هفت fixture ساختگی شامل طول صفر، طول‌های زوج و فرد مرزی و حالت سرلیست تهی بررسی شد. هیچ fixture دادهٔ حافظهٔ کاربر نیست.
- ۱۴ آزمون خراب‌سازی رد شدند: فهرست اشتباه، adjustment اشتباه entry، فیلد/offset اشتباه رشته، فرض ثابت‌بودن global، حذف شرط طول، ضریب یا منشأ اشتباه آرگومان، تغییر بایت، ادعای نام runtime، ادعای نبود ارسال، ادعای ارسال BIOS، تأیید ساختگی OS و تغییر پیوند baseline.
- baseline انتقال `0x5C6440` دوباره replay و بررسی شد. این بخش همان پیاده‌سازی و Capstone گام قبلی را به‌کار می‌برد؛ آن را یک decoder مستقل تازه نمی‌نامیم. آزمون‌های خراب‌سازی قدیمی baseline و آزمون‌های GUI در این گام دوباره اجرا نشده‌اند.
- دو اجرای entrypoint، دو گزارش اصلی یکسان ساختند؛ ورودی‌های ناشناس هم رد شدند. جزئیات در `reports/reproduction.json` ثبت شده است.

## حدود نتیجه

در این گام نام واقعی هیچ ماژولی، محتوای حافظهٔ فرایند یا OS build کاربر خوانده نشده است. layout مرجع داخلی است و تعریف عمومی Microsoft نیز هشدار تغییرپذیری دارد. تفسیر دقیق عبارت است از: «با قرارداد معمول Windows x64 و layout مرجعِ تطبیق‌یافته، این ورودی نام پایهٔ ماژول است.»

این تحلیل نبود رفتار سخت‌افزاری در کل loader، EXE یا تابع داخلی را ثابت نمی‌کند. اما برای دنبال‌کردن همین شاخه به‌عنوان مسیر مستقیم CPU/BIOS، شاهد تازه‌ای نداریم؛ به همین دلیل گسترش کور این شاخه متوقف می‌شود. برای ادامهٔ هدف اصلی باید یک پیوند اختصاصیِ جمع‌آوری سخت‌افزار یا مقداردهی فیلد پیام انتخاب شود، نه اینکه هر تابع عمومی به‌عنوان قدمی به سوی 3724 شمرده شود.

تست تازه، اجرای بازی، attach یا تغییر بلاک‌ها از کاربر لازم نیست. سورس، شواهد و تصمیم ادامه در همان شاخهٔ `analysis/entry-loader-startup-2026-10-23` ثبت می‌شوند؛ main و GUI 0.2 تغییر نمی‌کنند. همگام‌سازی روال پایان گام است، نه سرویس پس‌زمینه.

## بازتولید

```bash
python -m pip install -r requirements.txt
python source/run_review.py --input /path/to/wow_loader.dll --out-dir /path/to/new-results
```

فقط بررسی گزارش موجود، با نیاز به Capstone برای replay baseline و بدون Z3/pefile:

```bash
python source/verify_record.py --input /path/to/wow_loader.dll --report reports/provenance-proof.json --out /path/to/new-verification.json
```

`baseline/5c6440-scenario-proof.json` و منبع verifier آن برای بازبینی انتقال همراه بسته‌اند؛ فایل بازی همراه بسته نیست. این بسته نسخهٔ اجرایی تازهٔ ویندوز یا GUI نیست.
