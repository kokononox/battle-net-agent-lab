# تحلیل محدود تابع 0x5C6440 — گام سوم مسیر راه‌اندازی

## نتیجه

در تابع `wow_loader.dll + RVA 0x5C6440`، اولین dispatcher با ورودی سراسری DWORD دلخواه، ۱۷ مسیر حسابی سازگار و **۱۷ مقصد متمایز** دارد. این عدد مربوط به این تابع است؛ گام قبلی `0x14BC180`، ۱۷ مسیر و ۱۶ مقصد داشت. پوشش همهٔ DWORDها و ناسازگاری زوج‌به‌زوج مسیرهای این dispatcher بررسی شد؛ این پوشش کل تابع یا مسیرهای واقعی فرایند نیست.

در سناریوی صریحِ برابرماندن خواندن‌های سراسری با مقادیر روی دیسک، و با شرط stack توضیح‌داده‌شده، مسیر محدود این تابع به call در `0x5C6ED9` با مقصد `0x683780` می‌رسد. پیش از call، یک DWORD محلی ساخته و آدرس آن به مقصد داده می‌شود. مقدار این DWORD در **همین سناریو صفر است، نه برای همهٔ مقادیر runtime**.

این یک پیوند داده‌ای و کنترل‌جریان قابل‌بازبینی است؛ معنای تابع مقصد، BIOS، آماده‌سازی EXE و ارسال شبکه هنوز شناسایی نشده‌اند.

## ورودی و منشأ

- ورودی: `wow_loader.dll`، 41,250,000 بایت؛ SHA-256: `c0a3c393db5cee834387e4f151fb97b109370330a0ed02310f597cad999b6b0c`.
- از پنج قطعهٔ آرشیو موجود در `binaries/retail-70448` در commit `f257422eaed942f6c8c15ec84192734878df4f93` بازیابی شد. هش هر قطعه، آرشیو و سه فایل داخلی با manifest قبلی تطبیق یافت؛ هیچ باینری تازه‌ای وارد مخزن نمی‌شود.
- بازهٔ تابع در `.pdata`: `[0x5C6440, 0x5C6F0C)`، طول `0xACC` بایت.
- همهٔ آدرس‌های کد و global، RVA هستند. ImageBase ترجیحی `0x180000000` است؛ آدرس runtime مشاهده نشده است.

هیچ PE ورودی اجرا، بارگذاری به‌عنوان کتابخانه یا patch نشد. تحلیلگر فقط فایل را می‌خواند و معنای محدود دستورها را در مدل حسابی پیاده می‌کند. attach، injection، اجرای بازی، درخواست شبکهٔ بازی و تغییر فایروال انجام نشد.

## اولین انتخاب‌گر

DWORD خوانده‌شده از `0x212326C` را x بنامیم. عبارت ۳۲‌بیتی اولیه:

```text
state = (((x + 0x4605E98C) XOR 0x9D9EC112)
         - 2*x + 0x900FDF43) mod 2^32
```

مقایسه‌های signed و برابریِ dispatcher از `0x5C6564` مدل شده‌اند. مقادیر witness در گزارش نمونهٔ حل هستند، نه مقادیر runtime. برای مقدار دیسک `x=0x208757B5`، state برابر `0x4A14B02C` و نخستین مرز مسیر `0x5C6CAE` است. ثابت‌بودن این global در فرایند ادعا نمی‌شود.

بررسی‌کنندهٔ مستقلِ dispatcher بدون Capstone و pefile، opcodeها، مقصد شاخه‌ها و عبارت اولیه را از بایت‌ها بازبینی می‌کند. پرسشِ وجود DWORD خارج از اجتماع مسیرها و پرسش‌های هم‌پوشانی، `unsat` شدند. هر دو مدل از Z3 یکسان استفاده می‌کنند، نه دو solver مستقل.

## مسیر مشروط تا انتقال داده

مدل بعدی ۵۴۳ رخداد دستور، ۴۱۲ شروع دستور متمایز، ۸۸ تصمیم شاخه و ۱۹ خواندن متمایز از حافظهٔ ماژول را ثبت می‌کند. تکرار dispatcher در این شمارش طبیعی است؛ تعداد رخداد دستور، تعداد تابع نیست.

فرض‌ها:

1. هر خواندن ثبت‌شده از حافظهٔ ماژول، هنگام خواندن همان بایت‌های روی دیسک را داشته باشد. حتی مقدار cookie خوانده‌شده نیز در فهرست فرض‌ها ثبت شده است.
2. دستورها تغییر نکرده باشند؛ stack و دسترسی‌ها معتبر باشند؛ exception، انتقال غیرمحلی و تغییر ناهمگام مدل نشده‌اند.
3. در محافظ `0x5C677F`، مقدار unsigned پایین ۳۲ بیتِ `entry_RSP - 0x118` بزرگ‌تر از `0x2400` باشد. شاخهٔ مکمل که ESP را تغییر می‌دهد، پوشش این مسیر نیست.
4. ورودی‌ها مطابق انتقال wrapper قبلی باشند. RCX، RDX، R9 و آرگومان هفتم stack نمادین می‌مانند. **R9 عدد 0x44 فرض نشده است**؛ wrapper آن را از stack فراخواننده می‌خواند.

برای نمایش stack، مبنای مصنوعی `0x1000000008` انتخاب شده که با قرارداد تراز ورود x64 سازگار است. این آدرسِ فرایند کاربر نیست. در این مسیر تنها استفادهٔ تصمیم‌ساز از مقدار مطلق stack همان محافظ بند ۳ است؛ سایر روابط با اختلاف offset ثبت می‌شوند. دستورهای هم‌پوشان فقط از شروع‌های واقعاً دنبال‌شده دیکد شده‌اند، نه دیس‌اسمبلی خطی کل بازه.

### آرگومان‌ها در call به 0x683780

اگر S مقدار RSP در ورود به `0x5C6440` باشد، frame اصلی `S-0x118` است:

| محل انتقال | مقدار در مدل |
| --- | --- |
| RCX | `0x17` |
| RDX | R9 ورودی تابع؛ اشاره‌گر نمادین منتقل‌شده از wrapper |
| R8 | `S-0x4C`، آدرس DWORD محلی در frame+`0xCC` |
| R9 | `0x10` |
| آرگومان stack شمارهٔ ۵ | RCX ورودی |
| آرگومان stack شمارهٔ ۶ | RDX ورودی |
| آرگومان stack شمارهٔ ۷ | `0x2F` |
| آرگومان stack شمارهٔ ۸ | آرگومان stack شمارهٔ ۷ ورودی |

این‌ها توصیف محل‌های انتقال طبق قرارداد x64 هستند، نه prototype، نوع داده یا معنای قطعی تابع. تا این call، در مسیر مدل‌شده اشاره‌گرهای ورودی dereference نشده‌اند و writeها فقط در stack مدل بوده‌اند؛ رفتار تابع فراخوانده‌شده و مسیرهای دیگر خارج از این ادعا هستند.

بایت‌های wrapper نشان می‌دهند R9 ورودی این تابع از `[wrapper_frame+0x68]` می‌آید؛ با محاسبهٔ stack، این همان stack+`0x28` فراخوانندهٔ wrapper است، نه R9 پیشین آن فراخواننده. در شاخهٔ قبلی، این مقدار آدرس scratch در stack بود. بررسی بایت‌های wrapper در verifier قفل شده است؛ هویت محتوای آن scratch هنوز معلوم نیست.

## صفر بودن مقدار، نتیجهٔ عمومی نیست

seed داده از `RVA 0x20E0E58` با مقدار دیسک `0xCD76CD71` خوانده می‌شود. مدل عددی جداگانه فقط برای آزمون حساسیت، مقدار این خواندن را در حافظهٔ مدل صفر قرار داد؛ فایل ورودی تغییر نکرد. مسیر به همان call رسید ولی DWORD حاصل `3795322209` بود. برخی شاخه‌های میانی نیز تفاوت داشتند. بنابراین مقدار محلی به داده وابسته است و نمی‌توان «همیشه صفر»، «پیام خالی» یا «عدم ارسال» نتیجه گرفت. این آزمایش یک ضدنمونهٔ مصنوعی است، نه مشاهدهٔ runtime یا جست‌وجوی کامل همهٔ seedها.

## اعتبارسنجی و حدود استقلال

- producer مسیر از BitVec و Z3 استفاده می‌کند؛ verifier جداگانه از Python integer و پیاده‌سازی جداگانهٔ رجیستر، فلگ و stack استفاده می‌کند.
- نگاشت PE در verifier با `struct` و parser دستی است، نه pefile.
- دیکدر دستور مسیر در هر دو **Capstone** است؛ این تأیید با دو disassembler مستقل نیست.
- replay عددی، ترتیب دستورها، تمام تصمیم‌های شاخه، globalهای خوانده‌شده، DWORD محلی و انتقال آرگومان‌ها را تطبیق داد.
- سه آزمون خراب‌سازی dispatcher (حذف مسیر، تغییر global و witness غلط) نیز رد شدند.
- ۱۱ آزمون خراب‌سازی گزارش مسیر رد شدند: مقصد call، offset اشاره‌گر، مقدار محلی، حذف شرط global، حذف محافظ stack، تغییر بایت، وارونه‌کردن شاخه، حذف دستور، تغییر global، ادعای ارسال و ادعای ثابت‌بودن runtime.
- اجرای بسته از entrypoint و بازتولید دوباره، چهار گزارش اصلی را بایت‌به‌بایت یکسان تولید کرد؛ جزئیات در `reports/reproduction.json` است.
- آزمون‌های نسخهٔ GUI و گام‌های قبلی در این مرحله دوباره اجرا نشده‌اند.

## وضعیت و قدم بعد

ارسال CPU/BIOS روی 3724، خواندن BIOS، نویسندهٔ اسلات EXE در `0x4AD5F38` و آماده‌سازی کد **هنوز اثبات نشده‌اند**. نبود شاهد در مسیر محدود پیش از call، نبود رفتار در کل برنامه را ثابت نمی‌کند.

هدف بعدی `0x683780` است: ابتدا مصرف آرگومان‌های مشخص بالا، به‌ویژه pointer به DWORD محلی و اشاره‌گرهای ورودی، بررسی شود. فقط در صورت وجود شاهد، ارتباط با دادهٔ ماژول یا EXE دنبال شود؛ فعلاً به آن برچسب شبکه، رمزگشا یا unpacker نمی‌دهیم.

همگام‌سازی در پایان گام روی شاخهٔ `analysis/entry-loader-startup-2026-10-23` است، نه سرویس پس‌زمینه. main و GUI 0.2 تغییر نمی‌کنند. این بسته ابزار تحلیل و بازبینی است، نه نسخهٔ اجرایی جدید ویندوز. تست تازه از کاربر لازم نیست.

## بازتولید

Python 3 در محیط مجازی؛ نصب وابستگی‌ها برای ابزار تحلیل، نه اجرای بازی:

```bash
python -m pip install -r requirements.txt
python source/run_review.py --input /path/to/wow_loader.dll --out-dir /path/to/new-results
```

فقط اعتبارسنجی گزارش مسیر، با Capstone و بدون Z3/pefile:

```bash
python source/verify_review.py --input /path/to/wow_loader.dll --report reports/scenario-proof.json --out /path/to/new-verification.json
```

برای بررسی dispatcher، `verify_dispatch.py` به Z3 نیاز دارد ولی Capstone و pefile لازم نیست. نسخه‌های distribution این گام در requirements قفل شده‌اند؛ Z3 این محیط `4.16.0.0` است و با نسخهٔ ثبت‌شدهٔ بستهٔ قبلی یکسان فرض نشده است.
