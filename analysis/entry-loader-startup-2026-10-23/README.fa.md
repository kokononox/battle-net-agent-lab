# بررسی آفلاین نقطهٔ ورود و TLS لودر — گام بعد از BIOS Path 0.2

## ادامهٔ جدید و وضعیت فعلی

گام دوم در [helper-14bc180/README.fa.md](helper-14bc180/README.fa.md) ثبت شد: ۱۷ مسیر اولین dispatcher، بلوک شرطی با دسترسی‌های شبیه PEB/Ldr و زنجیرهٔ wrapper تا `0x5C6440`؛ همگی با دامنه و شرط‌های صریح. نویسندهٔ اسلات EXE و ارسال BIOS روی 3724 همچنان نامعلوم‌اند. سورس، شواهد و نتیجهٔ آزمون در هر گام با همین شاخه همگام می‌شوند.

**بخش‌های زیر گزارش تاریخی گام اول هستند؛ برای آخرین نتیجه، ادامهٔ بالا را بخوانید.**

## نتیجهٔ این گام

از اسکن دوبارهٔ رشته‌ها عبور کردیم و یک مسیر راه‌اندازی را با بایت‌های واقعی بررسی کردیم. در callback صفر TLS لودر، برای ورودی `Reason=1`، تمام مسیرهای عادیِ مدل‌شده پیش از هر خروج به فراخوانی `wow_loader.dll + RVA 0x14BC180` می‌رسند. این نتیجهٔ ایستا و مشروط است، نه مشاهدهٔ اجرای بازی و نه شناسایی کارکرد تابع مقصد.

**وضعیت پرسش اصلی همچنان نامشخص است:** هیچ زنجیرهٔ اثبات‌شده‌ای از خواندن CPU/BIOS به پرشدن پیام، serialization و ارسال روی اتصال realm TCP 3724 به دست نیامده است. رشته، import، آدرس تابع یا موفقیت در دیس‌اسمبلی به‌تنهایی چنین زنجیره‌ای نیست.

## ورودی و دامنه

فایل‌های اصلی از آرشیو قطعه‌شدهٔ موجود در همین مخزن، مسیر `binaries/retail-70448` در commit پایهٔ `131779214fef477493e2cfee3c82d27ab3d7987d`، بازیابی شدند. اندازه و SHA-256 همهٔ قطعه‌ها، آرشیو و سه ماژول با manifest تطبیق یافتند. باینری جدیدی به این بسته اضافه نشده است.

| فایل | بایت | SHA-256 |
| --- | ---: | --- |
| Wow.exe | 80834256 | `1c51e68c00e7183c2c187606d2c443c27252a629406454de4afec336e8c5753a` |
| wow_loader.dll | 41250000 | `c0a3c393db5cee834387e4f151fb97b109370330a0ed02310f597cad999b6b0c` |
| libxell.dll | 359792 | `5ce63652eee5720203e0e41cc97eb45ee541c499c8a51d4bdb1e8fe4eaef4890` |

هیچ فایل ورودی اجرا یا patch نشد؛ اتصال به فرایند، تزریق، اجرای بازی، شبیه‌سازی کامل PE و تغییر فایروال انجام نشد. اسکریپت‌ها فقط بایت‌ها را می‌خوانند و عبارت‌های حسابی محدود را تحلیل می‌کنند. فایل‌های خروجی در پوشهٔ جدا نوشته می‌شوند.

تمام آدرس‌های زیر **RVA** هستند، نه offset فایل. image base ترجیحی EXE برابر `0x140000000` و لودر برابر `0x180000000` است؛ این اعداد آدرس مشاهده‌شدهٔ runtime نیستند.

## تفکیک‌های تأییدشده

1. EXE یک descriptor واردات دارد: `Wow_loader.dll`، ordinal شمارهٔ ۱، اسلات IAT برابر `0x3B5B000`. export متناظر در لودر `0x22EFF0` است. وجود import به‌معنای اجرای خودکار export توسط entry point نیست.
2. entry point خود EXE در `0x1DA9B0` از اسلات دیگری، `0x4AD5F38`، آدرس می‌خواند؛ اگر تهی نباشد، `call rax` می‌کند. این اسلات در دنبالهٔ مجازی `.data` است و روی دیسک بایت متناظر ندارد. در بارگذاری معمول PE این ناحیه ابتدا صفر می‌شود؛ **نویسندهٔ بعدی و مقدار runtime آن هنوز معلوم نیست**. بنابراین عددی را به‌عنوان qword موجود در فایل گزارش نکرده‌ایم.
3. سه خانهٔ TLS در EXE همگی به `0x1DA9E0` اشاره دارند؛ بایت‌های stub برابر `C2 00 00` است.
4. لودر دو callback TLS دارد: `0xDF87C0` و `0x200319C`. هدف جدید این گام callback اول است؛ entry point و stubهای پیشین کشف تازه محسوب نشده‌اند.
5. لودر ۳۶ import descriptor دارد که همگی `FirstThunk=0x20A0088` را تکرار می‌کنند، با جدول‌های lookup جدا. از روی این اسلات مشترک، نام یک API runtime را قطعی نسبت نمی‌دهیم. گزارش importها را به‌صورت descriptorهای مستقل نگه می‌دارد، نه دیکشنری با کلید اسلات.

## اثبات محدود مسیر callback اول

بازهٔ ثبت‌شده در `.pdata`: `[0xDF87C0, 0xDF88D9)`، طول ۲۸۱ بایت.

SHA-256 این بازه:
`63e6cb40089dcf063485ef3c4d0b0e2d831a20fec57893eb55cd1cbc087dc53d`

دیس‌اسمبلی خام با دنبال‌کردن هر دو شاخه وارد بایت‌های هم‌پوشان می‌شد. برای مدل نرمال‌شده هیچ بایتی تغییر نکرد؛ فقط سه تصمیم مستند به گراف اعمال شد:

| محل شاخه | تصمیم در مدل | دلیل |
| --- | --- | --- |
| `0xDF8822` | رفتن به `0xDF8869` | `AND AL, 0xFF` بلافاصله قبل از `JAE`، CF را صفر می‌کند. |
| `0xDF886C` | ادامهٔ مستقیم | `CMP EDX,1` و فرض صریح `DLL_PROCESS_ATTACH=1`؛ EDX در مسیر پیشین تغییر نمی‌کند. |
| `0xDF88B8` | ادامهٔ مستقیم | عبارت محافظ برای هر DWORD فرد است؛ ثابت مقایسهٔ `0x40B8FEBE` زوج است؛ JE نمی‌تواند گرفته شود. |

محافظ اول در `0xDF8814` **ثابت نیست و هر دو شاخه‌اش باقی مانده است**. مقدار خوانده‌شده روی دیسک در نمونهٔ فعلی با ثابت مقایسه برابر می‌شود، ولی آن را invariant زمان اجرا فرض نکردیم. مقادیر نمونهٔ ۰، ۱ و `0xFFFFFFFF` نتیجهٔ دیگری می‌دهند.

اثبات حسابی محافظ دوم، با حساب پیمانهٔ `2^32`:

```text
K1 = 0x4F87B8DB   (odd)
K2 = 0x4D3E9198   (even)
K3 = 0x72579D11
K4 = 0x8474598D   (odd)
c = (x + K1) XOR K2
r = -((c + K3) + x + K1) + c + K3 + x = -K1
g = (c + r + K4) XOR x
```

`c` نسبت به `x` زوجیت مخالف دارد؛ `K4-K1` زوج است. پس `g` همیشه فرد و هرگز برابر با ثابت زوج نیست. سه پرسش نقض به Z3 داده شد؛ هر سه `unsat` شدند. بررسی‌کنندهٔ دوم، بدون Z3، pefile و Capstone، PE و اهداف پرش‌ها را مستقل می‌خواند و همین استدلال زوجیت را به‌همراه ۱۰٬۰۰۴ نمونهٔ حسابی بازبینی می‌کند. نمونه‌ها به‌تنهایی اثبات همگانی محسوب نمی‌شوند.

گراف نرمال‌شده **۴۶ دستور بدون هم‌پوشانی** دارد. بررسی گراف نشان می‌دهد هیچ مسیر خروج یا چرخهٔ پیش از call، در مدل فرایند-attach باقی نمانده است. در محل `0xDF88CE`، هدف نسبی call برابر `0x14BC180` است. مقادیر آماده‌شدهٔ رجیسترها: `ECX=0x62`, `EDX=0x1F`, `R8D=0x19`. این‌ها **مشاهدهٔ بایت‌های call site** هستند؛ prototype یا معنا و مصرف آرگومان‌ها در تابع مقصد اثبات نشده است.

### فرض‌های لازم

- فراخوانی معمول TLS با reason شمارهٔ ۱، طبق قرارداد ویندوز.
- بایت‌های دستور callback تا رسیدن به call همان بایت‌های بررسی‌شده باشند.
- خواندن DWORDها و stack موفق باشد؛ exception، انتقال غیرمحلی یا تغییر ناهمگام کد مدل نشده است.
- دربارهٔ مقدار globalها در runtime فرضی نداریم.
- بدنه و بازگشت تابع مقصد خارج از اثبات پیش از call است. لبهٔ بعد از call در نمایش، مشروط به بازگشت تابع است.

## کیفیت و حدود خروجی

- parser مستقل مبتنی بر کتابخانهٔ استاندارد: headerها، import/export، TLS، نگاشت raw/virtual، `.pdata`، بایت‌ها و اهداف rel32 را تأیید کرد.
- بررسی مستقل زوجیت و دسترسی به call: گذشت.
- ۷ آزمون خراب‌سازی گزارش: مقصد اشتباه، شاخهٔ اشتباه، file-backed خواندن اسلات مجازی، فرض ثابت‌بودن global، ادعای ارسال، تغییر بایت و حذف لبهٔ گراف؛ همگی رد شدند.
- تست‌های ۴۲تایی و ۱۴تایی ابزار قبلی در این گام دوباره اجرا نشده‌اند؛ آن‌ها را به این بررسی نسبت نمی‌دهیم.
- این بسته installer جدید Windows یا نسخهٔ جدید GUI نیست؛ **ماژول تحلیل و تأیید قابل‌بازتولید** برای گام راه‌اندازی است. نسخهٔ 0.2 و main دست‌نخورده‌اند.

## آنچه هنوز نداریم و قدم دقیق بعدی

بدنهٔ `0x14BC180` فقط به‌عنوان هدف واقعی call site شناسایی شده است. نقش آن، نوشتن در اسلات EXE، بازکردن/رمزگشایی کد، ارتباط با BIOS و هرگونه ارسال شبکه **نامعلوم** است. نباید به آن برچسب unpacker یا VM بدهیم. گام بعدی تحلیل محدود همین تابع و اثبات شاخه‌هایش از روی بایت‌هاست، با تمرکز بر هر write قابل‌اثبات که به اسلات یا کد EXE مرتبط شود؛ نبود آن ارتباط باید صریح گزارش شود.

برای این گام از کاربر تست بازی، تغییر تنظیمات سیستم یا فایل جدیدی لازم نیست.

## بازتولید برای توسعه‌دهنده

Python 3 در محیط مجازی؛ ورودی‌های هم‌هش در پوشه‌ای جدا. نصب پکیج‌ها فقط برای ابزار تحلیل است، نه اجرای بازی.

```bash
python -m pip install -r requirements.txt
python source/run_review.py --input-dir /path/to/verified-inputs --out-dir /path/to/new-results
```

فقط تأیید مستقل، بدون نصب وابستگی خارجی:

```bash
python source/verify_startup.py --input-dir /path/to/verified-inputs --report reports/startup-proof.json --out /path/to/verification.json
```

ابزار فقط hashهای همین ورودی‌ها را می‌پذیرد؛ این محدودیت عمدی است تا ruleهای مختص این build به فایل دیگری اعمال نشوند. هیچ مسیر خصوصی، URL امضاشده یا اطلاعات ورود در بسته نیست.

نسخهٔ توزیع پکیج‌ها در اجرای حاضر: pefile `2024.8.26`، capstone `5.0.9`، z3-solver `5.3.1.0`. مقدار نسخهٔ داخلی گزارش‌شده توسط binding کپستون `5.0.7` بود؛ برای تکرار نصب، نسخهٔ distribution در requirements ثبت شده است.

## فایل‌ها

- `source/prove_startup.py`: گزارش byte-bound، سه query اثبات و CFG تازه.
- `source/verify_startup.py`: parser مستقل PE و تست‌های خراب‌سازی گزارش.
- `source/run_review.py`: اجرای متوالی تولید و تأیید.
- `reports/startup-proof.json`: دادهٔ ساختاریافتهٔ ورودی‌ها و اثبات.
- `reports/tls-process-attach.normalized.asm`: دیس‌اسمبلی همراه علت هر annotation.
- `reports/verification.json`: نتیجهٔ بررسی مستقل و ۷ تست ردشدن ادعا/خرابی.
- `reports/input-manifest.json`: منشأ و hashهای آرشیو اصلی.

## منابع قرارداد PE / TLS

- Microsoft PE Format: https://learn.microsoft.com/en-us/windows/win32/debug/pe-format — zero-fill برای بخش مجازی، TLS callback array به‌صورت VA و قرارداد callback.
- Microsoft DllMain: https://learn.microsoft.com/en-us/windows/win32/dlls/dllmain — reason شمارهٔ ۱ برای process attach و ۲ برای thread attach.

این اسناد قرارداد معمول loader را توضیح می‌دهند؛ جایگزین مشاهدهٔ runtime این بازی نیستند.
