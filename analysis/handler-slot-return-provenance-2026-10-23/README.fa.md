# منشأ محلی مقدارِ نوشته‌شده در اسلات handler

## نتیجهٔ تازه

هدف این گام یافتن منشأ local slot برابر [RSP+0x338] در تابع لودر با بازهٔ pdata [0x902A40, 0x905AA6) بود. رابطهٔ محلی زیر از بایت‌ها استخراج و مستقل تأیید شد:

```asm
0x902E0C  xor ecx, ecx
0x902E0E  call qword ptr [rip + 0x179D93C]  ; slot RVA 0x20A0750
0x902E14  mov qword ptr [rsp + 0x338], rax
```

در بازگشت عادی فراخوانی مطابق قرارداد x64، مقدار بازگشتی RAX فوراً در slot ذخیره می‌شود؛ دستور دیگری بین CALL و STORE نیست. RCX پیش از call صفر است. سایر آرگومان‌ها و هویت تابع مقصد هنوز تعیین نشده‌اند.

در بلاک دیگر تابع:

```asm
0x90593B  mov rax, qword ptr [rsp + 0x338]
0x905943  mov qword ptr [rip + 0x189647E], rax ; destination RVA 0x219BDC8
```

اسلات مقصد همان اسلات مجازیِ خوانده‌شده توسط thunk استثنا در 0x1F4DC80 است. **اگر** بلاک مقداردهی پیش از بلاک دوم اجرا شود و نوشتن هم‌پوشان یا غیرمستقیم دیگری slot محلی را تغییر ندهد، مقدار منتقل‌شده همان خروجی call است. ترتیب واقعی اجرا و alias analysis کامل هنوز اثبات نشده است. این یک رابطهٔ محلی دقیق است، نه زنجیرهٔ runtime مشاهده‌شده.

## مرزها و شرط ورود

از اولین dispatcher، یک مسیر نحوی به frontier برابر 0x902DBC ثبت شد. بلاک از آن مرز، شامل محاسبه از localهای دیگر و JAE به 0x905776 است؛ برای رسیدن به callها و store باید شاخهٔ fallthrough گرفته شود. مقادیر آن predicate هنوز حل نشده‌اند.

دو فراخوانی قبلی در همین بلاک وجود دارند؛ بازگشت عادی آن‌ها نیز فرض لازم برای رسیدن به call موردنظر است و احراز نشده است. صرف وجود مسیر نحوی به معنی قابل‌رسیدن‌بودن این store در اجرای واقعی نیست. CFG کل تابع در این گام بازسازی نشده است.

اسکن دقیق displacement برابر 0x338 در همین بازه دو محل دستور با prefix کامل را نشان داد: یک store و یک load. decodeهای بدون REX prefix نیز به‌صورت نامزدهای هم‌پوشان حفظ شده‌اند؛ آن‌ها چهار دستور مستقل نیستند. جست‌وجوی دقیق RSP displacement، نوشتن از طریق alias، base دیگر، pointer عبوری به callee یا کد runtime را پوشش نمی‌دهد. «تنها store مطلق» ادعا نشده است.

## اسلات فراخوانی هنوز به API مشخص وصل نشده است

در فایل دیسک، qword اسلات 0x20A0750 برابر 0x20A1A98 است. این عدد به‌عنوان function pointer واقعی زمان اجرا یا بدنهٔ کد تعبیر نشده است. بررسی تفسیر احتمالی import-by-name نیز نامی نداد؛ نخستین ۳۰ بایت محل پیشنهادی صفر است. فرض پاک‌شدن نام یا نوع دقیق رکورد نیز ثابت نشده است.

ارجاع‌های خام FF15/FF25 به همین اسلات در این آدرس‌ها ثبت شدند:

- 0x902E0E
- 0x115576A
- 0x2005E01
- 0x20062F7
- 0x2013EF3

این فهرست نامزدهای raw با مقصد یکسان است، نه اثبات دسترسی یا اجرای تمام call siteها. از شباهت امضا یا صفر بودن RCX، نام API قطعی نسبت نداده‌ایم. گلوگاه فعلی، تعیین هویت مقصد runtime یا سازوکار مقداردهی این اسلات است، نه رمزگشایی یک «کلید» از عدد دیسک.

## تأیید مستقل

verify.py با parser تازهٔ PE مبتنی بر struct، بدون pe_manual/Capstone/Z3، بایت‌ها، اتصال نحوی مسیر dispatcher، پیوستگی CALL→STORE، offset محلی و هر دو مقصد RIP-relative را تأیید کرد. GNU objdump مرز ۳۴ دستور یکتا را مستقل تطبیق داد. بایت‌های نامزدِ رکورد نام نیز خالی تأیید شدند.

این آزمون اجرای Windows نیست. API identity، بازگشت calleeهای قبلی، predicate بلاک، ترتیب دو بلاک، aliasهای کامل، مقدار runtime و نقش در آماده‌سازی سه صفحهٔ هدف همچنان نامعلوم‌اند. CPU/BIOS serialization و ارسال ثابت نشده‌اند.

هیچ PE ورودی اجرا یا patch نشد؛ attach، تغییر protection، spoof یا ابزار Windows جدید انجام نشد. پاسخ تهیه‌کنندهٔ بسته‌های ثالث برای ادامهٔ این گام لازم نبود و هیچ ادعای آن بسته‌ها وارد شواهد این رابطه نشد. main و GUI 0.2 تغییر نکردند.

## ادامهٔ مستقیم

شناسایی مقصد اسلات 0x20A0750 یا نوشتنِ مقدار معتبر در آن، با تمرکز بر همین call siteهای مرتبط. تا شناسایی معتبر، نام API یا مقصد handler حدس زده نمی‌شود و عدد RVA روی دیسک نیز به‌جای آدرس زنده به کار نمی‌رود.
