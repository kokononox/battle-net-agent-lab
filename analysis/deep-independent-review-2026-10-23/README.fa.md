# تحقیق عمیق‌تر: تفکیک مسیر گزارش خرابی از سرنخ Eidolon

## جمع‌بندی اجرایی
تحقیق جدید، کلید یا الگوریتم رمزگشایی این بیلد را به دست نیاورد و ارسال CPU/BIOS روی TCP/3724 را اثبات یا رد نکرد. اما دو نتیجهٔ مشخص داد:

1. برای کنارگذاشتن شاخهٔ wrapper/اسلات API از جست‌وجوی مستقیم رمزگشا، اکنون شواهد ایستای بسیار قوی‌تری داریم: دو caller، دستور fail-fast، ساختار دقیق رکورد استثنا و تطبیق با سورس عمومی CRT. این نتیجه دیگر صرفاً به حدسِ اسم API از روی یک آرگومان صفر متکی نیست.
2. در خود DLL پین‌شده، نشانۀ لفظی `EIDOLON` در `.eidsig` تثبیت شد و بخش همراه `.eid` جداگانه بررسی شد. این یک سرنخ واقعیِ فایل است، نه کلید یا decoder پیدا‌شده.

**هیچ تست زندهٔ تازه، attach، تغییر protection، injection، ابزار دورزن یا اجرای باینری بازی انجام یا درخواست نشد.**

## ۱. شاهد تازه برای طبقه‌بندی شاخهٔ قبلی

### دو caller مشخص، نه هم‌جواری تصادفی
در فایل `wow_loader.dll`، دو caller مستقیمِ wrapper واقع در RVA `0x20062EC` بررسی شدند:
- `[0x2006080, 0x200611D)`
- `[0x2006134, 0x2006207)`

هر دو به جفت اشاره‌گر ثابتِ RVA `0x2040A90` ارجاع می‌دهند و همان را به wrapper می‌فرستند. این جفت به RVAهای `0x2194730` و `0x21947D0` اشاره می‌کند و با دو عضو `ExceptionRecord` و `ContextRecord` در `EXCEPTION_POINTERS` سازگار است.

در caller دوم، نوشتن‌ها دقیقاً با چیدمان مستند Windows x64 منطبق‌اند:

| محل نسبت به رکورد | عضو منطبق | مقدار در مسیر بررسی‌شده |
| --- | --- | --- |
| `+0x00` | ExceptionCode | `0xC0000409` |
| `+0x04` | ExceptionFlags | `1` |
| `+0x18` | NumberParameters | `1` |
| `+0x20` | ExceptionInformation[0] | `2` |

در همان تابع، `mov ecx,2; int 0x29` وجود دارد. مستند Microsoft، `INT 0x29` با آرگومان در RCX را روش x64 برای `__fastfail` معرفی می‌کند و کد استثنای user-mode آن را `0xC0000409` می‌داند. بنابراین ثابتِ قبلی صرفاً یک عدد شبیه خطا نیست؛ با دستور و ساختار دادهٔ متناظر همراه است.

وجود این مسیر روی دیسک **به معنی وقوع خرابی واقعی در اجرای کاربر نیست**. ContextRecord نیز وضعیت ثبات‌های CPU هنگام استثنا را توصیف می‌کند، نه اینکه خودش گزارش مدل CPU یا BIOS باشد.

منابع:
- https://learn.microsoft.com/en-us/cpp/intrinsics/fastfail?view=msvc-170
- https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-exception_pointers
- https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-exception_record

### تطبیق سورس عمومی، با مرز روشن
در سورس عمومی `gs_support.c` از ReactOS/mingw-runtime، تابع `__report_gsfailure` چنین توالی‌ای دارد:

```text
ExceptionCode = STATUS_STACK_BUFFER_OVERRUN
SetUnhandledExceptionFilter(NULL)
UnhandledExceptionFilter(exception_pointers)
TerminateProcess(GetCurrentProcess(), STATUS_STACK_BUFFER_OVERRUN)
```

wrapper ما نیز آرگومان صفر، آرگومان اصلیِ جفت استثنا، خروجی یک call به‌عنوان آرگومان call آخر و `EDX=0xC0000409` دارد. همراهی این توالی با دو caller و چیدمان رکورد، **طبقه‌بندی به‌عنوان کد گزارش security-failure / fail-fast از خانوادهٔ CRT را بسیار قوی می‌کند**.

بااین‌حال، این تطبیق، PDB همین نمونه، نام دقیق توابع یا binding زندهٔ اسلات‌ها نیست. `SetUnhandledExceptionFilter` همچنان نامزدِ بسیار سازگار است، نه نامی که از یک نمونهٔ زندهٔ خوانده‌شده تأیید شده باشد. تمام اثرهای calleeها یا همهٔ handlerهای loader نیز تحلیل کامل نشده‌اند.

سورس پین‌شده:
https://github.com/reactos/reactos/blob/fae4549cb0cd6d5867e65e61c2bc29985b57bc98/sdk/lib/crt/startup/gs_support.c

**تصمیم:** این شاخه را از مسیر مستقیم جست‌وجوی رمزگشا کنار می‌گذاریم. دیگر برای تعیین اولویت آن، کاربر را وارد چرخهٔ خواندن دوبارهٔ اسلات API نمی‌کنیم. این تطبیق عمومی می‌توانست زودتر در اولویت قرار بگیرد.

## ۲. سرنخ مشخص در خود فایل: EIDOLON

در فایل DLL با SHA-256 ثابت قبلی:
- بخش `.eidsig` در RVA `0x2210000` با بایت‌های لفظی `EIDOLON` آغاز می‌شود.
- بایت بعدی `0x0B` است؛ برای آن بدون شناخت قالب، معنای «نسخهٔ ۱۱»، کلید یا الگوریتم تعیین نشده است.
- بخش `.eid` در RVA `0x2270000` دادهٔ file-backed دارد. موقعیت، اندازهٔ خام/مجازی و SHA-256 آن در `reports/evidence.json` ثبت شد.

این نام از خود باینری خوانده شده است. اما از آن **نمی‌توان علت خطای 1006، مکان کلید، الگوریتم رمز، نقش همهٔ داده‌های .eid یا پیوند آن با Warden را نتیجه گرفت**. نام یک چارچوب جای تحلیل قالب و dataflow را نمی‌گیرد.

### آزمون محدودِ پیوند به صفحات هدف
در دادهٔ file-backed همین `.eid`، سه RVA تابع هدف و سه مبنای صفحهٔ مربوط به آن‌ها، در دو نمایش صریح بررسی شدند:
- RVA به‌صورت little-endian 32-bit؛
- VA مبتنی بر ImageBase ترجیحی Wow.exe به‌صورت little-endian 64-bit.

در این دامنه هیچ تطبیق صریحی پیدا نشد. این نتیجه فقط همین نمایش‌ها را پوشش می‌دهد؛ دادهٔ رمز/فشرده، offset نسبی، جدول index، آدرس runtime یا محاسبه‌شده می‌تواند خارج از آن باشد. بنابراین «بخش .eid به صفحات ربط ندارد» نتیجهٔ مجاز نیست. در این نوبت پیوند ساختاری قابل‌اتکایی به همان سه صفحه بازیابی نشد.

## ۳. بررسی ابزارها و ادعاهای عمومی
یک منبع عمومی مرتبط با نام Eidolon و loaderهای WoW پیدا و بررسی شد: پروژهٔ **MAML**. README آن خودش را زبان تطبیق بایت و آدرس معرفی می‌کند؛ نمونهٔ `tools/durability/flatten.py` از فایل‌های با پسوند `-devirt.dll` برای بیلدهای 69273، 69382، 69404 و 69497 استفاده می‌کند.

این نمونه، decoder آمادهٔ بیلد 70448 ما ارائه نمی‌کند. تطبیق الگو روی تصویر آماده‌شده یا استفاده از BinDiff، به‌تنهایی بایت‌های غیرقابل‌تحلیلِ همین فایل اصلی را plaintext نمی‌کند. از فایل‌های اجرایی یا dumpهای بیلدهای دیگر استفاده نشد؛ خود پروژه نصب/اجرا نشد. این یک ارزیابی از منابع مشخصِ بررسی‌شده است، نه ادعای ممیزی کل مخزن یا ناممکن‌بودن کاربردهای دیگر ابزار.

منابع پین‌شده:
- https://github.com/mahmoudimus/maml/blob/8e34b843eb723b3d8faafb6015edaa7d76fe92fb/README.md
- https://github.com/mahmoudimus/maml/blob/8e34b843eb723b3d8faafb6015edaa7d76fe92fb/tools/durability/flatten.py
- https://github.com/mahmoudimus/maml/blob/8e34b843eb723b3d8faafb6015edaa7d76fe92fb/tools/durability/mapping.py

بحث عمومی قدیمی دربارهٔ رمزگشاییِ حین استفاده هم پیدا شد، اما نه هویت همین بیلد را داشت و نه شاهد خامی برای نمونهٔ ما. ادعای انجمن، جای بایت یا trace منطبق را نگرفت و هیچ injector/patch/decryptor متفرقه‌ای اجرا نشد. در جست‌وجوی محدود این نوبت، تعریف عمومیِ قابل‌اتکایی از قالب دقیق `.eid` همین نمونه پیدا نشد؛ این ادعای نبودن آن در همهٔ منابع نیست.

## ۴. بازگشت به سؤال اصلی

رابطهٔ ساختاری `ClientSystemSpec.engine_log → ClientEngineLogV2` و فیلدهای CPU/BIOS قبلاً ثبت شده بود؛ آن را کشف تازه حساب نمی‌کنیم. حاصل این تحقیق هنوز چنین است:

| حلقه | وضعیت |
| --- | --- |
| وجود فیلدها و نام کلیدهای سخت‌افزار در فایل | شواهد ساختاری قبلی |
| collector واقعی همین اجرا | بازیابی نشده |
| نوشتن نتیجه در همین شیء پیام | بازیابی نشده |
| serializer همان نمونهٔ پرشده | بازیابی نشده |
| اتصال payload به ارسال TCP/3724 یا endpoint HTTP | اثبات نشده |
| رمزگشا/کلید/کد آماده‌شدهٔ سه صفحهٔ هدف | بازیابی نشده |

گزارش‌های Warden شخص ثالث، با محدودیت‌های ثبت‌شدهٔ قبلی، این حلقه‌ها را پر نمی‌کنند. متن خطای 1006 نیز اجازه نمی‌دهد آن را به ضدچیت یا خرابی دیسک نسبت بدهیم. از این تحقیق قانون firewall، opt-out اثبات‌شده یا نسخهٔ جدید ابزار Windows صادر نمی‌شود.

## ۵. مسیر بعدیِ موجه و شرط توقف

سرنخ فنیِ باقی‌مانده، **قالب .eid / مسیر آماده‌سازی کد و پیوند قابل‌بررسی آن با صفحات هدف** است؛ نه callback عمومیِ گزارش خرابی. تنها با یافتن چنین پیوندی، بررسی یک الگوریتم یا کلید مشخص معنادار می‌شود. فعلاً چنین decoder یا پیوندی به دست نیامده و نصب صرف یک ابزار عمومی این شکاف را رفع نمی‌کند.

این تحقیق نشان می‌دهد کجا باید جست‌وجو را متوقف کرد و کدام نام در خود فایل مبنا دارد؛ نباید به‌عنوان «راه بازیابی کشف شد» فروخته شود. برای کاربر در این مرحله اقدام یا اجرای تازه‌ای لازم نیست. main و BIOS Path GUI 0.2 دست‌نخورده می‌مانند.

## بازتولید و QA
ورودی‌ها همان دو فایل پین‌شده‌اند. تحلیلگر فقط آن‌ها را می‌خواند:

```sh
PYTHONPATH=/path/to/deps python source/review.py /path/to/wow_loader.dll /path/to/Wow.exe NEW-evidence.json
python source/verify.py /path/to/wow_loader.dll /path/to/Wow.exe NEW-evidence.json NEW-QA.json
```

نیاز تحلیلگر: Python 3، pefile 2024.8.26، Capstone 5.0.9 و GNU objdump. verifier از PE parser مبتنی بر کتابخانهٔ استاندارد استفاده می‌کند، نه pefile یا Capstone. متن public-domain مرجع CRT همراه بسته است؛ سایر منابع فقط با URL/هش/نقل محدود ثبت شده‌اند.

مرز/طول دستورهای سه تابع با objdump مستقل مقایسه شد؛ verifier بایت‌ها، رکوردها، displacementها، تطبیق بخش‌ها و جست‌وجوی محدود را کنترل می‌کند، نه اجرای واقعی و معنای همهٔ mnemonicها. نتایج نهایی و آزمون‌های خراب‌سازی در reports ثبت‌اند. یک فرض اولیهٔ نادرست دربارهٔ محل tail-jump، قبل از تولید گزارش نهایی رد و اصلاح شد. فقط اجرای نهایی موفق مبناست.
