# گزارش پیشرفت ۵ — ارزیابی شاخهٔ Ghidra و استفادهٔ هدفمند در کار فعلی

## تصمیم
**Ghidra برای این کار مفید است و به مسیر تحلیل اضافه شد؛ اما نه به‌صورت دیکامپایل انبوه و اعتماد به هر خروجی C.** ترکیب مناسب فعلی: انتخاب آدرس معتبر و کنترل بایت/گراف، سپس Ghidra برای ساختاردهی شبه‌کد و اصلاح تدریجی نوع‌ها.

هیچ فایل بازی اجرا، emulate، inject یا patch نشد. تغییری در نصب بازی یا تنظیمات امنیتی داده نشد. این شاخه در مخزن موجود نگهداری می‌شود؛ شاخهٔ اصلی و شاخهٔ جلسهٔ دیگر دست‌نخورده‌اند. در این sync هیچ باینری بازی، پروژهٔ باینری Ghidra یا لاگ خام کاربر وارد Git نشده است.

- گزارش خودش نیز می‌گوید تحلیل EXE ناقص است و API-success، صحت شبه‌کد را ثابت نمی‌کند. در نمونه‌های EXE واقعاً `halt_baddata`، overlap و کنترل‌فلو ناقص وجود دارد.

## ۲. ابزار و روش این نوبت
- Ghidra 12.2 PUBLIC از release رسمی NSA دریافت شد؛ SHA256 بسته با digest اعلام‌شدهٔ GitHub تطبیق داشت.
- JDK کامل Amazon Corretto 25.0.4.10.1 از دامنهٔ رسمی Amazon دریافت شد. SHA256 آن ثبت شد؛ checksum مستقل رسمی برای آن در این مرحله تطبیق داده نشد. Java موجود محیط فقط runtime بود و برای شروع Ghidra کافی نبود.
- دو import اولیه با `-noanalysis`، حداکثر دو CPU و heap 1800M انجام شد. اسکریپت، فقط توابع منتخب را می‌سازد و دیکامپایل می‌کند؛ اسکن خودکار کل برنامه درخواست نشده است.
- مرز توابع از unwindهای بررسی‌شده و stubهای کوتاه قبلی به ابزار داده شد. این مرزها همگی کشف مستقل Ghidra نیستند. خود decompiler ممکن است tail-call یا مسیرهای خارج از محدوده را دنبال/inline کند؛ محدودهٔ انتخاب‌شده تضمین محصوربودن تمام استنتاج ابزار نیست.
- هدف، مقایسهٔ مستقیم با شواهد قبلی و بررسی بدنهٔ راه‌اندازی DLL بود، نه نمونه‌گیری اولین توابع در DLL گرافیکی.

## ۳. خروجی خامِ هدفمند

| هدف | خروجی API | ارزیابی محدود |
| --- | --- | --- |
| ورودی DLL، RVA 0x2006630 | تولید شبه‌کد | شرط reason==1 و helper قبلی دیده می‌شود؛ dispatcher نیز در خروجی inline شده است |
| cookie initializer نامزد، 0x2006670 | تولید شبه‌کد | ثابت، ماسک و مکمل با اسمبلی قبلی سازگار؛ چهار callee غیرمستقیم همچنان نامعلوم |
| dispatcher، 0x2006508 | تولید شبه‌کد | ساختار شاخه‌ها خواناتر شد؛ پروتوتایپ‌های فراخوانی غیرمستقیم نیاز به بررسی دارند |
| بدنهٔ راه‌اندازی، 0x1beb830 | شکست | خطای bad instruction/p-code؛ خروجی قابل قبول به دست نیامد |
| export ordinal 1، 0x22eff0 | شکست | bad instruction/overlap؛ خروجی خام قابل قبول به دست نیامد |
| stub ورودی EXE، 0x1da9b0 | تولید شبه‌کد | همان فراخوانی مشروط از slot نامعلوم و return 0؛ مقصد حل نشده |
| stub TLS، 0x1da9e0 | تولید شبه‌کد | همان بازگشت سادهٔ روی دیسک |

پنج مورد از هفت درخواست خام از نظر API شبه‌کد دادند. **این نسبت، نرخ بازیابی صحیح برنامه نیست**؛ نمونه‌ها کوچک و دست‌چین‌اند و معنی کامل برخی فراخوانی‌ها هنوز معلوم نیست.

نام‌هایی با پیشوند `review_` و بدنهٔ توابع، annotation تحلیلی‌اند. امضاهایی مانند `(void)` و نام‌های `_DAT_...` را نباید به‌عنوان امضای واقعی یا هویت معنایی قطعی تلقی کرد.

## ۴. پیشرفت اصلی: Ghidra روی export با CFG اثبات‌شده
برای export شمارهٔ ۱، در پروژه‌ای جدا:
1. 289 محدودهٔ دستورِ گراف مرحلهٔ ۴، بایت‌به‌بایت با ورودی Ghidra تطبیق داده شد.
2. دستورها با همان مرزهای ثبت‌شده تعریف شدند؛ بایت حافظه یا باینری تغییر نکرد.
3. فقط دو annotation برای fallthrough ثبت شد؛ هر دو بر اساس جفت پرش‌های مکملِ قبلاً اثبات‌شده هستند. مسیر false پرش اول به همان مقصد مشترک هدایت شد؛ اثر حذف‌شده فقط پرش مکمل و در یک مورد SAL DL,0 است.
4. هویت پرش‌ها، بایت‌ها و ثابت‌بودن فلگ‌ها دوباره بررسی شد. جدول annotationها در خروجی موجود است.
5. Ghidra این بار **شبه‌کد ساخت‌یافته با حلقه‌ها و محاسبهٔ مقدار برگشتی** تولید کرد؛ دیگر خطای fatal bad-instruction آن درخواست رخ نداد.

فایل: `output/wow_loader.dll.22eff0.verified-cfg.c`.

این خروجی خام نیست؛ **به CFG و اصلاحات ما متکی است و تأیید مستقل آن CFG محسوب نمی‌شود**. همچنان هشدار حذف بلوک دست‌نیافتنی و هم‌پوشانی نمادهای global وجود دارد. مقدار واقعی globalها، امکان تغییرشان در اجرا و مسیرهای exception/هم‌زمانی مدل نشده‌اند. برخی متغیرهای محلی فقط در مسیرهای خاص مقداردهی می‌شوند؛ تا مسیر stateها اثبات نشود، از ظاهر مرتب C نتیجهٔ قطعی نمی‌گیریم.

فایدهٔ عملی این روش آن است که مدل C سطح پایینِ پر از label/goto مرحلهٔ قبل، اکنون خروجی ساخت‌یافتهٔ قابل مرور دارد. بازیابیِ کاربرد تابع و هم‌ارزی کامل هنوز انجام نشده است.

## ۵. چه چیزی دربارهٔ تله‌متری ثابت شد؟
در این مرحله **هیچ مسیر تازه‌ای از CPU/BIOS به پیام و socket ثابت نشد**. تولید C برای یک تابع راه‌اندازی، جای شناسایی مقداردهی فیلدهای پیام و ارسال آن را نمی‌گیرد. نتیجهٔ ارسال یا عدم ارسال روی 3724 همچنان نامشخص است.

## ۶. روش پذیرفته‌شده برای ادامه
1. Ghidra ابزار اصلیِ مرور شبه‌کد توابع قابل‌خواندن باشد.
2. Capstone، PE metadata و بررسی مستقل بایت/گراف برای اعتبارسنجی مرزها باقی بمانند.
3. هر اصلاح CFG یا type/signature جداگانه ثبت شود؛ خروجی خام و اصلاح‌شده مخلوط نشوند.
4. در EXE محافظت‌شده، ساخت صدها هزار تابع یا زیادکردن timeout به‌تنهایی پیشرفت معتبر محسوب نشود.
5. برای بدنهٔ `0x1beb830` که هنوز شکست می‌خورد، ابتدا شاخه‌ها و مرزها بررسی شوند؛ خروجی ناقص به‌عنوان دیکامپایل موفق معرفی نشود.
6. x64dbg/attach بازی یا تکرار ابزار کرش‌زای قبلی جزو این مسیر فعلی نیست.

## ۷. فایل‌ها و بازتولید
- `run-targeted.sh`: نیازمند Ghidra 12.2 و JDK سازگار؛ متغیرهای `GHIDRA_HOME`، `JAVA_HOME`، `INPUT_DIR` و اختیاری `WORK_DIR`. برای اجرای دوباره، WORK_DIR تازه انتخاب کنید؛ overwrite خودکار وجود ندارد.
- `scripts/TargetedReview.java`: ورودی‌های hash-pinned، مرزهای مشخص و timeout هر تابع 30 ثانیه.
- `scripts/VerifiedExportReview.java`: پروژهٔ مستقلِ export، کنترل بایت و دو annotation اثبات‌شده؛ timeout دیکامپایل 45 ثانیه.
- `scripts/export-verified-instructions.tsv`: بایت و RVA دستورهای تأییدشده.
- `scripts/export-proven-fallthroughs.tsv` و `export-normalization-proofs.json`: جدول تغییرات metadata و علت هر مورد.
- `output/*.raw.c`: خروجی خام Ghidra یا گزارش شکست؛ نام raw به معنی صحت نیست.
- `output/*.verified-cfg.c`: خروجی متکی بر annotation؛ جدا از خام.
- `logs/`: لاگ ابزار Ghidra با مسیرهای محیط کار نرمال‌شده، نه لاگ خام بازی.
- `validate_outputs.py`: کنترل مستقلِ هش ورودی‌ها، بایت‌ها، پرش‌ها، annotationها و سازگاری فایل‌های خروجی؛ **نه اثبات صحت معنایی decompiler**.
- `provenance.json`، `tool-release.json`، `jdk-provenance.json` و `QA.json`: هویت ورودی/ابزار و حدود کنترل کیفیت.

اعتبارسنجی:
`python validate_outputs.py --input-dir INPUT --work-dir WORK`

در بازتولید، خروجی‌ها در WORK_DIR قرار می‌گیرند؛ برای اجرای validator، فایل‌های provenance و پوشهٔ scripts همین بسته را نیز در WORK قرار دهید یا از یک کپی تازهٔ کل این پوشه به‌عنوان WORK_DIR استفاده کنید. هیچ باینری ورودی در این پوشه توزیع نشده است.
