# پیگیری محدود مسیر BIOS — ClientEngineLogV2

## نتیجه

یک پیوند ساختاری تازه پیدا شد، اما معمای ارسال سخت‌افزار روی TCP/3724 هنوز حل نشده است. جدول پارسِ کاندید برای `ClientEngineLogV2`، آفست و بیت حضور هر ۹۸ فیلد را با دادهٔ MigrationSchema تطبیق می‌دهد. سه فیلد BIOS هم در این تطبیق هستند. این شواهدِ ساختار پیام است، نه شاهد اجرای جمع‌آوری، سریال‌سازی یا ارسال.

تحلیل فقط فایل را خوانده است؛ بازی اجرا نشده، attach، تزریق و تغییر حافظه انجام نشده است. هیچ باینری یا لاگ خام کاربر در این پوشه قرار ندارد.

## تفاوت با مرحلهٔ قبل

مرحلهٔ hardware-message-layout قبلاً ۹۸ فیلد، اندازهٔ کاندید ۳۷۶ بایت و دادهٔ MigrationSchema را گزارش کرده بود. شمارش مجدد همان فیلدها پیشرفت جدید محسوب نشده است. یافتهٔ تازه، بازیابی چرخهٔ کاندید `prototype ↔ ClassData ↔ TcParseTable` و تطبیق یک جدول مجزای پارس با آن داده‌هاست. دو جدول از یک باینری هستند؛ تطبیق ساختاری مستقل به معنای شاهد مستقلِ رفتار در اجرا نیست.

## ورودی دقیق

- فایل: Wow.exe، بیلد 12.1.5.70448
- SHA-256: `1c51e68c00e7183c2c187606d2c443c27252a629406454de4afec336e8c5753a`
- نشانی‌های زیر RVA هستند، نه نشانی قابل استفاده روی هر بیلد یا در حافظهٔ اجرای بازی.

## پیوند تازه

با مدل upstream protobuf v30.1، این ساختارها کاندید منطبق‌اند:

| جزء | RVA | تطبیق |
| --- | --- | --- |
| default instance | `0x4856510` | ClassData به این نمونه اشاره می‌کند |
| ClassDataFull کاندید | `0x47cf7e0` | prototype و parse table و descriptor table |
| TcParseTable کاندید | `0x47cec08` | اشارهٔ برگشتی به ClassData |
| descriptor registration | `0x47cebb0` | پیوند از ClassData با جابه‌جایی `+0x48` |

Header جدول: has_bits_offset=16، تعداد فیلد=98، بیشینهٔ شمارهٔ فیلد=198، field_entries_offset=604. تعداد کاندید ورودی سریع ۳۲ است؛ `56 + 32×16 = 568` با آغاز جدول lookup منطبق می‌شود. ۹۸ ورودی ۱۲بایتی نیز تا offset=1780 امتداد دارند و aux در 1784 شروع می‌شود.

هر ۹۸ ورودی با آفست MigrationSchema و رابطهٔ `parse_has_idx = 16×8 + hasbit_index` منطبق‌اند؛ ناسازگاری صفر است.

| شماره | فیلد | آفست در شیء کاندید | parse_has_idx | RVA ورودی |
| --- | --- | --- | --- | --- |
| 194 | motherboardBiosVendorName | `0x60` | 135 | `0x47cf2c0` |
| 195 | motherboardBiosReleaseDate | `0x68` | 136 | `0x47cf2cc` |
| 196 | motherboardBiosVersion | `0x70` | 137 | `0x47cf2d8` |

مدل MessageCreator در همین ساختار allocation_size=376، tag=-1 و alignment=8 می‌دهد. در upstream، tag=-1 ساخت مبتنی بر تابع است؛ این اشاره‌گر نباید serializer یا sender نامیده شود. نقش تابع‌ها و هم‌ارزی ABI نسخهٔ Blizzard هنوز از بدنهٔ کد تأیید نشده‌اند.

## سرنخ خواندن سخت‌افزار

رشته‌های دقیق UTF-16LE دارای NUL در فایل وجود دارند:

| رشته | RVA |
| --- | --- |
| HARDWARE\DESCRIPTION\System\BIOS | `0x3f99f10` |
| BIOSVersion | `0x3f9a070` |
| BIOSVendor | `0x3f9a088` |
| BIOSReleaseDate | `0x3f9a108` |
| BaseBoardProduct | `0x3f99f78` |
| BaseBoardManufacturer | `0x3f99fa0` |
| BaseBoardVersion | `0x3f9a0e0` |
| BiosMinorRelease | `0x3f9a128` |
| HARDWARE\DESCRIPTION\System\CentralProcessor\0 | `0x3f9a010` |

وجود این نام‌ها با قابلیت پرس‌وجوی سخت‌افزار سازگار است، ولی اجرای خواندن رجیستری یا تحویل حاصل آن به پیام را اثبات نمی‌کند. جست‌وجوی relocation-backed absolute reference فقط به ابتدای دقیق این رشته‌ها، مرجعی پیدا نکرد؛ این جست‌وجوی محدود، نبودِ استفاده را ثابت نمی‌کند. اسکن قبلیِ ۹ anchor نیز به عنوان نتیجهٔ تازه بازنشر نشده است.

## مرز نتیجه‌گیری

| پیوند مورد نیاز | وضعیت |
| --- | --- |
| وجود نام کلیدهای BIOS در فایل | مشاهده شد |
| وجود فیلدهای BIOS و تطبیق دو ساختار داده | تأیید ساختاری با مدل کاندید |
| خواندن واقعی BIOS در اجرا | اثبات نشده |
| انتساب خروجی خواندن به این فیلدها | اثبات نشده |
| سریال‌سازی پیام پرشده با سخت‌افزار | اثبات نشده |
| ارسال آن داده | اثبات نشده |
| اتصال آن ارسال به realm / TCP 3724 | اثبات نشده |

جدول پارس، ساختار **خواندن/پارس پیام سریال‌شده** را توصیف می‌کند. حتی کدی که از روی این جدول فیلدی را مقداردهی کند، لزوماً جمع‌کنندهٔ سخت‌افزار نیست. این یافته نه اثبات ارسال روی ۳۷۲۴ است و نه اثبات عدم ارسال روی آن. از آن نمی‌توان قانون فایروال جدید یا نتیجهٔ قطعی حریم خصوصی استخراج کرد.

گلوگاه بعدی، بازیابی یک بدنهٔ قابل بررسی است که خواندن سخت‌افزار را به مقداردهی این شیء وصل کند؛ سپس باید مصرف‌کنندهٔ همان شیء تا serializer و اتصال شبکه دنبال شود. این گزارش آن بدنه را بازیابی نکرده است. برای پیشرویِ مؤثر، منبع جدید مثل نمادهای مجاز، کد منبع یا بیلد مجازِ قابل تحلیل لازم است؛ تکرار همان اسکن‌های metadata جای این شاهد را نمی‌گیرد. فعلاً از کاربر اجرای ابزار، تغییر انسداد یا آزمایش کرش‌زا خواسته نمی‌شود.

## بازتولید و کنترل کیفیت

Python 3 به همراه pefile و protobuf لازم است. ورودی اجرایی را **اجرا نکنید**؛ این دستورها صرفاً بایت‌های فایل را می‌خوانند:

```sh
python analyze.py /path/to/Wow.exe --out evidence.json
python verify.py /path/to/Wow.exe --evidence evidence.json --out QA.json
```

اعتبارسنج از PE mapping دستی استفاده می‌کند، نه pefile یا import کردن تحلیلگر. descriptor از باینری دوباره خوانده می‌شود؛ ۹۸ ورودی، سه فیلد BIOS، چرخهٔ اشاره‌گر، هندسهٔ جدول و هش بررسی شدند. پنج آزمون تغییر عمدی نیز خطای آفست، تغییر نشانی ClassData و ادعای بی‌پشتوانهٔ population/serialization/3724 را رد کردند. نتیجه PASS است؛ این PASS فقط صحت آزمون ساختاری و محدودبودن ادعاهاست، نه صحت رفتار زمان اجرا یا اثبات ABI.

فایل evidence.json همهٔ ردیف‌ها و بایت‌های کوچک مرتبط را نگه می‌دارد. QA.json نتیجهٔ کنترل کیفیت است.
