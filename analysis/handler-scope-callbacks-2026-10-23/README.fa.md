# از handlerهای عمومی به callbackهای واقعی استثنا

## نتیجهٔ تازه

هشت آدرس handler استخراج‌شده از unwind بررسی شدند. الگوی کنترل cookie، بررسی کد استثنای C++ و dispatch جدول scope در آن‌ها دیده می‌شود؛ این شواهد با خانواده‌های runtime سازگار است، اما نام دقیق symbol یا نسخهٔ CRT احراز نشده است. مهم‌تر: handler عمومی می‌تواند فیلتر اختصاصی را صدا بزند، پس عمومی‌بودن بدنه دلیل کنارگذاشتن callbackهای آن نیست.

دو handler با layout مشخصِ count به‌علاوهٔ رکوردهای ۱۶ بایتی، در RVAهای 0x20069B4 و 0x2035A08، از روی مصرف واقعی فیلدها بررسی شدند. فقط برای همین دو قالب:

- ۶۲ جدول scope و ۷۸ رکورد استخراج شد.
- پس از کنارگذاشتن مقادیر قراردادی ۰، ۱ و 0xFFFFFFFF، ۴۳ آدرس callback متمایز ثبت شد. برخی finally و برخی فیلتر except هستند؛ همه «فیلتر» یا «رمزگشا» نیستند.
- پیوند function → unwind → HandlerData → scope → callback به‌طور مستقل تطبیق یافت.
- فرمت دادهٔ شش handler دیگر و handlerهای vectored هنوز بازسازی نشده‌اند. فهرست حاضر جامع همهٔ استثناهای برنامه نیست.

## سه callback ابتداییِ غیرهم‌جوار با خوشهٔ متأخر

این دسته‌بندی فقط مکانی/ساختاری است، نه تعیین نقش یا منشأ کتابخانه‌ای:

1. **0x1F4DC80**: یک JMP غیرمستقیم از اسلات RVA **0x219BDC8**. اسلات در دنبالهٔ مجازی .data است، بایت روی دیسک ندارد؛ qword یا مقصد runtime از آن گزارش نشده است. این callback در scope تابع 0x125BF0 ارجاع دارد. آدرس فراخوانی واقعی بدون مقدار runtime هنوز مجهول است.
2. **0x17DCD50**: بایت‌های `B8 FF FF FF FF C3`، یعنی بازگشت مستقیم DWORD برابر 0xFFFFFFFF. وابستگی آن به scope تابع 0x15A3170 ثابت شد؛ بدنهٔ این stub به‌تنهایی رمزگشا نیست. اثر ادامهٔ استثنا بر فراخواننده/Context بررسی نشده است.
3. **0xC59140**: بدنه‌ای با محاسبات مبهم و dispatcher؛ به‌عنوان callback در scope تابع **0x1FF6330**، بازهٔ محافظت‌شدهٔ [0x1FF67C5, 0x1FF67DB)، ثبت شده است. خود تابع در pdata بازهٔ [0xC59140, 0xC59D90) دارد. این یک ارتباط مشخص با سازوکار استثناست، **نه ارتباط اثبات‌شده با صفحات هدف و نه شناسایی رمزگشا**.

برای callback سوم، پیمایش خام دوشاخه‌ای با قواعد محدود پرش مکمل در موقعیت 0xC59D4D متوقف شد، چون decoder در آن موقعیت دستور نداد. امکان‌پذیری آن مسیر هنوز اثبات نشده؛ از این خطا نتیجهٔ رمزگذاری، خرابی فایل یا غیرقابل‌تحلیل‌بودن نمی‌گیریم. CFG کامل گزارش نشده است. اشتباه اولیهٔ انتخاب root قدیمی اصلاح و خروجی قدیمی حذف شد؛ فایل custom-filter-attempt.json صریحاً وضعیت incomplete دارد.

## شواهد تفکیک نقش‌ها

- 0x2005E5C از frame و دادهٔ handler مقدار می‌خواند، XOR می‌کند و به 0x2005F70 می‌رود.
- 0x2005F70 مقدار RCX را با global مقایسه می‌کند و در عدم تطابق به مسیر دیگری می‌رود. مقدار فعلی دیسکِ global برابر مقدار شناخته‌شدهٔ پیش‌فرض cookie x64، 0x2B992DDFA232، است؛ مقدار runtime ثابت فرض نشده است.
- handler 0x20069B4 جدول scope را می‌پیماید و می‌تواند آدرس محاسبه‌شده از رکورد را به‌صورت غیرمستقیم فراخوانی کند؛ همین نکته مانع ردکردن آن صرفاً به علت شکل runtime می‌شود.
- شرط 0xE06D7363 و در برخی بدنه‌ها ثابت‌های 0x19930520/21 برای طبقه‌بندی مقدماتی ثبت شده‌اند. وجود ثابت به‌تنهایی نام دقیق handler یا نقش کل تابع را ثابت نمی‌کند.
- یک callback متأخر، 0x203B2B2، صریحاً کد 0xC0000005 را مقایسه و نتیجهٔ ۰/۱ برمی‌گرداند. صرف بررسی access violation نیز اثبات آماده‌سازی صفحه نیست.

مستند عمومی Microsoft توضیح می‌دهد که /GS بررسی cookie را در پردازش/unwind استثنا نیز انجام می‌دهد؛ این مرجع فقط برای معنای عمومی مقایسه است، نه تطبیق دقیق symbol این بیلد:

- https://learn.microsoft.com/en-us/cpp/build/reference/gs-buffer-security-check?view=msvc-170
- https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/security-init-cookie?view=msvc-170

هیچ کد منبع CRT شخص ثالث دانلود یا اجرا نشد.

## تأیید و محدودیت

verify.py با parser تازهٔ مبتنی بر struct، بدون pe_manual/Capstone/Z3، هر ۶۲ جدول، ۷۸ رکورد و ۴۳ callback را از فایل دوباره خواند. مرز بایت‌های ۷۵۷ دستور یکتا از بدنه‌های triage و prefixهای callbackها با GNU objdump مستقل تطبیق یافت. این آزمون صحت پیوند و decode محدود را می‌سنجد، نه تمام معنا یا اجرای runtime. CFG کامل callback مبهم تأیید نشده است؛ فراخوانی‌های غیرمستقیم در handlerهای عمومی نیز کامل حل نشده‌اند.

هیچ بازی یا PE ورودی اجرا نشد؛ attach، تغییر protection، patch، driver یا EXE جدید وجود ندارد. CPU/BIOS serialization و ارسال همچنان اثبات نشده‌اند. main و GUI 0.2 تغییر نکردند.

## قدم دقیق بعد

تحلیل شرط‌های dispatcher و اثرهای حافظهٔ callback 0xC59140 با حفظ متغیربودن globalها. هدف، تعیین ورودی/خروجی و نوشتن واقعی است، نه عبور حدسی از بایت‌هایی که decode نمی‌شوند. اسلات مجازی callback اول، بدون دادهٔ معتبر runtime، فعلاً مقصد ثابت ندارد و نباید برایش آدرس ساختگی انتخاب شود.

## بازتولید

ورودی wow_loader.dll هم‌هش در /data/wlab-inputs؛ اسکریپت‌ها مسیر ثابت /data دارند و در محیط دیگر باید تغییر کنند. تولید triage و prefix به Capstone 5.0.9 نیاز دارد؛ بررسی مستقل فقط Python و GNU objdump می‌خواهد. scopes.py فهرست unwind گام قبل را نیز ورودی می‌گیرد.

```bash
PYTHONPATH=/data/wlab-deps:source python source/triage.py
PYTHONPATH=source python source/scopes.py
PYTHONPATH=/data/wlab-deps:source python source/callbacks.py
python source/verify.py
```

source/custom_filter_cfg.py ثبت تلاش ناقص است؛ اجرای فعلی آن در آدرس مستندشده متوقف می‌شود و خروجی موفق ندارد.
