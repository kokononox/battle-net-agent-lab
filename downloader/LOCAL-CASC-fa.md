# بازاستفادهٔ محتوای محلی CASC — راهنمای توسعه

## نتیجهٔ اجرایی این مرحله

`local_casc.py` اتصال واقعی میان ایندکس‌های محلی، برنامهٔ هدف و تأیید کامل محتوا
است؛ صرفاً شمارش پیشوند یا خواندن هدر نیست. هیچ مسیر نوشتن در بازی ندارد.
روی نصب واقعی کاربر و Windows هنوز اجرا نشده است؛ این بسته درخواست تست کاربر نیست.

- `inventory`: فقط پوشهٔ مشخص `Data/data`، بدون جست‌وجوی بازگشتی دیسک؛ ثبت
  فایل‌ها و همهٔ نسل‌های مشاهده‌شدهٔ `.idx`، نه انتخاب جدیدترین نسل.
- قالب پشتیبانی‌شده: revision 7، بلوک پیوسته، فیلدهای 4/5/9 و segment bits=30.
  checksum هدر و checksum چرخشی کل entryها تأیید می‌شود؛ هر دو روش native
  و Blizzget جداگانه بررسی می‌شوند. قالب ناشناخته تأیید نمی‌شود.
- پیشوند ۹بایتی فقط نامزد می‌سازد؛ تمام EKeyهای هدف با همان پیشوند حفظ می‌شوند.
  اندازهٔ span باید دقیقاً encoded size یا encoded size+30 باشد؛ محدودهٔ آرشیو
  و یکتایی archive ID الزامی است. نام‌های چندگانهٔ یک ID باعث انتخاب حدسی نمی‌شوند.
- ارجاع‌های پوشش‌دهندهٔ wrapper و ارجاع مستقیم همان payload، بعد از تبدیل دقیق
  مختصات به یک نامزد واحد تبدیل می‌شوند. صفر بودن wrapper یا BLTE magic اثبات نیست.
- `verify_batch`: خواندن فقط‌خواندنی بازهٔ محدود و تأیید EKey کامل، checksumهای
  chunk در صورت وجود و CKey کل محتوای decoded. داده اجرا یا منتشر نمی‌شود.
- برخورد پیشوند، دادهٔ ناقص/نامعتبر، mode ناشناخته یا رمزگذاری‌شده، قابل‌بازاستفاده
  حساب نمی‌شود؛ خطای یک نامزد، حکم خرابی کل بازی نیست. نامزد جایگزین بررسی می‌شود.
- هر batch سقف بایت و تعداد دارد. در اتمام بودجه، نامزد بعدی pending می‌ماند.
  checkpoint جدید فایل مستقل است و قبلی بازنویسی نمی‌شود. پس از لغو یا مرگ process،
  از آخرین checkpoint کامل ادامه داده می‌شود؛ batch ناتمام باید دوباره بررسی شود.
- ادامه فقط با همان plan ID، snapshot ID، مجموعهٔ فایل و fingerprint منابع ممکن
  است. تغییر index/archive/shmem یا اضافه/حذف فایل، ادامه را مسدود می‌کند و نیاز به
  inventory تازه دارد. symlink، reparse point و hardlink مشترک پذیرفته نیست.
- کمبود فضا پیش از ساخت inventory/checkpoint بررسی می‌شود. خطای حین نوشتن Lab
  نیز اجازهٔ انتشار checkpoint ناقص نمی‌دهد؛ هیچ دادهٔ منبع بازی بازنویسی نمی‌شود.

## اتصال API توسعه‌ای

ورودی `plan_db` خروجی برنامهٔ هدف قبلی و متعلق به همان Lab است. پوشهٔ بازی باید
از Lab جدا باشد؛ ساخت Lab داخل `Data/data` ممنوع است. مثال زیر راهنمای توسعه است،
نه دستور اجرای تأییدشده برای بازی کاربر:

```python
import local_casc

summary, inventory_db = local_casc.inventory(lab, plan_db, storage_directory)
progress, checkpoint = local_casc.verify_batch(
    lab, plan_db, inventory_db, byte_budget=2 * 1024**3, max_candidates=4096)
# در صورت pending بودن و ثابت ماندن منابع:
progress, next_checkpoint = local_casc.verify_batch(
    lab, plan_db, inventory_db, previous=checkpoint)
report = local_casc.remaining(lab, plan_db, inventory_db, next_checkpoint)
```

بودجه باید حداقل اندازهٔ نامزد بعدی باشد؛ بودجهٔ صفر عمداً فقط checkpoint توقف
می‌سازد. مصرف بودجه فقط خواندن واقعی payload است؛ wrapperها خوانده نمی‌شوند.
کپی checkpointهای قبلی در نسخهٔ فعلی هزینهٔ I/O دارد؛ این طراحی immutable است،
نه وعدهٔ checkpoint با هزینهٔ ثابت در نصب‌های چندمیلیونی.

گزارش `remaining` فقط تعداد و جمع مشروط داده‌های encoded اثبات‌شده را از برنامه
کم می‌کند. دادهٔ decoded قبلی جای representation encoded حساب نمی‌شود. این API
هنوز شواهد cacheهای مستقل قبلی را خودکار با شواهد محلی ادغام نمی‌کند.

## آزمون آفلاین بدون بازی و شبکه

از داخل پوشهٔ کد، با مسیری که وجود ندارد و بیرون از بازی است:

```text
python -B local_casc_demo.py --new-case C:\Temp\WoW-Local-Proof-Demo
```

دمو یک Lab و storage مصنوعی مجزا می‌سازد: سه هدف، دو نسل ایندکس، ارجاع‌های
wrapper/direct، دو محتوای سالم و یک payload معیوب. توقف بودجه، ادامهٔ checkpoint،
رد payload معیوب و عدم تغییر فایل‌های منبع را بررسی می‌کند. این دمو آپدیتر نیست.

## محدودیت‌های مهم و قدم بعدی

- fingerprint شامل dev/inode/size/mtime/nlink و مجموعهٔ فایل‌هاست؛ snapshot اتمیک
  سیستم‌عامل یا قفل روی Battle.net/WoW نیست. در اتصال واقعی باید بازی و updater
  بسته باشند. در برابر برنامهٔ متخاصم با توان بازگرداندن timestamp تضمین نداریم.
  پیش از استفادهٔ نهایی از بازهٔ منبع نیز باید صحت/ثبات دوباره بررسی شود.
- نبود نامزد، تمام‌شدن بررسی نامزدها، یا خطای checksum در یک قالب ناشناخته،
  «مفقود بودن قطعی» نیست. همهٔ دادهٔ آرشیوها خطی جست‌وجو نمی‌شود؛ فایل orphan،
  قالب paged/قدیمی و اطلاعات بیرون از ایندکس‌های پشتیبانی‌شده پوشش قطعی ندارند.
- shmem فقط از نظر تغییر فایل دیده می‌شود؛ active generation حل نشده است.
- آخرین checkpoint سالم معتبر می‌ماند؛ فایل‌های `.part` حاصل از مرگ process
  خودکار import یا موفق تلقی نمی‌شوند. پاکسازی خودکار این orphanها پیاده نیست.
- DBهای inventory/evidence خصوصی‌اند: مسیر محلی، پیشوند و مختصات دارند؛ ارسال
  نشوند. خروجی `remaining` مسیر و کلید محلی ندارد. فایل‌های بازی/PRIVATE را نفرستید.
- سیاست نهایی نصب/زبان، ادغام cacheهای قبلی، آزمون Windows روی storage واقعی،
  دریافت واقعی asset و نویسنده/فعال‌سازی CASC هنوز باید تکمیل/اعتبارسنجی شوند.
  `required_network_download_bytes` همچنان null و `installation_ready` برابر false است.

نتایج سازنده در `LOCAL-CASC-TESTS.json` است. آزمون مقیاس و fixtureها مصنوعی‌اند؛
اتصال به برنامهٔ واقعی کامل با payloadهای عمداً نامعتبر آزموده شده است، نه با
آرشیو بازی کاربر. تلاش دریافت نمونهٔ زنده از CDN به HTTP 403 خورد؛ نتیجه در
`LOCAL-CDN-SAMPLE-ATTEMPT.json` جدا ثبت شده و موفقیت دریافت واقعی ادعا نمی‌شود.

## به‌روزرسانی پس از این مرحله

API محلیِ `remaining` عمداً فقط شواهد CASC را گزارش می‌کند. ادغام cacheهای مستقل
اکنون در `reuse_coordinator.py` انجام شده است؛ راهنما: `REUSE-QUEUE-fa.md`.
همچنین علت 403 تست اولیه، اشتباه harness در نام route_kind بود، نه اثبات انسداد
CDN. با نوع دقیق archive_range و Range صحیح، سه نمونهٔ رسمی دریافت و تأیید شدند.
گزارش اولیه برای تاریخچه حفظ شده و با گزارش اصلاح‌شده تکمیل شده است.
