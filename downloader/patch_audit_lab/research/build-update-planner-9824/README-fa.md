# برنامه‌ریز فقط‌خواندنی آپدیت — مرحلهٔ اول

این مرحله تصمیم‌گیری را از اجرای آپدیت جدا می‌کند. برنامه‌ریز هیچ فایل بازی، Lab، صف دریافت یا وضعیت نصب را تغییر نمی‌دهد. خروجی JSON روی stdout است؛ ذخیرهٔ گزارش فقط با هدایت خروجی به مسیر **جدا از ورودی‌ها** انجام می‌شود.

## چه چیزی اضافه شده؟

- موتور تصمیم برای `reuse`، `patch`، `full_download` و `needs_verification`.
- خواندن خروجی SQLite موجودِ `downloader/content_plan.py`، بدون بازسازی کاتالوگ، دریافت شبکه‌ای یا واردکردن پرچم‌های موفقیت صف به‌عنوان اثبات محلی.
- اتصال به برنامهٔ نمونه با فرمان تازهٔ `build-plan`؛ فرمان قبلی `plan` و مسیر اجرای پچ تغییر نکرده‌اند.
- کنترل تطابق کامل build/CDN و دو کلید Download با متادیتای پین‌شده، نام plan، تعداد رکوردها، کلیدهای تکراری، نوع/اندازه‌ها و تغییر فایل‌های ورودی.
- پچ‌های PA فقط به مقصدهای با CKey و اندازهٔ decoded یکسان متصل می‌شوند؛ وجود رابطهٔ PA به‌تنهایی نشانهٔ داشتن فایل مبدأ نیست.

زیرساخت‌های قدیمی `content_plan`، `update_scope` و `reuse_coordinator` از قبل وجود داشتند. این مرحله جایگزین آن‌ها یا بازنویسی صف نیست. مبدل جدید فقط طرح مقصد را می‌خواند و **هنوز** مجموعهٔ شواهد reuse یا مبدأهای پچِ نصب واقعی را به‌صورت تازه بررسی نمی‌کند. در حالت saved-plan، وضعیت محلی `unknown` می‌ماند و پچ عمومی مجاز نمی‌شود.

## معنای تصمیم‌ها

- `reuse`: هم هویت encoded و هم محتوای decoded همین مقصد تازه بررسی شده‌اند. در مبدل workspace این بررسی از مسیر lookup، خواندن مستقیم تحت قفل آرشیو owned، span و بررسی payload انجام می‌شود؛ نه فقط خواندن یک فلگ موفقیت.
- `patch`: فعلاً فقط رابطهٔ دقیق نمونهٔ پین‌شده، با مبدأ تازه بررسی‌شده، پچ در دسترس و بازتولید دقیق encoding تأییدشده. قابلیت عمومی PA، ترتیب ordinal/chaining و همهٔ ESpecها ادعا نمی‌شود.
- `full_download`: نامزد **مشروط** دریافت کامل، با مسیر ثبت‌شده در طرح قبلی؛ نه اثبات نیاز قطعی به دانلود یا دسترسی فعلی HTTP. ممکن است بررسی محلی بعدی آن را حذف کند.
- `needs_verification`: نگاشت/اثبات/مسیر کافی وجود ندارد. به معنی فایل خراب یا حتماً مفقود نیست. مدرک قبلی هدف، بدون بازخوانی تازه، reuse محسوب نمی‌شود. محتوای decoded نیز جای نمایش encoded را نمی‌گیرد.

برای هر مقصد، هزینهٔ پچِ پشتیبانی‌شده با هزینهٔ کاملِ قابل‌بررسی مقایسه می‌شود؛ در تساوی، مسیر کامل ترجیح دارد. این سیاست یک بهینه‌سازی سراسری برای پچ‌های مشترک نیست. شیء انتقالی مشترک بر اساس نوع و کلید فقط یک بار جمع می‌شود و اختلاف اندازهٔ یک کلید باعث توقف می‌شود.

## حدود عددها

`conditional_payload_bytes` فقط مجموع بدنهٔ اشیای انتخاب‌شده است، نه سربار HTTP، رزرو fallback یا تضمین مقدار شبکه. اگر مورد حل‌نشده وجود داشته باشد، این مقدار `null` است؛ جمع بخش شناخته‌شده جداگانه گزارش می‌شود. `required_network_download_bytes` همواره `null` باقی می‌ماند.

در آزمایش واقعی این مرحله، پچ ۱۱۷بایتی از قبل موجود و تأییدشده است؛ به همین علت هزینهٔ دریافت مشروط آن صفر است. **این عدد، حجم آپدیت کامل بازی نیست.** وجود `target.decoded` داخل Portable نیز به معنی نصب بودن مقصد encoded تلقی نمی‌شود.

## اجرا

از پوشهٔ `downloader/patch_audit_lab` و با Python موجود در محیط آزمایش اجرا کنید. مسیرها باید واقعی، بدون symlink/reparse و جدا از مسیر خروجی باشند؛ در لینوکس برای مسیری مثل `/data` ابتدا مسیر فیزیکی را با `realpath` بگیرید.

```bash
# فضای owned نمونهٔ ساخته‌شده در مرحلهٔ قبلی
python -B retail_sample_updater.py build-plan --workspace /physical/path/SampleWorkspace

# بررسی کامل دوبارهٔ بستهٔ Portable؛ حدود ۲۰۰ مگابایت متادیتا خوانده می‌شود
python -B build_update_plan.py portable --root /physical/path/Portable-Retail-Sample

# طرح ذخیره‌شدهٔ موجود؛ بازی یا آرشیو را اسکن نمی‌کند
python -B build_update_plan.py saved-plan \
  --plan-db /physical/path/Lab/objects/content-plan-UUID.sqlite \
  --audit-dir /physical/path/Portable-Retail-Sample/pinned_metadata \
  --object-limit 4096 --preview-limit 128
```

حالت saved-plan به‌صورت پیش‌فرض فقط ۴۰۹۶ مقصد اول به ترتیب EKey را ارزیابی می‌کند؛ `evaluated_all_saved_rows` و تعداد کل کاتالوگ در scope مشخص‌اند. سقف صریح ۱۰۰هزار مقصد است و فقط تعداد محدودی جزئیات چاپ می‌شود. کنترل تعداد/کلید تکراری می‌تواند کل جدول متادیتا را بخواند؛ محدودیت فوق مربوط به تصمیم‌هاست، نه تمام کار SQL. SQL ورودی فقط‌خواندنی، با `trusted_schema=OFF` است؛ پایگاه WAL، journal باز، view به‌جای جدول و فایل‌های لینک‌شده پذیرفته نمی‌شوند.

مدل اعتماد: ورودی محلی معتبر و فایل‌های پایدار در برابر تغییر تصادفی؛ این ابزار sandbox امنیتی برای SQLite خصمانه یا نویسندهٔ مهاجم نیست. API داخلی وضعیت‌های اثبات را از مبدل‌ها می‌گیرد؛ هیچ فایل JSON دلخواهی برای اعلام `verified=true` وارد نمی‌شود. `apply_authorized=false` همیشه برقرار است.

## شواهد این اجرا

- ۴۴ تست تازه: تصمیم‌ها، مدرک ناکافی، کلید/اندازهٔ متعارض، ورودی SQLite مصنوعی، تطابق binding، محدودیت پوشش، رد sidecar/link و ثابت‌ماندن فایل‌ها.
- اجرای مجدد ۱۴۴ تست مرحلهٔ قبل؛ مجموع ۱۸۸ تست، بدون خطا/شکست/skip.
- بررسی دوبارهٔ Portable واقعی و دو وضعیت واقعیِ فضای **آزمایشی owned**: پیش از آپدیت `patch`؛ پس از آپدیت `reuse` با خواندن تازهٔ مقصد.
- تست مبدل saved-plan با fixtureهای SQLite مصنوعی انجام شده است؛ طرح کامل واقعیِ کاربر و Download manifest کامل در این محیط موجود نیست. این تفاوت در `TEST-RESULTS.json` ثبت شده است.
- مجموعهٔ تاریخی ۸۱۴تستی، ویندوز، قطع برق، چند payload واقعی و نصب واقعی بازی در این مرحله آزمایش نشده‌اند.

برای بازتولید، `PYTHONPATH` را روی مسیر فیزیکی پوشهٔ lab بگذارید و `run_experiments.py --help` را ببینید. به templateهای owned و چهار oracle مرحلهٔ قبل نیاز دارد. خروجی جدید را خارج از تمام ورودی‌ها بدهید.

## قدم باقی‌مانده

اتصال این لایه به inventory/شواهد محلی معتبرِ نصب کاربر و انتخاب پروفایل از متادیتای واقعی، بازخوانی محدود مبدأهای لازم، سپس پوشش چند مقصد واقعی و fallback دریافت. تشخیص build نصب‌شده، سیاست کامل انتخاب فایل‌های بازی، کلوزر نصب، دریافت شبکه و فعال‌سازی نصب هنوز در این برنامه‌ریز پیاده/تأیید نشده‌اند.
