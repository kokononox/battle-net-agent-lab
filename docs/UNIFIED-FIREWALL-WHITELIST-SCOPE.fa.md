# تصمیم دامنهٔ وایت‌لیست — کل سیستم، همهٔ برنامه‌ها

## انتخاب صریح کاربر

کاربر گزینهٔ «همهٔ برنامه‌های سیستم بتوانند به مقصدهای وایت‌لیست وصل شوند» را انتخاب کرد، نه محدودکردن به executableهای نصاب. دلیل: مقصدها بعداً قابل حذف/اضافه باشند؛ مرورگر بتواند سایت مجاز را باز کند و برنامه‌های دیگر هم به مقصدهای مجاز دسترسی داشته باشند. هدف اولیهٔ بتل‌نت نباید به یک executable allowlist اجباری تبدیل شود. این تصمیم مربوط به دامنهٔ مجوز است، نه اجازهٔ Apply روی سیستم.

## قرارداد طراحی

- دامنه whole_system؛ تطبیق برنامه Any برای دادهٔ مجاز، نه انتخاب مسیر exe یا فرض ارث‌بری child process.
- مجوز داده حاصل تطبیق مقصد/پروتکل/پورت صریح و binding تازهٔ معتبر SSTP است؛ برنامه‌ای خاص استثنای اینترنت آزاد ندارد. سایر مقصدها و fallback داده روی کارت فیزیکی مجاز به طراحی نیستند.
- حمل خود SSTP از دادهٔ همهٔ برنامه‌ها جداست: endpoint بازبینی‌شده، سرویس/هویت صحیح، TCP443 دقیق و بازاعتبارسنجی؛ «همهٔ برنامه‌ها» نباید حمل VPN را به TCP443 عمومی تبدیل کند.
- در disconnected/connecting/identity-unknown، دادهٔ وایت‌لیست مجوز خودکار نمی‌گیرد؛ هدف حفظ قابلیت اتصال حمل ازپیش‌مجاز است، ولی DNS/certificate/underlay/reconnect هنوز qualification ندارند.
- افزودن/حذف مقصد باید نسل جدید پلن بسازد. ذخیره/ویرایش به معنی Apply نیست؛ stale plan، binding یا baseline نامعتبر قابل اعمال نیست. حذف مقصد نباید با یک allow گستردهٔ قبلی بی‌اثر شود؛ بازبینی قواعد Allow موجود و اتصال‌های برقرار جزو نیازهای اجرای آینده‌اند، هنوز پیاده/اثبات نشده‌اند.
- blockهای دیگر ویندوز/مدیریت دستگاه/TLS/شبکه ممکن است مقصد مجاز را همچنان مسدود کنند؛ allowlist شرط دسترسی است، نه تضمین لودشدن سایت یا اجبار Override قواعد امنیتی.

## مرز نام دامنه و IP

خواست کاربر شامل سایت در مرورگر است. از آن نباید ادعای پشتیبانی آمادهٔ domain enforcement ساخت: IPهای DNS/CDN متغیرند، سایت ممکن است subresource/auth/redirect روی مقصدهای دیگر لازم داشته باشد و چند دامنه روی یک IP مشترک باشند. IP/port allowlisting نمی‌تواند نام HTTPS یا محتوای آن را به‌طور اختصاصی محدود کند و مانع ارسال fingerprint در یک مقصد مجاز نمی‌شود. resolution محدود، refresh، rollback، consent مقصدهای جدید و جلوگیری از broad fallback هنوز کار اجرایی می‌خواهند. wildcard/CIDR/Any-port نباید خودکار از یک نام سایت تولید شوند.

## مسیر ادامه و وضعیت

سازندهٔ global destination policy و draft حمل SSTP موجودند؛ نباید صرفاً برای تغییر نام ابزار دوباره ساخته شوند. compose پلن غیرقابل‌اجرا با همین دامنه و فهرست قابل‌ویرایش، مبنای ثبت/بازخوان‌شده و گیت‌های صریح، مرحلهٔ بعد است. هنوز native Apply/recovery/rule-binding/reconnect یا site-level filtering ساخته/qualified نشده‌اند. علت Block تاریخی مجهول است؛ baseline صریح Block باید همان Block بماند و انتخاب دامنه آن را به Allow تبدیل نمی‌کند. آماده‌بودن Windows storage/preparation/reopen با آماده‌بودن فایروال یکسان نیست.

هیچ فایل اجرایی جدیدی در این تصمیم ساخته نشده و هیچ تست تازه یا تغییر Windows انجام نشده است. کاربر فعلاً اقدام ندارد؛ آماده‌سازی یا بازخوان موفق تکرار نشود، ژورنال محافظت‌شده حذف/اصلاح نشود و شبکه/SSTP همان وضعیت بماند. ready_for_apply=false و no_leak_certified=false.
