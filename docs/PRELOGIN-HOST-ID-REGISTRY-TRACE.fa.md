# UserUUID: ساختن و خواندن پیش از لاگین، با شاهد مستقیم API

## نتیجهٔ a11

در runner تازه و بدون حساب، این زنجیره مشاهده شد:

1. **قبل از اجرای هدف:** مقدار `UserUUID` در کلید زیر وجود نداشت.
2. **startup اول:** در فرایند Setup دارای pin، `RegSetValueExW` با نتیجهٔ موفق و مقدار UUID ثبت شد؛ این مقدار دقیقاً با `host_id` پیام مشخصات همان مرحله برابر بود.
3. **در هر دو startup:** فرایند Agent دارای pin با `RegQueryValueExW` مقدار REG_SZ معتبر و برابر با `host_id` پیام مشخصات آن مرحله را خواند.
4. **پس از اجرای مجدد فرایندها:** host_id همان بود و رجیستری همچنان مقدار معتبر داشت. هر دو پیام مشخصات تا ارسال موفق سوکت و ciphertext ضبط‌شدهٔ محلی NIC پیوند خوردند.

```text
HKEY_CURRENT_USER\Software\Blizzard Entertainment\Blizzard Error
Value name: UserUUID
```

شناسهٔ واقعی و hash آن منتشر نشده‌اند.

**این دیگر صرفاً «پیداشدن یک رشته در رجیستری» نیست:** snapshot پیش از هدف و مشاهدهٔ API، نوشتن در startup و خواندن توسط Agent را مستقیماً نشان می‌دهند. با این حال، بازهٔ بررسی startup نصاب است؛ بدون کلیک Install، تکمیل نصب محصول یا ورود به حساب. «ایجاد در این بازه» را به «اولین ایجاد در تمام عمر دستگاه» تعمیم نمی‌دهیم.

## نقش فرایندها و تعداد callbackها

| مرحله | callback نوشتن موفق Setup با مقدار برابر | callback خواندن موفق Setup با مقدار برابر | callback خواندن موفق Agent با مقدار برابر |
| --- | --- | --- | --- |
| اول | 2 | 6 | 2 |
| دوم | 0 | 8 | 2 |

این‌ها **شمار callback ابزار هستند، نه تعداد مستقل عملیات منطقی**: APIها ممکن است یکدیگر را صدا بزنند یا به پیاده‌سازی دیگری forward شوند؛ در این آزمایش dedup فراخوانی‌های تو در تو نداریم. برای نتیجهٔ وجود نوشتن/خواندن موفق، شمار دقیق لازم نیست. بعضی queryهای موفق Agent فقط پرسش اندازه بودند و UUID معتبر نداشتند؛ آن‌ها شاهد خواندن مقدار محسوب نشدند.

## کنترل‌های اعتبار

- 28 آزمون Python و 34 کنترل اجرای کد واقعی hook با mock حافظهٔ 32/64 بیتی پاس شدند.
- پیش از هدف، fixture بومی مستقل x64 و x86 با مقدار مصنوعی، خواندن A/W، RegGetValueW، نوشتن W و منفی size-only را با نتیجهٔ موفق کنترل کرد. fixture فقط زیرکلید مخصوص آزمایش خود را ساخت/پاک کرد، نه کلید Blizzard.
- native gate شبکهٔ پیشین نیز پاس شد. فرایندهای مرحلهٔ اول/دوم به‌ترتیب 3 و 4 بودند و همه پیش از resume ابزارگذاری شدند.
- خطا و limit مشاهده‌گر رجیستری صفر؛ خطا، افت رویداد و خطای مهلک collector شبکه صفر.
- observer آرگومان، مقدار برگشتی یا buffer هدف را تغییر نداد. مقدارهای رجیستری و پیام‌ها فقط داخل RAM آزمایش مقایسه شدند.

## چه چیزی هنوز اثبات نشده؟

- **زنجیرهٔ علّی کامل provider:** خواندن API توسط Agent ثابت است؛ اما اینکه همان فراخوانی مستقیماً کدام شاخه/تخصیص داخلی provider را تغذیه کرده، هنوز trace نشده است. `provider_assignment_causality_proven=false` باقی می‌ماند.
- تمام `caller_rva`های هدف null شدند؛ بنابراین از این اجرا آدرس داخلی فراخوانی یا stack قابل‌اتکا نداریم. آدرس‌های بررسی ایستا را جای trace زنده نمی‌گذاریم.
- ساعت/ترتیب مشترک بین کانال رجیستری و شبکه صادر نشده است؛ برای تمام eventها ترتیب زمانی دقیق یا جریان دادهٔ علّی ادعا نداریم.
- هنوز نمی‌گوییم شناسه مخصوص «هر نصب» است، از سخت‌افزار مشتق می‌شود، هویت واقعی شخص است، به حساب وصل است یا بین ماشین‌ها یکتا است. محدودهٔ کلید HKCU پروفایل کاربر ویندوز است.
- reboot ویندوز، حذف/نصب مجدد و انتقال فایل WoW آزمایش نشده‌اند. این گزارش دربارهٔ watermark فایل بازی نیست.
- دریافت کاربردی یا ذخیرهٔ سرور از capture محلی نتیجه نمی‌شود. هدف سازمانی یا ضرورت این رفتار هم از trace به دست نمی‌آید.

نام کلید `Blizzard Error` اثبات استفادهٔ صرفاً کرش نیست: همان مقدار در host_id پیام عادی StartAgent پیش از حساب دیده شد.
