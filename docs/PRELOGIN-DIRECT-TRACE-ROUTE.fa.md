# تغییر مسیر: ردیابی مستقیم Setup/Agent، نه نصب مهمان

به درخواست کاربر، مسیر نصب Windows داخل QEMU/UEFI کنار گذاشته شد. workflow مهمان با یک job صرفاً ثبت توقف جایگزین شد؛ هیچ VM، ابزار هدف، NIC یا دسترسی از راه دوری از این job اجرا نمی‌شود. concurrency همان گروه قبلی با cancel-in-progress=true است تا درخواست لغو اجرای قبلی ارسال شود. انتشار رسید pause به‌تنهایی اثبات وضعیت terminal اجرای قبلی نیست؛ آن ادعا جدا تأیید می‌خواهد. source e4 برابر c4558413d6068bb9ffe4f081d12120493843fa51 و run برابر 40169407184 بود و آخرین وضعیت خوانده‌شدهٔ آن dispatched بود؛ نبود خروجی نهایی موفقیت یا شکست نیست.

## چرا مسیر مستقیم؟

a11 قبلاً با Windows runner آماده موفق بود و API نوشتن/خواندن UserUUID و برابری خصوصی با host_id خروجی دو startup را نشان داد. گلوگاه باقی‌مانده در این خط، زنجیرهٔ داخلی provider است، نه اجرای سیستم‌عامل. هیچ شاهد جدیدی از مسیر مهمان به نتیجهٔ Q1 اضافه نمی‌کنیم.

## هدف بعدی قابل اندازه‌گیری

1. مشاهده‌گر رجیستری فعلی تنها returnAddress را با محدودهٔ mainModule می‌سنجد؛ null می‌تواند ناشی از wrapper/forwarder باشد و نبود فراخوانِ مرتبط را ثابت نمی‌کند.
2. برای آزمایش جدید، backtrace دقیق و محدود لازم است؛ فقط frameهایی که با محدودهٔ ماژول هدفِ pinشده تطبیق دارند به RVA تبدیل شوند. مسیر ماژول، آدرس مطلق، مقدار UUID و hash آن منتشر نشود. backtrace حدسی جایگزین شاهد معتبر نشود.
3. ابتدا fixture بومی کنترل‌شدهٔ x86/x64 و منفیِ unresolved؛ سپس startup محدود Setup/Agent بدون حساب یا کلیک Install. mock فقط قرارداد ابزار را می‌سنجد و شاهد رفتار هدف نیست.
4. stack/RVA به‌تنهایی جریان دادهٔ علّی را ثابت نمی‌کند. نسبت‌دادن خواندن رجیستری به assignment provider باید جداگانه با trace متصل به همان اجرا و پیام تأیید شود؛ تا آن زمان provider_assignment_causality_proven=false باقی بماند.

این سند برنامهٔ مسیر جدید است؛ اجرای a12 یا اثبات تازه‌ای را اعلام نمی‌کند. reboot واقعی ویندوز و «شناسهٔ مخصوص هر نصب» همچنان تأییدنشده است. e1/e2/e3 در firmware/monitor متوقف شدند؛ c2/d6 صرفاً CPU آزمایشی/آماده‌سازی paused را ثابت کرده‌اند. Q2 دربارهٔ فایل‌های WoW در صف باقی است.
