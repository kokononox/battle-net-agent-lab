# تحویل وضعیت جلسهٔ patch-audit

## جدیدترین مرحله: توابع اصلی visibility، نه فقط مدل — ۵۲۰ آزمون

چهار تابع اصلی Agent 9824 (caller انتشار header، reader wrapper، writer orchestrator و reader refresh)، مجموع ۸۵۷ بایت، با VA و بایت‌های اصلی در ELF محدود Linux i386 اجرا شدند. مرز helperها صریح است: ۱۷ مقصد mock، شامل عملیات فایل/bind/serializer/logging و frame/SEH پژوهشی؛ ۳۰ callsite بررسی شدند. Agent.exe و Windows API اجرا نشدند.

**یافتهٔ مهم:** در مسیر nonthrowing با open موفق و bind خطادار، reader cache را پیش از bind جلو می‌برد، خطا را log می‌کند ولی EBX صفر را برمی‌گرداند؛ فراخوانی دوم به‌علت برابری cache/header bind را تکرار نمی‌کند. writer در bind خطادار کد خطا می‌دهد و header را قدیمی نگه می‌دارد، اما cache آن هم جلو رفته است. این رفتار محدود، اثبات وقوع خطا در نسخهٔ نصب‌شده یا نبود handling در لایه‌های بالاتر نیست. خطای ۷۳ فقط token مصنوعی است.

۱٬۴۴۰ بردار، همهٔ ۱۶ باکت، ۳ نوع فراخوانی، ۶ mode و ۵ رابطهٔ unsigned sequence با مدل مطابق بودند؛ ۱۵ سناریوی صریح ثبت شد. **۵۲۰ آزمون، صفر failure/error/skip**. نمونهٔ واقعی تک‌آبجکتی مرحلهٔ قبل هم فقط‌خواندنی دوباره با native EKey/CKey تأیید شد و فایل‌هایش تغییر نکردند. [گزارش و رسیدها](../downloader/patch_audit_lab/research/sequence-visibility-9824/README-fa.md).

**اثر طراحی:** return صفر و cache==header شرط کافی سلامت نیست. گیت مستقل bind/readback را نگه می‌داریم؛ چرخهٔ قبلی از قبل همین گیت را داشت. هیچ reset/recovery واقعی Agent در این مرحله پیاده نشده؛ قفل، mapping، durability، SEH ویندوز و activation کامل همچنان خارج از اثبات‌اند. بازی، Lab، Portable و Release دست‌نخورده‌اند.

گام بعد بررسی helper واقعی bind در `0x72b84f` و handling لایهٔ بالاتر، سپس آزمایش visibility/قفل در کپی Windows جداست؛ writer نصب اصلی هنوز آماده نیست.

۹ خروج عمدی subprocess با `os._exit(91)` پیش/پس از نقاط مشخص publication آزمایش شد؛ همه resume شدند و source/prefix اولیه دست‌نخورده ماند. reader پیش از control publication هدف را نمی‌دید؛ وجود نام index جدیدتر به‌تنهایی کافی نبود. bind ناموفق control را قدیمی نگه داشت؛ retry موفق شد. اجرای دوبارهٔ حالت تکمیل هیچ فایلی را تغییر نداد. suite کامل: **۴۹۰ تست؛ صفر failure/error/skip**.

**مرز شاهد:** journal اختصاصی پژوهش + UUID فضای کاری + `flock`؛ انتشار index با Linux `renameat2(RENAME_NOREPLACE)` و تعویض کل control پژوهشی. این اجرای MoveFileExW یا store DWORD خود Agent نیست، قطع برق/تمام crashها را اثبات نمی‌کند و به نصب Windows، profile کامل یا `.build.info` وصل نشده است. source CKey مشتق‌شده است، target CKey از متادیتای مستقل. هویت نام/مسیر همچنان مصنوعی LAB-PC است. [گزارش، کد و رسیدها](../downloader/patch_audit_lab/research/retail-update-cycle/README-fa.md).

بازی، Lab، fixture و assetهای Release تغییر نکردند؛ اسکن/دانلود payload تکرار نشد. این اولین چرخهٔ موفق یک نمونه است، نه آپدیتر عمومی یا نصب قابل‌اجرا. گام بعد قرارداد واقعی control/visibility و activation کامل در کپی Windows جداست؛ فعال‌کردن صرف با `.build.info` مجاز نیست.

## جدیدترین مرحله: نام رایانه + مسیر تا seed — ۴۵۳ آزمون

**نوع شاهد جدید:** ۷ تابع خالص اصلی، مجموعاً ۲۵۰۱ بایت، از باینری ثابت استخراج و در ELF کوچک Linux i386 اجرا شدند. normalizer، MD5 و ۱۶ full key با مدل تطبیق داده شدند. خود Agent.exe، loader PE و APIهای Windows اجرا نشدند. helperهای memcpy/memset جایگزین‌اند؛ نام رایانه و مسیرها فقط مثال مصنوعی‌اند. کل بایت‌های fragment در ELF نهایی هم hash-check شدند؛ باینری‌ها/fragmentها منتشر نمی‌شوند.

**۴۵۳ تست؛ صفر failure/error/skip**. آزمایش جدا: ۹ حالت wrapper، ۱۰۲۴ بردار خام deterministic و ۱۵ بردار مرزی MD5؛ ۱۰ ورودی خارج از سیاست مدل و ۴ ورودی نامعتبر harness رد شدند. نمونهٔ واقعی Retail با seed مشتق‌شده از مثال مصنوعی به prefix/index رفت و native دوباره EKey/CKey را خواند. [مدارک و اجرا](../downloader/patch_audit_lab/research/name-seed-9824/README-fa.md).

مرز باقی‌مانده: ASCII محدود و ورودی صریح؛ Unicode، خطای API، cwd/name واقعی Windows، اتصال به نصب کاربر و publication/activation واقعی اثبات نشده‌اند. بازی، Lab، fixture اصلی، Release و build.info تغییر نکردند. گام بعد تکمیل همین edge caseها یا قرارداد control/publication در fixture جدا است؛ writer نصب واقعی هنوز مجاز/آماده نیست.

## هدف و قواعد ثابت

هدف فعلی کاربر ساخت به‌روزرسان مستقل فایل‌های WoW Retail بدون تکیه بر رابط Battle.net است؛ هدف تاریخی تحقیق تله‌متری جدا و هنوز اثبات‌نشده است. نصب اصلی 12.1.0.69933 و هدف ثابت آزمایش 12.1.5.70391، wow/eu، Windows/x86_64/enUS است. این هدف به معنی آخرین نسخهٔ آنلاینِ امروز نیست.

Lab اصلی، صف‌ها/checkpointها، `.build.info`، `WTF`، `Interface` و `Screenshots` را حفظ کنید. هیچ تکرار prepare متادیتا، اسکن کامل حدود ۱.۵ میلیون payload یا دانلود گسترده درخواست نشده است. «unsupported» به معنی corruption نیست. فایل‌های خارج inventory هدف هم لزوماً روی دیسک غایب نیستند.

## مسیر این جلسه و اصلاحات

1. خطاهای `target_binding_conflict` و `plan_id_conflict` با بررسی binding و شواهد حل شدند؛ حذف Lab یا نادیده‌گرفتن کلی اختلاف‌ها راه‌حل نبود. دو CDN config متفاوت فقط زیر شرط دقیق سایر bindingها پذیرفته شدند؛ معادل‌بودن عمومی routing اثبات نشده است.
2. Agent 2.41.1.9824 به‌صورت ایستا تحلیل شد؛ برنامه در محیط Linux اجرا نشد. SHA256 فایل exe برابر `b422e8d4f0fe0cbcb2d106b455aa44d78eb3a4e173340f05e6cadac5091571b5` است. ordinal گزینه‌ها نباید به عنوان نوع patch تعبیر شود.
3. source واقعی از یک بازهٔ ۱۵۸بایتی تأیید شد. patch موردنیاز ۱۱۷بایت است؛ پس از lookup در indexهای patcharchive، range دقیق دریافت و hash آن تأیید شد. fallback شبکه حدس آزاد یا دانلود کامل archive نبود.
4. فایل portable کاربر به‌صورت whitelist بررسی و بدون اجرای کد اعتمادنشده به آزمایش وارد شد. ابتدا parser ما به علت سقف داخلی 8MiB/250000 روی ESpec شکست خورد؛ این شکست خودِ Encoding را خراب نشان نمی‌داد. پس از hash کامل، سقف محدود به 16MiB/500000 و حداکثر recipe منتخب 4096 اصلاح شد.
5. بازسازی واقعی decoded و encoded دقیق گذشت. سپس مدل CASC ساختگی و تراکنش/recovery ساخته و با مرجع native و قطع پردازش آزمایش شد.

## محل توقف و گام بعد

از نقشهٔ اولیه جلوتر رفتیم: mapping فایل و انتقال pointer، constructorهای protocol 4/5، اندازه/offset بخش داده و ۱۶ sequence در header، و helper sync→rename با import واقعی و flags=0 بررسی شدند. خروجی قابل‌بازتولید در `AGENT-ACTIVATION-STATIC.json` است. parser فقط‌خواندنی صرفاً روی fixture ساختگی آزموده شده است؛ shmem واقعی کاربر در دسترس نیست. قرارداد payload، publication سراسری و writer `.build.info` هنوز کامل نیست. وجود رشته یا ارجاع literal، اجرای موفق مسیر یا ترتیب سراسری commit را ثابت نمی‌کند. CascLib برای خواندن آخرین نسخهٔ هر bucket را از نام فایل برمی‌گزیند؛ این رفتار به معنی قرارداد یکسانِ Agent/shmem نیست.

گام بعد: ادامهٔ disassembly محدود، مشخص‌کردن دادهٔ واقعی ورودی shmem و رابطهٔ sequenceها، سپس طراحی validator فقط‌خواندنی با ورودی محدود و binding صریح نصب/هدف. پیش از شواهد کافی نباید writer واقعی یا سیاست فعال‌سازی حدس زده شود.
