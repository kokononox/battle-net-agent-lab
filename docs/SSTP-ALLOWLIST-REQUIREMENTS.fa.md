# دامنهٔ قطعی — Allowlist همراه کیل‌سوییچ SSTP، اجرا و خروج

## نتیجهٔ آخرین شفاف‌سازی کاربر
آخرین توضیح کاربر مبناست: تنظیمات Windows طوری تغییر کند که **فقط آدرس‌های داخل Allowlist، فقط از VPN** عبور کنند و ویژگی کیل‌سوییچ حفظ شود. این دیگر انتخاب بازِ A/B نیست؛ حالت صرفاً «همه ترافیک از VPN به همراه denylist BAT۶» هدف نهایی نیست. بازآزمایی اکتشافی مقصدهای قبلی از صفر لازم نیست. نمونهٔ اولیه فهرست مجاز level3.blizzard.com است؛ نه بازکردن ۲۴ نامِ مسدودِ BAT۶.

### رفتار مورد انتظار
1. دامنه کل Windows است. پروفایل SSTP فعالِ یکتا اولویت دارد؛ در نبود اتصال، موجودِ یکتا و در حالت چند پروفایل غیرمتصل، holand انتخاب ترجیحی است اگر یکتا باشد. چند اتصال فعال یا دو scope هم‌نام بدون انتخاب صریح، خطا و توقف است، نه Select-First. نام rus در فایل اتصال ارسالی انتخاب خودکار نیست.
2. اتصال VPN فعلاً دستی است؛ برنامه خودش VPN را Connect/Disconnect نمی‌کند.
3. مقصدهای خارج Allowlist بسته‌اند حتی وقتی VPN وصل است. مقصدهای عادی داخل فهرست هم فقط داخل تونل منتخب مجازند. قطع VPN یا binding نامعلوم/تغییریافته نباید به مسیر عادی fallback بدهد. LAN عادی بسته است.
4. **Enable: اعمال تنظیمات پایدار و خروج. Disable: بازیابی فقط تغییرات خودش و خروج.** کاربر تأکید کرد بازماندن برنامه قابل‌قبول نیست. هیچ monitor، سرویس/فرایند اختصاصی دائمی یا task دوره‌ای نباید برای enforcement لازم باشد؛ خود Windows قواعد را اجرا می‌کند.
5. بدون انقضا؛ محدودیت بعد reboot باقی بماند. task/انقضای هفت‌دقیقه‌ای helper قبلی فقط fixture CI بود و به محصول منتقل نمی‌شود. باقی‌ماندن قواعد باید از قابل‌اعتمادماندن binding بعد reboot تفکیک و تست شود؛ در ابهام، fail-closed و Refresh صریح، نه Allow باز.
6. config قابل افزودن/حذف مقصد باشد. Disable config را پاک نکند و نباید کل firewall را reset یا Allow کند. مدیریت فهرست و تغییر hosts از بازیابی firewall جدا هستند. تغییرات موجود BAT۶/۹۹ و entryهای نامرتبط بدون backup و کنترل تعارض بازنویسی نشوند.

## استثناهای ضروری و محدودیت‌های صریح
- خود SSTP برای تشکیل تونل به ارتباط محدود با سرور VPN نیاز دارد. این یک استثنای transport مشخص است، نه مجوز برنامه‌ها به اینترنت مستقیم. service/program، مقصد، پورت و binding واقعی هنوز باید qualification شوند.
- DNS عادی بیرون تونل در طرح باز نیست؛ resolver لازم فقط به مقصدهای مشخص داخل تونل و با قید مناسب مجاز شود. bootstrap و CRL/OCSP ناسازگار باید باعث توقف شوند؛ اعتبارسنجی TLS خاموش یا دسترسی عمومی باز نشود.
- دامنه باید به snapshot IP تبدیل شود. بدون برنامه دائمی، تغییر DNS/CDN ممکن است نیازمند Refresh صریح باشد؛ IP جدید پیش از refresh بسته بماند. IP مشترک بین چند hostname با firewall IP به‌تنهایی قابل تفکیک نیست. نبود تله‌متری در مقصد مجاز، پاکی محتوا و fingerprint فایل تضمین نمی‌شوند.
- «هیچ نشتی» معیار پذیرش است، نه ادعای موفقیت فعلی. DNS/IPv6، قطع و reconnect، نام/شناسه رابط، boot، تغییر شبکه، فرآیندهای دیگر، Allowهای قدیمی و GPO/قواعد غیرقابل‌کنترل باید سنجیده شوند. صرف Set default outbound=Block یا Allow همه RemoteAccess این هدف را تأمین نمی‌کند.
- افزودن مقصدِ قبلاً مسدودشده در hosts می‌تواند با legacy BAT۶ تعارض داشته باشد. مهاجرت باید صریح و محدود به دادهٔ مدیریت‌شده باشد؛ هستهٔ فعلی هیچ hosts را حذف یا تغییر نمی‌دهد.

## مرز فعلی پیاده‌سازی
[هسته P1](SSTP-ALLOWLIST-POLICY-P1.fa.md) فقط config و policy-plan را پیاده کرده و ۳۵ آزمون مصنوعی روی PowerShell Windows پاس شده است. backend اجرایی Enable/Disable، journal محصول، binding واقعی SSTP و enforcement هنوز ساخته/تأیید نشده‌اند. ready_for_user_apply=false؛ هیچ بستهٔ فعال‌سازی به کاربر تحویل نشده و دستگاه او تغییر نکرده است.

طرح پیشنهادی backend: journal خصوصی پیش از mutation، transition guard بسته برای جلوگیری از پنجره باز میان چند فرمان، مدیریت Allowهای قبلی با کنترل هویت/تعارض، ساخت قواعد محدود و readback پیش از برداشتن guard؛ Disable نیز زیر guard فقط journal خودش را برگرداند. این طرح هنوز کد اجراییِ تأییدشده نیست. خرابی نباید EmergencyResetِ Allow عمومی بسازد.
