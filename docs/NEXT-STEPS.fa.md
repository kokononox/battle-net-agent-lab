# ادامهٔ کار بدون تکرار بی‌هدف

## اکنون: بدون اقدام تازه روی Lab کاربر

1. گزارش schema2 probe فقط‌خواندنی را با source_commit/run_id بخوانید. اگر هنوز گزارش schema1 قدیمی است، اجرای تازه را موفق فرض نکنید.
2. session/window/labelهای مجاز را بررسی کنید: آیا session قابل‌مشاهده است؟ پنجرهٔ زبان/توافق‌نامه واقعاً دیده شد؟ unknown/custom UI را به یک پیام خیالی تبدیل نکنید.
3. اگر محدودیت hosted desktop مانع است، همان‌جا توقف و محدودیت ثبت شود. کلیک، silent/EULA flag یا ورود حساب خودکار اضافه نشود. هدف این run رفع یک ابهام است، نه loop نصب.

## دانلودر: کار مهندسی بعدی

- از خروجی scope فعلی، نصب/فایل‌های اجرایی/config و patch metadata را به‌صورت مستند جدا کنید؛ selection محافظه‌کارانه به صف فعال نصب تبدیل نشده است.
- ابتدا closure/policy و تفاوت download/patch/write/temporary bytes را روشن کنید. شبکهٔ لازم فقط بعد از مسیر دقیق asset/patch و اثبات بازاستفاده قابل‌محاسبه است.
- repair/download را روی Lab آزمایشی با منابع عمداً سالم/خراب/قطع‌شده و rollback بررسی کنید؛ source واقعی کاربر فقط‌خواندنی بماند.
- CASC writer/فعال‌سازی باید پروژهٔ جدا و دارای journal، crash recovery، اعتبارسنجی قبل/بعد و محیط Windows دورریختنی باشد. تا آن زمان installation_ready=false.
- به‌جای full verify در هر آپدیت، از metadata delta و شواهد معتبر قابل‌ارث‌بری استفاده شود؛ اگر منبع تغییر کرده، اثبات قدیمی خودبه‌خود معتبر نیست. سرعت Battle.net را بدون شناخت patch policy با روش اسکن کامل برابر نگیرید.

## بازگشت به هدف اصلی

پس از رفع پیش‌نیاز بازی، مراحل pre-login، login و in-world واقعی تفکیک شوند. معیار موفقیت: «فیلد قابل‌مشاهده → درخواست مشخص → مقصد مشخص → زمان/مرحله و منشأ روشن». SNI یا رشتهٔ باینری معیار کافی نیست.

کلید TLS، token، cookie، شناسهٔ حساب و body حساس منتشر نشود. دادهٔ قابل‌اشتراک تنها حداقل لازم و redacted باشد. روش‌های قبلاً بی‌نتیجه مثل صرفاً تنظیم SSLKEYLOGFILE یا تکرار hook بدون تشخیص جدید دوباره تحمیل نشود. هیچ تغییر anti-cheat یا bypass حفاظت بازی برای این هدف توجیه نشده است.

## قانون تحویل جلسهٔ بعد

ابتدا SESSION-HANDOFF، سپس current-state، evidence و راهنمای ماژول مرتبط؛ بعد ابزار اجرا شود. نسخهٔ ۳۴۸تستی قدیمی را به‌جای TagFix بازیابی نکنید. قبل از هر تغییر، `downloader/PACKAGE-MANIFEST.json` و SHAها را کنترل کنید. پس از تغییر واقعی، تست و provenance تازه ثبت شود؛ context قدیمی را با واقعیت جدید overwrite بی‌ردپا نکنید.
