# G66 — بررسی هدفمند اطلاعات خروجی، نه تکرار آزمون نصب

پرسش: آیا داده‌های خروجی دو مقصد فقط لازم برای دانلود هستند یا اطلاعات دستگاه/کاربر نیز حمل می‌کنند؟ این مرحله دو ابهام باقی‌ماندهٔ G65 را بررسی می‌کند و به‌تنهایی نبود فینگرپرینت را ثابت نمی‌کند.

- ساختار User-Agent به واژه‌های ثابت محدود، بخش‌های شبیه نسخه، جداکننده‌ها و بخش‌های نامعلوم تجزیه می‌شود. مقادیر ناشناخته و حتی شماره‌های نسخه صادر نمی‌شوند. شبیه نسخه‌بودن مجوز ارسال نیست.
- query با نام seqn در حافظه با مرجع عمومی آماده‌شده و شمارهٔ توالی پاسخ‌های کامل 200 از جدول شناخته‌شده در همان context TLS مقایسه می‌شود. تطابق همان context معادل انتساب دقیق درخواست/پاسخ یا اثبات معنا نیست.
- صفر فقط «نامزد sentinel با معنای اثبات‌نشده» است. عدم تطابق هم اثبات شناسهٔ دستگاه نیست.
- parser پاسخ HTTP/1 محدود است؛ Content-Length و chunked ساده را می‌پذیرد و framing مبهم، compression، trailer/extension و عبور از سقف‌ها را نامعلوم/ردشده گزارش می‌کند، نه پاک.
- دادهٔ خصوصی و متن خام در حافظهٔ runner می‌مانند؛ گزارش پالایش‌شده منتشر می‌شود. هیچ hash از مقادیر خصوصی صادر نمی‌شود.
- همان حفاظ‌های G65: فقط ویندوز موقت github-hosted، مقصدهای قبلی و استثنای مدیریت CI؛ بررسی کامل TLS/ابطال، آزمون بومی قبل از اجرا، یک Continue شناخته‌شدهٔ زبان، مشاهدهٔ محدود، بدون ورود و Install و نصب بازی.
- نه شاخهٔ main و نه نسخهٔ 0.9.10 تغییر نمی‌کند. این مشاهده‌گر هنوز مسدودساز معنایی محتوای درخواست‌ها نیست و پوشش کامل دانلود را اثبات نمی‌کند.

کنترل‌ها: آزمون‌های واحد شامل شکستن پاسخ در تمام مرزهای بایت، chunked، context اشتباه، framing مبهم، دادهٔ ناقص، تشخیص صفر، ساختار User-Agent و عدم افشای raw هستند. تست‌ها قبل از build بومی و تغییر فایروال دوباره روی runner اجرا می‌شوند.
