# G52 — بازشماری محتوای موجود و اعتبارسنجی نحوی ناظر در ویندوز

این مرحله آزمایش زنده جدید بتل‌نت نیست و هم‌ارزی با تنظیم موفق RC را ادعا نمی‌کند.
فایل reports/level3-audit-t11-user.json از قبل در مخزن بوده؛ فقط همین ورودی بازشماری می‌شود. هیچ داده خصوصی جدید، کد بسته RC یا ضبط خام به مخزن افزوده نمی‌شود.

واحد داده یک ردیف درخواست بازسازی‌شده API است؛ نه فایل یکتا، نه حجم ترافیک و نه بستهٔ تحویل‌شده به سرور. درخواست‌های دارای metadata تکراری حذف نمی‌شوند، زیرا مقادیر URL/هدر در منبع صادر نشده‌اند. پروفایل‌کردن مستقیم JSON تو در تو ردیف‌های مصنوعی/خالی می‌سازد؛ تحلیل صریحاً از audit.requests استفاده می‌کند.

در نمونه قبلی ۲۶ درخواست Level3 قابل بازشماری است؛ GET و بدنه مشاهده‌شده صفر است. این یافته نبود فینگرپرینت، نبود شناسهٔ کدگذاری‌شده یا پوشش کامل را ثابت نمی‌کند. برای us.version.battle.net ردیف درخواست صادرشده نداریم؛ صفر ردیف به معنای صفر ترافیک نیست. چهار tuple فرایند/مقصد ۴۴۳ بدون محتوای ثبت‌شده به هیچ‌یک از این دو نام نسبت داده نمی‌شود.

CI ویندوز فقط ParseFile ناظر محلی و تست تحلیلگر را اجرا می‌کند؛ نه نصب‌کننده، نه ضبط زنده و نه تغییر فایروال. فایل CAPTURE.fa.md روش ضبط محلی را توضیح می‌دهد ولی برای آزمون زندهٔ گیت‌هاب هنوز باید ناظر مستقل، انتساب پردازش و پوشش هر دو مقصد آماده و بررسی شوند. این محدودیت دلیل اعلام نتیجهٔ نامشخص است، نه رفتن دوباره به بحث امکان دانلود.
