# G15a — احراز هویت اتصال پیش از forward

آزمون محدود Windows-2025 با client ساختگی x64/x86 و اتصال‌های loopback IPv4/IPv6. نصاب واقعی و نسخه ۰.۹.۱۰ دست‌نخورده‌اند. این مرحله به‌تنهایی ابزار آماده نصب نیست.

peer_guard از GetExtendedTcpTable برای نگاشت tuple معکوس اتصال پذیرفته‌شده به PID استفاده می‌کند، handle فرایند را باز نگه می‌دارد و PID + FILETIME ایجاد + مسیر EXE را با دفتر خصوصی تطبیق می‌دهد. نبود/ابهام در نگاشت، انقضای دفتر، خطای هویت یا عدم ثبت، مجوز نیست. احراز قبل از خواندن HTTP/ClientHello، دوباره قبل از هر dial و پیش از ارسال داده تکرار می‌شود. در relay نیز پیش از ارسال chunk احراز می‌شود.

دفتر peers.json باید توسط کنترل‌کننده مورد اعتماد در پوشه محافظت‌شده ProgramData ایجاد شود؛ مسیر و reparse بررسی می‌شود و DACL آزمایش فقط SYSTEM/Administrators است. این سازوکار مهاجم دارای دسترسی Administrator/SYSTEM یا دست‌کاری کد درون فرایند مجاز را مهار نمی‌کند.

Harness کد اصلی connect/handler را اجرا می‌کند اما تمام dialهای upstream را فقط به گیرنده شمارشگر محلی هدایت می‌کند؛ هیچ اتصال بیرونی به Battle.net یا IP نمونه انجام نمی‌شود. HTTP و ClientHello ساختگی‌اند؛ TLS واقعی، اعتبارسنجی گواهی و محتوای HTTPS در این مرحله آزموده نمی‌شوند. مسیر کنترل موقت harness در main پروکسی وجود ندارد.

هر معماری ۲۸ مورد دارد: فرایند مجاز/نامجاز برای HTTP، پورت نسخه 1119، TLS و CONNECT در IPv4/IPv6؛ PID، زمان ایجاد و مسیر جعل‌شده در دفتر؛ دفتر منقضی؛ لغو مجوز پس از پاسخ اولیه CONNECT و پیش از ClientHello؛ و تزریق صریح خطای ابهام owner. در موارد رد باید هم شمارنده تلاش dial، هم تعداد اتصال و هم بایت گیرنده upstream صفر بماند. خطای ابهام مصنوعی است؛ سایر نگاشت‌های peer از API واقعی ویندوز خوانده می‌شوند.

محدودیت حیاتی: این سد WFP کرنلی یا اثبات ایمنی socket duplication نیست. انتساب TCP owner لزوماً هویت هر فرایندی را که handle مشترک/duplicated دارد ثابت نمی‌کند؛ check و dial نیز اتمیِ کرنلی نیستند. ثبت خودکار فرزندان و سرویس واقعی، یکپارچگی با کل فایروال G14، PID reuse واقعی، همه raceها و «صرفاً دانلود» اثبات نمی‌شوند. قابلیت ثبت PID بدون احراز منبع نباید به نصاب داده شود. ضرورت تلمتری موضوع این مرحله نیست.
