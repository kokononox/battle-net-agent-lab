# G57 — مشاهده WinINet علاوه بر Winsock، پس از همان guard یک‌بارهٔ زبان

فایل pinشدهٔ نصب‌کننده از InternetConnectA، HttpOpenRequestA و HttpSendRequestA در WININET.dll استفاده می‌کند. این ناظر به همان exportها وصل می‌شود و ورودی درخواست را قبل از TLS در حافظه می‌بیند؛ نبود داده در send/WSASend را با نبود درخواست برابر نمی‌گیرد.

کنترل مثبت native Winsock قبلی و کنترل جدید WinINet در هر دو x86/x64 الزامی‌اند. کنترل WinINet فقط به HTTPServer با آدرس loopback و پورت تصادفی وصل می‌شود؛ POST، query و بدنهٔ کاملاً ساختگی دارد. بایت/مسیر/بدنهٔ دقیق در سرور دریافت‌کننده و ورودی API کنترل می‌شوند. دادهٔ مصنوعی وارد گزارش واقعی نمی‌شود. شکست هر کنترل مانع اجرای نصب‌کننده است.

در اجرای واقعی، server/port از InternetConnect و method/path از HttpOpenRequest و هدر صریح/بدنه از HttpSendRequest پیوند می‌خورند. خروجی فقط برای دو نام هدف و به شکل metadata/سرنخ لغوی است؛ مقدار URL، هدر، User-Agent یا بدنه صادر نمی‌شود. نام هدر ناشناخته به other تبدیل می‌شود. مقدارهای API ممکن است شناسه opaque/encoded داشته باشند؛ گزارش نبود فینگرپرینت صادر نمی‌شود.

نتیجه HttpSendRequest و کد خطا جدا ذخیره می‌شود. حتی returned_true اثبات مستقل دریافت/ذخیره سرور نیست و returned_false به معنای ارسال‌نشدن همه بایت‌ها نیست. درخواست‌های automatic redirect/retry و هدرهای خودکار، Cookie store، async و APIهای دیگر کامل پوشش داده نشده‌اند. user_agent_argument_present فقط وجود پارامتر را می‌گوید، نه محتوای دقیق یا نبود شناسه. مقدار سرور خارج از دو نام در خروجی عمومی منتشر نمی‌شود و فقط یک شمارش unknown/other دارد؛ مقصد جدید خودکار مجاز نمی‌شود.

همان pin/امضا، gate IP-based با استثناهای CI، native Job، guard دقیق یک‌بارهٔ زبان و پاکسازی حفظ شده است. هیچ Install/ورود/پذیرش شروط/نصب بازی کلیک نمی‌شود. این VM همان محیط RC کاربر نیست و نتیجهٔ آزمایش موفق دو مقصد کاربر زیر سؤال نمی‌رود.
