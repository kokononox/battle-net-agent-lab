# G54 — تفکیک نقص ناظر از وضعیت رابط کاربری

ابتدا روی VM تازه ویندوز، دو fixture بومی C# با platform=x86 و x64 ساخته می‌شود. هرکدام فقط به loopback با پورت تصادفی سرور آزمون وصل می‌شوند. یک send و یک WSASend همگام با دو buffer، دو درخواست معلوم و کاملاً ساختگی می‌فرستند. Host ساختگی نام دو مقصد است اما هیچ اتصال خارجی یا DNS مربوط به این fixture وجود ندارد. دریافت بایت‌های دقیق در سرور و ناظر، تطابق peer/port و نصب hook مستقل کنترل می‌شود. داده fixture در گزارش واقعی مخلوط نمی‌شود. شکست هرکدام مانع اجرای نصاب است.

تنها پس از کنترل مثبت معتبر مربوط به همان run/commit، راه‌اندازی۹۰ثانیه‌ای G53 با همان pin/امضا و ایزولاسیون ماشین موقت تکرار می‌شود. وضعیت root و فرزندان مشاهده‌شده و پنجره‌هایشان با Win32 فقط خوانده می‌شود؛ هیچ کلیک یا advance زبان/نصب وجود ندارد. متن خام UI، URL، مقدار هدر، بدنه و مشخصات سخت‌افزار صادر نمی‌شود. کنترل‌های edit/password/ناشناخته خوانده نمی‌شوند. کلاس/labelهای ثابت و markerهای لغوی صرفاً سرنخ‌اند، نه اثبات مرحله نصب.

گروه ترکیبی peer قبلی اکنون به selected_target_IP، loopback، other_IP، peer_query_failed و peer_invalid تفکیک می‌شود. پاسخ صفر همچنان نامشخص است. موفقیت fixture تضمین همه APIها، async، TLS، HTTP2 یا پوشش نصب‌کننده نیست. ایزولاسیون IP-based با استثناهای مشخص مدیریت CI است؛ همان تنظیم RC کاربر یا دانلود کامل نیست. بازگردانی snapshot فایروال فقط بر ماشین مصرفی گیت‌هاب پس از توقف هدف انجام می‌شود.
