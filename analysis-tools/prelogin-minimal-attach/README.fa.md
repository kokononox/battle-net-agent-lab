# b3: راه‌اندازی عادی + اتصال حداقلی Frida، بدون hook

این مرحله پس از موفقیت کنترل بدون Frida در b2 است. همان bootstrap با SHA pin و Authenticode معتبر، همان Popen عادی، stdin/stdout/stderr عادی observer و همان پنجرهٔ ۱۵۰ ثانیه‌ای حفظ می‌شود. بلافاصله پس از Popen، فقط به **بوت‌استرپِ متعلق به آزمایش** attach می‌شود؛ نه به Agent یا فرایندهای دیگر. هیچ Frida spawn، suspend/resume، child gating، hook رجیستری یا hook شبکه درخواست نمی‌شود.

اتصال Frida خودش بارگذاری کد ابزار در فرایند است؛ بنابراین برخلاف b2، «بدون تزریق» نیست. منظور از حداقلی، نداشتن hook و داشتن تنها یک اسکریپت ثابت readiness است:

```js
send({kind:'ready',pointer_bits:Process.pointerSize*8});
```

به DLL/processهای دیگر attach نمی‌شود. دامنهٔ این مرحله صرفاً بررسی ادامهٔ کار bootstrap در حضور این اتصال است؛ جمع‌آوری یا رمزگشایی شبکه در آن انجام نمی‌شود.

## گیت و ایمنی

پیش از هدف، دو برنامهٔ C++ خودِ پروژه با MSVC برای x86/x64 ساخته می‌شوند. آن‌ها فقط روی stdin یک بایت می‌خوانند و شبکه/رجیستری هدف ندارند. هر کدام با Popen معمولی اجرا می‌شود؛ مسیر/hash و creation identity قبل و بعد از attach تأیید و بیت‌بودن از اسکریپت کنترل می‌شود؛ پس از readiness، یک newline برنامه را با exit صفر تمام می‌کند. فقط عبور هر دو گیت اجازهٔ اجرای bootstrap را می‌دهد. فایل‌های exe/build خصوصی و موقت‌اند.

هدف باید همان SHA قبلی و ناشر معتبر باشد؛ Popen handle باز، مالکیت همان process object را حفظ می‌کند و path/hash/creation پیش و پس از اتصال دوباره بررسی می‌شوند. گزارش فقط نتیجهٔ بررسی را صادر می‌کند، نه مسیر، PID، creation time، session ID یا آدرس حافظه. عملیات Frida با cancellable هشت‌ثانیه‌ای و readiness سه‌ثانیه‌ای محدود است. شکست اتصال نتیجهٔ موفق تلقی نمی‌شود؛ observer ممکن است به مشاهدهٔ عادی ادامه دهد، اما target_attach.status آن را جدا نشان می‌دهد.

پنجرهٔ زبان فقط با همان helper دارای بررسی امضا/صفحه/PID مجاز است؛ پس از شروع helper یا ابهام retry نمی‌شود. Install، login، دانلود بازی، تغییر TLS، دسترسی از راه دور، کلید رجیستری هدف و سؤال دوم دست‌نخورده‌اند. محیط فرزند فقط allowlist قبلی است و tokenهای GitHub منتقل نمی‌شوند.

## خواندن نتیجه

status=observation_complete یعنی مشاهدهٔ زمان‌دار کامل شده است؛ لزوماً نه attach موفق است و نه Agent دیده شده. target_attach، readiness و native_gate باید جدا خوانده شوند. حتی اگر attach آماده و Agent مشاهده شود، فقط وجود این مرحلهٔ startup در حضور attach نشان داده می‌شود؛ اتصال به خود Agent یا تلمتری آن اثبات نشده است.

اتصال بعد از launch است: process_birth_coverage=false و شبکهٔ ابتدای عمر فرایند پوشش داده نمی‌شود. این یک کنترل تشخیصی است، نه جایگزین شواهد شبکهٔ پیشین a11. این مرحله و b2 روی یک ماشین نیستند؛ ادعای علت قطعی یا anti-Frida بودن/نبودن نصاب مجاز نیست. بازهٔ ۱۵۰ ثانیه پس از برگشت Popen wrapper شروع می‌شود و زمان attach جزء آن نیست؛ پس زمان‌بندی دقیقاً هم‌ارز b2 نیست.

۳۸ آزمون محلی دربارهٔ پیام readiness، identity قبل/بعد، bitness، شکست و duplicate، عدم فراخوانی spawn/child gating، pin/gate پیش از target، حدود گزارش و جلوگیری از ادعای causality/coverage پاس شدند. این‌ها نتیجهٔ Windows نیستند. گزارش عمومی فقط دو JSON محدود runtime/CI است؛ native binaries، UI متن‌خام، UUID/هش آن یا capture منتشر نمی‌شود.
