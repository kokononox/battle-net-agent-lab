# مرز محصول: ایزولاسیون کل زنجیره نصب Battle.net

## هدف قطعی
خروجی نهایی یک پکیج اجرایی اختصاصی ویندوز برای کنترل ارتباطات مرتبط با نصب Battle.net است؛ نه صرفاً نمایش DNS و نه فهرست مجاز IP. نسخه Unified Firewall Desktop 0.9.10 منجمد و خارج از این تغییرات است. پرونده تحقیق جاری فقط دو نام دقیق `level3.blizzard.com` و `us.version.battle.net` را نامزد مجاز می‌داند. بررسی ضرورت تلمتری از آزمایش‌ها حذف شده است.

«فقط نصب» یعنی درخواست مجاز باید علاوه بر مقصد، نقش مستند در دریافت/اعتبارسنجی/اعمال فایل‌های نصب داشته باشد. GET لزوماً بی‌خطر یا صرفاً دانلود نیست؛ داده ممکن است در URL یا header هم ارسال شود. POST نیز بدون بررسی محتوا، خودبه‌خود غیرنصبی محسوب نمی‌شود. نام دامنه، رنگ ردیف، DNS موفق، پورت باز و نصب موفق به‌تنهایی اثبات این شرط نیستند.

## واحد مدیریت
یک نشست نصب شامل Setup، فرزندانش، Agent، کارهای زمان‌بندی‌شده و سرویس‌های مرتبط است. نمایش باید این زنجیره را به‌صورت یک بسته با راه‌های ارتباطی قابل انتخاب نشان دهد، نه چند ردیف تکراری و مستقل. PID به‌تنهایی هویت نیست: مسیر، امضای فایل، اثرانگشت باینری، زمان ایجاد فرایند و ارتباط آن با نشست باید بررسی شود. سرویس مشترک ویندوز مجوز کلی دریافت نمی‌کند.

Job Object می‌تواند فرزندان عادی را مهار کند، اما SCM ممکن است سرویسی را خارج از آن اجرا کند. بنابراین عضویت فرزندان در job به‌تنهایی اثبات پوشش سرویس‌ها نیست. دروازه خروجی و ثبت تغییرات سرویس/وظیفه باید مستقل از شمارش فرزندان عمل کنند. فرایند ناشناخته، تغییر هویت فایل یا خروج از پوشش، نتیجه را نامشخص/متوقف می‌کند؛ مجوز خودکار نمی‌گیرد.

## لایه‌های تفکیک
1. **قانون شبکه:** منع پیش‌فرض، رد خروج مستقیم و مسیرهای جایگزین، درگاه اختصاصی با مقصد پین‌شده، تطبیق Host/SNI؛ IP مشترک کافی نیست.
2. **شواهد درخواست:** فرایند صادرکننده، مرحله نصب، پروتکل/پورت، روش، الگوی مسیر، انواع header/body، بایت ارسال/دریافت، پاسخ/redirect و اثر آن بر فایل نصب. مقادیر خام حساس نباید وارد artifact شوند.
3. **طبقه‌بندی:** ضروری برای نصب، غیرمرتبط اثبات‌شده، یا نامشخص. حالت صرفاً نصب موارد نامشخص را خودکار ضروری نمی‌نامد. مسیر قطع‌شده باید دلیل روشن داشته باشد.
4. **آزمون مداخله‌ای هدفمند:** حذف/محدودکردن هر الگوی درخواست در همین دو مقصد، نصب تمیز و بررسی هویت/نسخه/امضای خروجی؛ موفقیت یک بار یا صرف شروع دانلود کافی نیست. آزمایش تلمتری جداگانه از سر گرفته نمی‌شود.

TLS در درگاه فعلی پایان داده یا رمزگشایی نمی‌شود. SNI فقط شاهد نام در handshake است، نه شاهد URL، header، بدنه یا Host داخل TLS. برای طبقه‌بندی HTTPS باید ثبت کنترل‌شده در مرز API برنامه، پیش از رمزگذاری، با پوشش x86/x64 و بدون تغییر CA یا غیرفعال‌کردن اعتبار گواهی انجام شود. نبود مشاهده در API به معنی نبود درخواست نیست.

## ایمنی چرخه اجرا
- backup و کنترل بازیابی پیش از تغییر؛ تفکیک پیش‌نویس از قانون مؤثر.
- فعال‌شدن دروازه پیش از اجرای نخستین دستور Setup.
- timeout، بسته‌شدن UI و خرابی ناظر نباید در حالی که مؤلفه نصب زنده است شبکه را آزاد کنند.
- پیش از برداشتن محدودیت، پایان زنجیره و سرویس/وظیفه متعلق به آزمایش باید احراز شود. در ماشین موقت، اگر این پایان قابل اثبات نباشد، محدودیت حفظ و VM کنار گذاشته می‌شود؛ بازگشت fail-open مجاز نیست.
- اجرا پس از reboot و سرویس دیرهنگام تا پیش از آزمایش مستقل، پشتیبانی‌شده اعلام نمی‌شود.
- استثنای Runner.Listener/Worker فقط برای مدیریت آزمایش GitHub است و بخشی از محصول نهایی یا مجوز نصب‌کننده نیست.

## شرط تحویل اجرایی
درگاه شبکه، پوشش فرایند/سرویس، مشاهده درخواست، نصب تمیز تکرارشونده و بازیابی باید جداگانه آزموده و گزارش شوند. موفقیت workflow به معنی موفقیت این شروط نیست. تا زمانی که محتوای ارتباطات TLS و مسیرهای خارج از پوشش تعیین تکلیف نشده‌اند، عبارت «تضمین فقط ترافیک نصب» و نسخه نهایی قابل اتکا اعلام نمی‌شود.

## وضعیت این سند
این سند قرارداد پذیرش و طراحی است، نه ادعای پیاده‌سازی یا آزمون کامل. G5 راه‌اندازی چهار listener و بازیابی IIS را ثبت کرد؛ آزمون HTTP us.version پیش از اعمال فایروال تأیید نشد. هیچ Setup در G1 تا G6 اجرا نشده است. G6 فقط برای تشخیص ثابت پروتکل/پورت دو مقصد تعریف شده است.
